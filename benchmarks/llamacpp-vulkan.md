# Как устроен llama.cpp Vulkan и почему он быстрее нас

Источник: `/tmp/llama.cpp` master `ad9d9e8`, `ggml/src/ggml-vulkan/vulkan-shaders/`.

## 1. GEMM (prefill): `mul_mm.comp`

| параметр | значение |
|---|---|
| WG | `BLOCK_SIZE = 64` (2 warp) |
| тайл выхода | `BM = 64`, `BN = 64` |
| тайл по K | `BK = 16` для квантованных весов (`BK_STEP = 2`) |
| на поток | `WM = 32`, `WN = 32`, `WMITER = 2`, `TM = 4`, `TN = 2` → **8 аккумуляторов**, тайл 4×2 |
| LDS | `buf_a[BM * (BK/2 + 1)]`, `buf_b[BN * (BK/2 + 1)]` типа **`FLOAT_TYPEV2`** (пары f16) |
| математика | **f16 FMA с f32-накоплением** (`FLOAT_TYPE = float16_t`), де-квант при загрузке в LDS |
| coopmat | отдельная ветка (`GL_KHR_cooperative_matrix`) для карт с matrix cores; на RDNA2 её нет |

Ключевое: веса и активации **де-квантизуются в f16 при загрузке в LDS**, дальше — упакованная
f16-математика (`half2`), по 8 независимых аккумуляторов на поток, без эпилога на группу.

## 2. Flash-attention: `flash_attn.comp`

- Тайл по **запросам** `Br` (block_rows) на workgroup, KV итерируется блоками `Bc`.
- `Qf` — в shared как `FLOAT_TYPEV4` (f16×4), K/V стейджатся в shared (или читаются из global
  на дискретных AMD), `Of[rows_per_thread][HSV/4]` — **аккумуляторы в регистрах**.
- Online softmax (`Mf`, `Lf`, `slope`), маска — в shared (`masksh[Bc * (Br+1)]`).
- Есть «flip»-режим: каждый subgroup владеет 16 Q-строками.
- Комментарий в коде: `Br=32 spills registers, only prefill benefits`.

То есть K/V читаются **один раз на блок запросов**, а не на каждый запрос.

## 3. Наш OpenCL-движок: что и почему отстаёт

Замеры (RX 6400, Q4_K_M 1.7B): prefill 512 — 597 tok/s против 1393 (×2.3),
8192 — 402 против 1236 (×3.1), decode — 64 против 91 (×1.4).

| наш тайл | llama.cpp |
|---|---|
| RT=32 строк × TT=32 токена, WG 256 | BM=64 × BN=64, WG 64 |
| 1 строка × 4 токена на поток = **4 аккумулятора** | 4×2 = **8 аккумуляторов** |
| int8 dp4a, LDS — int8-байты | f16 `half2` FMA, LDS — f16-пары |
| float-эпилог на 32-группу (sc×dot − mn×sum) | f16-накопление, эпилог один раз на строку |

### Замеренные потолки (честный микробенч, `lfm-bench dot-rate`)

| формат | MAC/s | что это |
|---|---|---|
| **int8 `dot(char4,char4)`** | **3.07 T** | 0.77 T dp4a/s = 43% тактов на дорожку |
| f16 packed `fma(half4,half4)` | 2.08 T | 4.17 TFLOP/s |

То есть **int8 на 48% быстрее f16** на Navi 24 — остаёмся на W4A8.

Мы выжимаем 0.76 T MAC/s = **25% от int8-пика**, llama.cpp — ~1.65–2.35 T MAC/s = 46–66%.
Цель: **86–90% = 2.6–2.8 T MAC/s**.

Где теряются 3.5x (по инструкциям на 32 значения на токен):

| статья | сейчас | предел |
|---|---|---|
| dp4a | 8 | 8 (18.6 такта при 0.43 dp4a/такт/дорожку) |
| загрузка x из LDS | 2 | 2 |
| загрузка весов | ~0.5 (на группу, делится на 4 токена) | 0.5 |
| **эпилог (cvt+mul+fma на группу-токен)** | **3** | 0 (int-накопление, скейлы раз на блок) |
| **аккумуляторов на поток** | **4** (не хватает ILP на латентность dp4a) | 8 |
| тайл по строкам | 32 (переиспользование веса ×32) | 64 (×64) |

Итого структурный потолок текущего ядра ≈76%, а фактически 25% — остальное дают простои
на зависимой цепочке `acc += dot` (4 цепи на поток) и латентности LDS.

**Важная поправка к предыдущим выводам:** llama.cpp Vulkan для Q4_K тоже использует
`v_dot4_i32_i8` (dp4a), а не f16-математику — то есть мы с ним в одном формате, и разрыв
не в int8 против f16, а в планировании/тайлинге/занятости. Атрибуты их шейдера: 8
аккумуляторов (TM=4, TN=2), 64×64 тайл, **ноль scratch-спилов**, ~410 LDS-чтений на 1024
dp4a (≈2.5 dp4a на чтение).

### ISA нашего ядра (снято через `sdot4`-заглушку и system clang 23)

| | `lds11` (портируемый `dot(char4,char4)`) | packed-uint + `__builtin_amdgcn_sdot4` |
|---|---|---|
| инструкций | **15273** | **3267** (×4.7 меньше) |
| из них dp4a | 1040 (**7%**) | 528 (**16%**) |
| `v_mov_b32` | 2994 | 437 |
| `v_perm_b32` (свизлы char4/char16) | 2400 | **0** |
| приватный сегмент (спилы) | **176–352 Б** | **0** |
| VGPR | 256 (максимум) | 188 |
| `ds_*` | 74 | 120 |

То есть портируемая формулировка через `char4`/`.s0123` порождает гору `v_perm` и спилов.

**Но:** внедрение packed-uint версии в реальное ядро **не изменило время** (1.31 мс против
1.32 мс). Значит ядро **не instruction-bound**: 4.7x меньше инструкций не дают ничего.
Остаются: глобальный трафик x (он перечитывается на каждый row-тайл: ~48 МБ на вызов при
идеале 9.1 МБ), занятость/LDS-латентность и барьеры (2 на блок).

### Что сделано по итогам ISA-разбора

1. **Packed-uint формулировка** (`as_char4` → маска на `uint`, без char16-свизлов) — в
   изолированном тесте ISA даёт 3267 инструкций вместо 15273 и ноль спилов, но на времени
   не сказывается: ядро не instruction-bound.
2. **`__builtin_amdgcn_sdot4` в Rusticl недоступен**: Rusticl компилирует через SPIR-V,
   target-специфичные builtins и `__AMDGCN__` не определяются (проверено — сборка падает
   с `use of undeclared identifier`). Поэтому host-define `-DLFM_AMD=1` бесполезен.
3. **Тайл 64×32 при WG=512** (`gemm_q4_k_i8_lds17`): два row-тайла по 32 строки в одной
   группе делят один x-тайл ⇒ глобальный трафик x вдвое меньше (~33 МБ против 48 МБ на
   `ffn_up`), регистров столько же (4 аккумулятора). **Это единственное, что дало выигрыш.**

| | lds11 (32×32, WG 256) | lds17 (64×32, WG 512) |
|---|---|---|
| `ffn_up` @64 токена | 1.32 мс | **1.18 мс** (−11%) |
| prefill 512 | 577 tok/s | **615 tok/s** (+6.6%) |
| prefill 8192 | 399 tok/s | **416 tok/s** (+4%) |

Вывод: на этом GPU GEMM упирается не в инструкции, а в трафик/латентность; двигаться дальше
надо тайлами (ещё больше строк на общий x-тайл) и двойной буферизацией LDS, а не
«сокращением числа инструкций».

### Предел тайла (проверено)

Тайл 128×32 требует WG=1024 → `CL_INVALID_WORK_GROUP_SIZE`: при нашем регистровом бюджете
устройство даёт максимум 512 потоков на группу. То есть 64×32 (WG 512) — практический
предел на этой оси, дальше только через снижение VGPR на поток.

### Flash-attention: гипотеза опровергнута

Сделал ядро `attention_flash_b_h4`: WG 256 = 4 подгруппы по 64, подгруппа = один запрос,
`sub_group_reduce_add` вместо LDS-редукции, K/V читаются один раз на 4 запроса.

- корректен при `splits == 1` (cos 0.9997), при `splits >= 2` — ошибка (не нашёл);
- **выигрыша нет**: 512 tok/s — 620 с ним против 625 без него.

Значит attention при 8192 не bandwidth-bound, как я предполагал, а **compute-bound**:
13 TFLOP f32 / 7.9 с ≈ 1.65 TFLOP/s при пике 3.5 — то есть ~47% утилизации, и упирается
он в f32-математику и редукцию, а не в чтение K/V (объём K/V и так укладывается в L2).

Ядро удалил (непроверенный код в дефолт не пускаем).

### Attention: что ещё проверил (всё нейтрально)

| гипотеза | результат (8192 tok/s) |
|---|---|
| тайлинг по запросам (K/V раз на 4 запроса) | 620 против 625 — нет |
| `half2`-математика в QK-доте | 413–421 против 424–426 — нет |
| `sub_group_reduce_add` вместо двухстадийной LDS-редукции (убрал сериализацию на lane 0) | 423–424 против 424–426 — нет |

Расчёт по числам: attention при 8192 — ~2.9 TFLOP за 7.9 с ≈ **370 GFLOP/s = 10% от f32-пика**.
На 4 позиции на дорожку приходится 32 MAC, но **16 редукций** (4 головы × 4 позиции) по 6
шагов — редукции в 3 раза дороже полезной работы. Это структурная проблема отображения
(«одна оценка = одна кросс-дорожная сумма»), а не трафика и не формата.

Следующий настоящий шаг — сменить отображение: держать 4–8 **позиций** в дорожке и делать
одну «транспонирующую» редукцию на пачку (как butterfly-редукция 32×32 в flash-attn),
либо считать attention через матричный тайл (позиции × головы) с регистровым блоком.

### Следующие эксперименты (по приоритету)

1. **Свип по тайлам без роста регистров**: RT=16/32/64 при 4 аккумуляторах, WG=128 vs 256 —
   цель: вдвое меньше перечитываний x (RT=64) при том же регистровом бюджете.
2. **Двойная буферизация LDS** — убрать один из двух барьеров на блок.
3. **Проверить, что Rusticl вообще определяет `__AMDGCN__`** (иначе `sdot4`-путь не
   включается): если нет — передавать `-DLFM_AMD=1` с хоста по имени устройства.

Скрипт разбора ISA:

```python
import re
lines=open('radv.log',errors='ignore').read().split('\n')
shaders=[];cur=None
for l in lines:
    if l.startswith('shader: MESA_SHADER'): cur=[]; shaders.append(cur)
    elif cur is not None: cur.append(l)
for idx,body in enumerate(shaders):
    instr=[l for l in body if re.match(r'^\s+(v|s|ds|buffer|scratch|exp|image)_', l)]
    if not instr: continue
    dots=sum('v_dot4' in l for l in instr)
    print(idx, len(instr), dots, sum('ds_' in l for l in instr))
```

| веса распаковывать внутри цикла по токенам (меньше регистров) | ×4.5 хуже: распаковка (32 ops) повторяется на каждый токен |

Вывод: узкое место **не** в числе аккумуляторов, не в I-cache и не в ветвлениях.
Следующий шаг — не гадать, а посмотреть сгенерированный ISA: сдампить бинарь ядра
(`CL_PROGRAM_BINARY`) и проверить (а) компилируется ли `dot(char4,char4)` в одну
`v_dot4_i32_i8` (в микробенче — да, иначе не было бы 3.07 T MAC/s), (б) нет ли `scratch`
(спилов) в горячем цикле, (в) сколько `ds_read` на 16 dp4a. Это даст точный ответ,
где теряются 3.5x.

### Проект нового ядра (цель 86–90%)

- WG **256**, тайл **RT=64 строки × TT=32 токена** (2048 выходов, 8 на поток).
- На поток: **2 строки × 4 токена = 8 аккумуляторов** (в 2 раза больше ILP).
- Веса — в LDS (8 КБ на блок, 64 строки × 128 Б), x — в LDS (8 КБ), двойная буферизация
  (32 КБ, влезает в 64 КБ).
- Активации квантуются **одним скейлом на 256** (как у llama.cpp) ⇒ эпилог: `sumi += dot*sc`
  (2 int-операции) вместо cvt+mul+fma, и раз на блок — `acc += dx*sumi - dm*sumn`.
- Внутренний цикл: на группу 64 dp4a (2 строки × 4 токена × 8), 2 загрузки весов
  (`uint4`), 8 загрузок x (`char16`), 16 int-операций эпилога ⇒ доля dp4a ≈ 71%,
  расчётный потолок ≈2.3–2.5 T MAC/s (75–82%). Дальше — вынос скейлов в отдельный проход
  и `v_dot4` через `__builtin_amdgcn_sdot4`, чтобы добрать до 86%+.
- Проверка: `gemm-cmp` (kernel vs CPU), затем `gpu-prefill 512/2048/8192` парами,
  при 2.5 T MAC/s ожидаем **~1100–1300 tok/s на 512** (llama.cpp 1393) и **×3.3** на GEMM.

**Attention** — отдельная история: мы читаем K/V на каждый запрос
(`attention_split_b_h4_p4`: WG на (token, kv_head, split)), поэтому при 8192 это 7.9 с из 20.4
(40%). llama.cpp читает K/V один раз на `Br` запросов.

## 4. План (по убыванию отдачи)

**A. GEMM на f16 + тайл 64×64 (помогает всему prefill)**
- де-квант Q4_K/Q6_K → f16 при загрузке в LDS (как у них), `half2`-FMA, f32-аккумулятор;
- WG 64 (2 warp), BM=64, BN=64, BK=16, на поток 4×2 = 8 аккумуляторов, SHMEM_STRIDE = BK/2+pad;
- ожидание: 1.33 → 0.65 мс на `ffn_up` при 64 токенах ⇒ prefill ×1.6–2.0 (≈1000–1200 при 512).

**B. Flash-attention с тайлом по запросам (главный резерв на 8192)**
- WG: 32–64 запроса × блок KV 64, K/V в LDS как f16×4, Q — в регистрах/`__local`,
  аккумуляторы в регистрах, online softmax, маска в `__local`;
- ожидание: attention 7.9 → 2.5 с ⇒ 8192: 20.4 → ~15 с (≈550 tok/s), затем и больше при
  переходе на f16-математику в самом attention.

**C. Decode (GEMV)**
- f16-дот по 8 строк на workgroup, широкие `half4`-загрузки, банковое выравнивание;
- ожидание: 64 → 85–95 tok/s.

**D. Мелочи**
- `half`-активации в KV (уже f16), `v_dot2_f32_f16` через `__builtin_amdgcn` (если драйвер
  даёт), отказ от лишних `barrier` (двойная буферизация LDS).

## 5. Как проверяем

Каждый шаг: `gemm-cmp` (kernel vs CPU-эталон), `gpu-cmp --batch 128` (граф), затем
`gpu-prefill --tokens 512/2048/8192` парами против текущего дефолта, и только после этого —
сравнение с `llama-bench` (Vulkan). При регрессе — откат.

## Агрегатные замеры: 1/2/4/8 параллельных запросов

Одинаковые условия: промпт 128 токенов на последовательность, декод 32, контекст 2048,
GPU RX 6400.

llama.cpp (`llama-batched-bench -npp 128 -ntg 32 -npl 1,2,4,8 -b 2048 -ub 512 -ngl 99`):

| B | PP tok/s | TG tok/s | всего tok/s |
|---|---|---|---|
| 1 | 719.7 | 89.1 | 298.1 |
| 2 | 1105.1 | 166.8 | 519.9 |
| 4 | 1273.3 | 251.6 | 702.6 |
| 8 | **1427.1** | **301.8** | **817.5** |

наш (`gpu-multi --seqs B --tokens 32 --prompt 128`, смешанный prefill общим батчем):

| B | PP tok/s | TG tok/s | всего tok/s |
|---|---|---|---|
| 1 | 638 | 46 | 178 |
| 2 | 648 | 81 | 270 |
| 4 | 653 | 114 | 335 |
| 8 | **656** | **118** | **344** |

Разрывы: prefill ×1.13 (B=1) → **×2.17** (B=8); decode ×1.95 → ×2.55; суммарно ×1.7 → ×2.4.

### Что это вскрыло

1. **llama.cpp масштабирует prefill с числом потоков** (720 → 1427, ×2), потому что кладёт
   все последовательности в один батч (`-b 2048`) и его GEMM выходит на **≈2.7 T MAC/s**
   (88% от замеренного int8-пика 3.07 T).
2. Мы префиллим чанками по 128 токенов на *все* последовательности (смешанный prefill уже
   работает) и упираемся в **≈1.5 T MAC/s (49%)** — при увеличении чанка до 512/1024
   aggregate не растёт (657 tok/s), то есть насыщение происходит на уровне GEMM-ядра,
   а не батчера.
3. Decode масштабируется у нас хуже (46 → 118, ×2.6 против ×3.4): при B=1 наш decode в этом
   стенде ниже одиночного замера (64 tok/s) из-за накладных `step_mixed` (перестройка
   таблиц KV каждый шаг) и скачивания логитов per-token.

### Что за этим делать

- **GEMM 49% → 88%**: единственный путь к паритету в агрегате. Сейчас на больших батчах
  ядро `lds17` (64×32, WG 512) упирается в 1.5 T; llama.cpp на 64×64-тайле с f16-LDS даёт
  2.7 T. Нужен либо тайл 64×64 (не влезает по VGPR при 512 потоках), либо снижение VGPR
  на поток (packed-uint версия показала 188 против 256 — с ней, возможно, влезет WG 1024
  и тайл 128×32).
- **Decode-оверхед**: argmax/сэмплинг на GPU и отказ от перестройки KV-таблиц на каждый
  шаг (кэшировать `tbl_off`/`pos_b` для неизменных последовательностей).

## Проверка «packed-uint + больший тайл» (не удалось)

1. **`gemm_q4_k_i8_lds20`** — packed-uint (маски на `uint`, без `char4`/свизлов) в тайле
   64×32: корректен, но по времени **то же самое** (1.295 против 1.274 мс). Ещё одно
   подтверждение, что ядро не instruction-bound.
2. **`gemm_q4_k_i8_lds19`** — тайл 128×32 при WG=1024 на packed-uint (188 VGPR вместо 256
   по ISA-дампу): всё равно `CL_INVALID_WORK_GROUP_SIZE`. То есть даже с меньшим числом
   регистров 1024 потока в группе это ядро не запускает — предел на стороне
   Rusticl/устройства, а не только наших VGPR.

Варианты удалены (нейтральные/незапускаемые).

### Вывод по GEMM

При больших батчах (512 токенов) наше ядро даёт **1.5 T MAC/s = 49%** от int8-пика;
llama.cpp на тех же условиях — **≈2.7 T = 88%**. Их преимущество складывается из:
- тайл 64×64 (вес переиспользуется на 64 токена, у нас — на 32);
- **64 потока на группу** (2 warp) против наших 512: меньше суммарных VGPR, отсюда
  больший тайл и 8 аккумуляторов на поток;
- f16-LDS-стейджинг с `SHMEM_STRIDE_PAD` (меньше банковских конфликтов).

Проверенная нами граница: 512 потоков — максимум, 1024 не запускается, 8 аккумуляторов
на поток при 256 потоках упираются в спилы. Значит следующий шаг — **перейти на 64–128
потоков на группу с 8–16 аккумуляторами** (как у них), а не пытаться втиснуть большой
тайл в широкую группу.

## Схема «мало потоков, много аккумуляторов» (как у llama.cpp) — не работает у нас

Сделал `gemm_q4_k_i8_wide`: WG 128/256, тайл **64×64**, 32 и 16 аккумуляторов на поток
(1 строка × 32/16 токенов, x читается из LDS как broadcast).

| вариант | `ffn_up` @64 токена | против `lds17` |
|---|---|---|
| `lds17` (WG 512, 64×32, 4 акк) | 1.32–1.41 мс | — |
| wide, 32 акк, WG 128 | 5.05 мс | **×3.8 хуже** |
| wide, 16 акк, WG 256 | 4.64 мс | ×3.5 хуже |
| wide, 16 акк, WG 256 + кооперативная загрузка x | 2.70 мс | ×2.0 хуже |

Все варианты корректны (max_rel 2.46e-5). Причина: 16–32 аккумулятора + операнды в
открытом виде дают спилы в private-память (Rusticl/LLVM), тогда как у llama.cpp тот же
приём компилируется через SPIR-V/ACO без спилов.

**Вывод: в OpenCL C на Rusticl оптимум — широкая группа (512 потоков) с 4 аккумуляторами.**
Дальнейший рост GEMM (49% → 88% пика) упирается не в алгоритм, а в кодогенерацию
Rusticl; варианты: генерировать SPIR-V самим, либо вернуть Vulkan-бэкенд (ACO), либо
смириться с текущим уровнем.
