# Как устроен llama.cpp Vulkan и почему он быстрее нас

Источник: `/tmp/llama.cpp` master `ad9d9e8`, `ggml/src/ggml-vulkan/vulkan-shaders/`.

## 1. GEMM (prefill): `mul_mm.comp`

| параметр | значение |
|---|---|
| WG | `BLOCK_SIZE = 64` (2 warp) |
| тайл выхода | `BM = 64`, `BN = 64` |
| тайл по K | `BK = 16` для квантованных весов (`BK_STEP = 2`) |
| на поток | `WM = 32`, `WN = 32`, `WMITER = 2`, `TM = 4`, `TN = 2` → **8 аккумуляторов**, тайл 4×2 |
| LDS | `buf_a[BM * (BK/2 + 1)]`, `buf_b[BN * (BK/2 + 1)]` типа **`FLOAT_TYPEV2`** (пары f16) |
| математика | **f16 FMA с f32-накоплением** (`FLOAT_TYPE = float16_t`), де-квант при загрузке в LDS |
| coopmat | отдельная ветка (`GL_KHR_cooperative_matrix`) для карт с matrix cores; на RDNA2 её нет |

Ключевое: веса и активации **де-квантизуются в f16 при загрузке в LDS**, дальше — упакованная
f16-математика (`half2`), по 8 независимых аккумуляторов на поток, без эпилога на группу.

## 2. Flash-attention: `flash_attn.comp`

- Тайл по **запросам** `Br` (block_rows) на workgroup, KV итерируется блоками `Bc`.
- `Qf` — в shared как `FLOAT_TYPEV4` (f16×4), K/V стейджатся в shared (или читаются из global
  на дискретных AMD), `Of[rows_per_thread][HSV/4]` — **аккумуляторы в регистрах**.
- Online softmax (`Mf`, `Lf`, `slope`), маска — в shared (`masksh[Bc * (Br+1)]`).
- Есть «flip»-режим: каждый subgroup владеет 16 Q-строками.
- Комментарий в коде: `Br=32 spills registers, only prefill benefits`.

То есть K/V читаются **один раз на блок запросов**, а не на каждый запрос.

## 3. Наш OpenCL-движок: что и почему отстаёт

Замеры (RX 6400, Q4_K_M 1.7B): prefill 512 — 597 tok/s против 1393 (×2.3),
8192 — 402 против 1236 (×3.1), decode — 64 против 91 (×1.4).

| наш тайл | llama.cpp |
|---|---|
| RT=32 строк × TT=32 токена, WG 256 | BM=64 × BN=64, WG 64 |
| 1 строка × 4 токена на поток = **4 аккумулятора** | 4×2 = **8 аккумуляторов** |
| int8 dp4a, LDS — int8-байты | f16 `half2` FMA, LDS — f16-пары |
| float-эпилог на 32-группу (sc×dot − mn×sum) | f16-накопление, эпилог один раз на строку |

### Замеренные потолки (честный микробенч, `lfm-bench dot-rate`)

| формат | MAC/s | что это |
|---|---|---|
| **int8 `dot(char4,char4)`** | **3.07 T** | 0.77 T dp4a/s = 43% тактов на дорожку |
| f16 packed `fma(half4,half4)` | 2.08 T | 4.17 TFLOP/s |

То есть **int8 на 48% быстрее f16** на Navi 24 — остаёмся на W4A8.

Мы выжимаем 0.76 T MAC/s = **25% от int8-пика**, llama.cpp — ~1.65–2.35 T MAC/s = 46–66%.
Цель: **86–90% = 2.6–2.8 T MAC/s**.

Где теряются 3.5x (по инструкциям на 32 значения на токен):

| статья | сейчас | предел |
|---|---|---|
| dp4a | 8 | 8 (18.6 такта при 0.43 dp4a/такт/дорожку) |
| загрузка x из LDS | 2 | 2 |
| загрузка весов | ~0.5 (на группу, делится на 4 токена) | 0.5 |
| **эпилог (cvt+mul+fma на группу-токен)** | **3** | 0 (int-накопление, скейлы раз на блок) |
| **аккумуляторов на поток** | **4** (не хватает ILP на латентность dp4a) | 8 |
| тайл по строкам | 32 (переиспользование веса ×32) | 64 (×64) |

Итого структурный потолок текущего ядра ≈76%, а фактически 25% — остальное дают простои
на зависимой цепочке `acc += dot` (4 цепи на поток) и латентности LDS.

### Проект нового ядра (цель 86–90%)

- WG **256**, тайл **RT=64 строки × TT=32 токена** (2048 выходов, 8 на поток).
- На поток: **2 строки × 4 токена = 8 аккумуляторов** (в 2 раза больше ILP).
- Веса — в LDS (8 КБ на блок, 64 строки × 128 Б), x — в LDS (8 КБ), двойная буферизация
  (32 КБ, влезает в 64 КБ).
- Активации квантуются **одним скейлом на 256** (как у llama.cpp) ⇒ эпилог: `sumi += dot*sc`
  (2 int-операции) вместо cvt+mul+fma, и раз на блок — `acc += dx*sumi - dm*sumn`.
- Внутренний цикл: на группу 64 dp4a (2 строки × 4 токена × 8), 2 загрузки весов
  (`uint4`), 8 загрузок x (`char16`), 16 int-операций эпилога ⇒ доля dp4a ≈ 71%,
  расчётный потолок ≈2.3–2.5 T MAC/s (75–82%). Дальше — вынос скейлов в отдельный проход
  и `v_dot4` через `__builtin_amdgcn_sdot4`, чтобы добрать до 86%+.
- Проверка: `gemm-cmp` (kernel vs CPU), затем `gpu-prefill 512/2048/8192` парами,
  при 2.5 T MAC/s ожидаем **~1100–1300 tok/s на 512** (llama.cpp 1393) и **×3.3** на GEMM.

**Attention** — отдельная история: мы читаем K/V на каждый запрос
(`attention_split_b_h4_p4`: WG на (token, kv_head, split)), поэтому при 8192 это 7.9 с из 20.4
(40%). llama.cpp читает K/V один раз на `Br` запросов.

## 4. План (по убыванию отдачи)

**A. GEMM на f16 + тайл 64×64 (помогает всему prefill)**
- де-квант Q4_K/Q6_K → f16 при загрузке в LDS (как у них), `half2`-FMA, f32-аккумулятор;
- WG 64 (2 warp), BM=64, BN=64, BK=16, на поток 4×2 = 8 аккумуляторов, SHMEM_STRIDE = BK/2+pad;
- ожидание: 1.33 → 0.65 мс на `ffn_up` при 64 токенах ⇒ prefill ×1.6–2.0 (≈1000–1200 при 512).

**B. Flash-attention с тайлом по запросам (главный резерв на 8192)**
- WG: 32–64 запроса × блок KV 64, K/V в LDS как f16×4, Q — в регистрах/`__local`,
  аккумуляторы в регистрах, online softmax, маска в `__local`;
- ожидание: attention 7.9 → 2.5 с ⇒ 8192: 20.4 → ~15 с (≈550 tok/s), затем и больше при
  переходе на f16-математику в самом attention.

**C. Decode (GEMV)**
- f16-дот по 8 строк на workgroup, широкие `half4`-загрузки, банковое выравнивание;
- ожидание: 64 → 85–95 tok/s.

**D. Мелочи**
- `half`-активации в KV (уже f16), `v_dot2_f32_f16` через `__builtin_amdgcn` (если драйвер
  даёт), отказ от лишних `barrier` (двойная буферизация LDS).

## 5. Как проверяем

Каждый шаг: `gemm-cmp` (kernel vs CPU-эталон), `gpu-cmp --batch 128` (граф), затем
`gpu-prefill --tokens 512/2048/8192` парами против текущего дефолта, и только после этого —
сравнение с `llama-bench` (Vulkan). При регрессе — откат.
