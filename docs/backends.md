# Модульные бэкенды

Цель — один движок и несколько взаимозаменяемых исполнителей (CPU, OpenCL),
с одинаковым поведением и общими проверками. Vulkan/ROCm исключены.

## Слои и зависимости

```
apps/*  (composition root: выбор бэкенда по CLI/env)
  └── application (порты, Generate, планировщик)
        └── domain (модель, сэмплинг, чат)
бэкенды реализуют lfm_app::InferenceBackend / TokenizerPort
  backend-cpu    pure Rust, AVX2 → NEON
  backend-opencl rusticl/PoCL (текущий)
общие крейты: domain, application, infra-gguf, infra-quant, infra-tokenizer
```

Правило: `application`/`domain` не знают про инфру; конкретный бэкенд подставляет
`main.rs` (`BackendLoader`), поэтому сервер и TUI зависят только от портов.

## Контракт

`InferenceBackend` (см. `crates/application/src/ports.rs`):
`create/free_sequence`, `prefill`, `prefill_begin/finish`, `step`, `logits`,
`logits_row`, `max_ctx`, `free_pages`, `cache_stats`.

`TokenizerPort`: `encode`, `decode`, `eos_id`.

Требования к каждому бэкенду:
- `Generate` даёт те же greedy-ids, что эталон, на фиксированных промптах;
- `step` поддерживает несколько последовательностей (mixed batch);
- `prefill_begin/finish` — крючки для префикс-кэша; бэкенд без кэша возвращает 0;
- `free_pages` используется admission-контролем планировщика.

## Выбор бэкенда

Конфигурация (TOML + CLI, см. `docs/config.md`):
- бэкенд один — OpenCL;
- `backend.devices` / `--devices` — индексы устройств;
- `backend.mode = single|pipeline|tp`, `tiers` — раскладка слоёв;
- Cargo-фич для выбора бэкенда нет: `infra-cpu` — эталонная CPU-реализация для
  сверки (`lfm-bench gpu-check`, `ref-gen`), серверный инференс идёт через
  `backend-opencl`; Vulkan/ROCm
  исключены.

## CPU и ARMv7

Вынесены в отдельные проекты (в этом репозитории остаётся только OpenCL):
CPU-бэкенд W4A8/AVX2 и ARMv7 (NEON + OpenCL 1.1 для Adreno 330).

## Vulkan/ROCm

Исключены решением от 18.11.2026: остаются CPU и OpenCL, цель — обогнать
llama.cpp по prefill и decode.

## Устройства без `cl_khr_fp16` (Intel iGPU)

Бэкенд работает и на устройстве без fp16 (проверено на Intel UHD 630 через
Rusticl). Отличия включаются автоматически по `caps.fp16`, отдельных флагов нет:

- KV-кэш хранится во `float` (`KV_T`/`-DLFM_F32_KV`), заголовки блоков
  (`d`/`dmin`) читаются из байтов и конвертируются вручную (`lfm_h2f`).
  Тип `kv=f16` в конфиге остаётся, меняется только представление в памяти;
  `kv=q4` на таком устройстве отвергается при загрузке, `kvarn` работает
  (staging и скейлы — тоже float).
- Ядра, рассчитанные на подгруппу 64 (`attention_b_h2`, `attention_b_fa`,
  `attention_split_b_fa*`, attn4/flash), не включаются: у Intel подгруппа 16,
  а `reqd_sub_group_size` Rusticl игнорирует. Остаётся `attention_b_h` /
  `attention_split_b_h`.
- Q6-decode идёт через int8-ядра по `prepacked_i8`: `gemv_q6_k_i8` написан под
  подгруппу ≥ 32 и на 16 полосах считает неверно. Признак — `sub_group_size < 32`
  (а не отсутствие fp16: Intel Xe с fp16 и подгруппой 16 тоже требует обхода).
  Q4-decode (`gemv_q4_k_i8*`) корректен при любой подгруппе.
- Батчевый decode/prefill на 2–16 токенов идёт через 64-поточный `b8p`
  (nibble для Q4, int8 для Q6) чанками по 8 токенов (`tok0` в ядре):
  512-поточные `gemm_i8_gz`/`pf` на 16 полосах дают по 16 КБ private/поток
  и работают в разы медленнее. iGPU multi-8: 4.0 → **10.6 tok/s** (multi-16
  10.7, single decode 6.2, prefill 11.2 без изменений). Профиль: `q4_b`,
  `q4p_b`, `q4x4p_b` — 64 КБ private/поток, `q6_b` — 32 КБ,
  `gemm_q6`/`b8p`/`i8_*` — 16 КБ.

Intel Gen9 не виден в OpenCL по умолчанию: нужен Rusticl с `RUSTICL_ENABLE=iris`
(intel-compute-runtime и PoCL/Level Zero устройство не отдают).

## kvarn

`kv=kvarn` держит в staging только неполную страницу: по кольцу из 128 позиций
(`KV_STAGE`) на каждую последовательность, а не весь контекст. Закоммиченные
страницы читаются из кодов (4 бита на K, 2 бита на V) в `attention_*_qk` и в
batch-ядрах `attention_b_h_rot`/`attention_split_b_h_rot`; из staging читается
только хвост `pos >= full_end`. Батч не должен превышать 128 токенов на
последовательность (это ограничение `prefill_ntok`), иначе загрузка вернёт
ошибку.

Варианты `kvarn`: `kvarn` (=`kvarn_k4v2`, по умолчанию: K 4 бита, V 2 бита) и
`kvarn_k4v4` (V 4 бита — 16 уровней с нулевой точкой). `k4v4` — опция, не
замена: точность 0.998151 на 1024/64 и 0.998632 на 2048/128 против 0.991101 и
0.995183 у k4v2 (f16: 0.999375/0.998781), цена — +25 МБ на ctx 8192 и −2…−4%
prefill.

Весовая память: int8-копии Q4_K для не-FFN тензоров (внимание, shortconv)
занимают ≈370 МБ и нужны только ради prefill. `--q4i8-ffn-only` оставляет
int8 у FFN, а внимание считает по 148-байтной раскладке: prefill −6%,
`gpu-cmp 1024/64` cos 0.999479.

Любой `ctx`, кратный 32, поддерживается и для `kvarn`, и для `q4`: сетка
зануления KV/conv округляется до размера рабочей группы (раньше ctx вроде
32000 давал `CL_INVALID_WORK_GROUP_SIZE`).

Пул KV по умолчанию равен `ctx` (токены на все последовательности сразу);
`--kv-pool N` увеличивает пул в N раз (память растёт линейно). На 16 клиентах
с разными промптами по 60 слов и `ctx 2048` пул ×1 обслуживает 7 из 16
запросов (остальные получают KV-ошибку), ×4 — все 16.

Память KV (24 слоя, ctx 8192, 4 KV-головы, 8 seq): `f16` — ≈185 МБ,
`kvarn` — ≈63 МБ при `prefill_ntok=128` (staging 22, коды 33, скейлы 8).
Staging — кольцо на `prefill_ntok` позиций, поэтому память зависит от размера
чанка: 64 → ≈52 МБ, 32 → ≈47 МБ (prefill при этом −7…−11%), decode не меняется.
На ctx 2048 — ≈46 и ≈16 МБ. Цена — скорость
prefill: коды декодируются в batch-внимании; после переноса flash-структуры
(`attention_split_b_fa_qk`, 4 головы × 16 полос, вращение в регистрах) на AMD
это −10% на 512 и −31% на 8192; decode на длинном контексте −5%. Остаток
разрыва — стоимость декодирования кодов K/V (1 загрузка + 3 ALU на канал
против одной векторной загрузки f16). `kvarn` не поддерживается вместе с tensor parallel.

## Несколько устройств: TP и pipeline

Два режима, оба через переменные окружения сервера:

| | `lfm serve --mode tp --devices 0/1` (tensor parallel) | `lfm serve --mode pipeline --tiers 50/50` (pipeline) |
|---|---|---|
| что делится | головы внимания и FFN (каждый слой на всех устройствах) | слои модели (каждое устройство считает свой диапазон) |
| ограничение | число устройств ≤ KV-голов (4); KV-головы делятся неравномерно: 4 → 2/1/1, тогда query-головы 8/4/4; миры 1–4 | число слоёв делится по процентам: 24 слоя → 2, 3, 4 и т.д. стадии |
| prefill / decode | prefill — чанками (подряд идущие токены одного слота), decode — батчем до `batch_cap` строк разных слотов; `LFM_TP_BATCH_DEC=0` возвращает построчный decode | батчевый, как на одном устройстве |
| устройства | желательно одинаковые по скорости | любые, включая CPU |

Индексы устройств — плоский список по платформам; что видно, зависит от
`RUSTICL_ENABLE`:

| окружение | 0 | 1 | 2 |
|---|---|---|---|
| без переменных | RX 6400 | CPU (PoCL) | — |
| `RUSTICL_ENABLE=iris` | Intel UHD 630 | CPU | — |
| `RUSTICL_ENABLE=iris,radeonsi` | RX 6400 | Intel UHD 630 | CPU |

CPU через PoCL работает (`cl_khr_integer_dot_product` и `cl_khr_fp16` есть):
`LFM_DEVICE=1 lfm-bench gpu-check` → cos 0.998653, prefill 32 токена —
12.2 tok/s, decode — 3.7 tok/s (i5-10400).

Замеры на этой машине (промпт ~200 токенов, 24 токена генерации, greedy):

| режим | было (по токену) | стало (чанками) |
|---|---|---|
| TP RX 6400 + CPU | 110.8 с | **~20–22 с** |
| TP RX 6400 + Intel | 104.8 с | **19.9 с** |
| TP RX 6400 + Intel + CPU | — | 26.0 с (kv 2/1/1, головы 8/4/4) |
| TP Intel + CPU (короткий запрос) | 8.3 с | 5.1 с |
| pipeline RX 6400 + CPU, 50/50 | 21.0 с (чанк 128) | — |
| pipeline RX 6400 + CPU, 60/40 | **17–18 с** | — |
| pipeline RX 6400 + Intel + CPU | 28.0 с (400 токенов) | — |

Выход batch- и пошагового путей совпадает с одиночными устройствами
(проверял на двух промптах; расхождений нет). Механика: `TpModel::step`
группирует подряд идущие prompt-токены одного слота и считает их одним
чанком через batch-ядра (`tp_*_b`), а всередукция по-прежнему на хосте.
`LFM_TP_SERIAL=1` возвращает пошаговый путь (для A/B), `LFM_TP_DEBUG=1`
печатает разбивку чанка по фазам, `LFM_TP_SYNC_NORMS=1` возвращает
синхронизацию x/hq/hs после каждой нормы (по умолчанию каждая стадия считает
их сама: веса норм реплицированы, вход одинаков).

Для разнородных устройств шардинг теперь взвешенный: `LFM_TP_WEIGHTS=75/25`
даёт GPU 3/4 KV-голов (12/4 query), 75% FFN и 75% словаря. На GPU+CPU при
двух устройствах такие веса включаются автоматически, если `LFM_TP_WEIGHTS`
не задан. На 4 клиентах (48 токенов): 7.3 tok/s поровну против **17.6 tok/s**
при 75/25 (шаг 519 → 206 мс).

### TUI-чат на нескольких устройствах

`lfm chat` и `lfm serve` понимают `--mode pipeline|tp`, `--devices` и
`--tiers`. Для GPU + iGPU с `kvarn` и ctx 65536:

```bash
RUSTICL_ENABLE=iris,radeonsi ./target/release/lfm chat \
  --devices 0,1 --mode pipeline --tiers 96/4 --kv kvarn --ctx 65536
```

Индексы устройств при `RUSTICL_ENABLE=iris,radeonsi`: 0 — RX 6400, 1 — UHD 630,
2 — CPU. Доли `tiers` — проценты слоёв; вторая стадия на iGPU в 30–80 раз
медленнее на слой, поэтому имеет смысл отдавать ей 1–2 слоя. Замеры для
ctx 65536 / kvarn / 48 токенов (RX 6400 + UHD 630):

| tiers | слои AMD/iGPU | decode |
|---|---|---|
| один AMD | 24 / 0 | **11.3 tok/s** (при `LFM_CACHE=0`) |
| 96/4 | 23 / 1 | 5.3 tok/s |
| 90/10 | 22 / 2 | 4.7 tok/s |
| 80/20 | 19 / 5 | 3.5 tok/s |
| 60/40 | 14 / 10 | 2.1 tok/s |

Один RX 6400 с `kvarn` и ctx 65536 помещается (≈3.6 ГБ с `LFM_CACHE=0`) и
быстрее; iGPU-стадия нужна, если не хватает VRAM (60/40 — ≈2.3 ГБ на AMD) или
нужен запас. Если не влезает — `LFM_CACHE=0` (без снапшотов conv, история не
кэшируется между ходами) или больше слоёв на iGPU. TP с `kvarn` несовместим.

Prefill в pipeline идёт **конвейером по чанкам**: стадии работают в отдельных
потоках и перекрываются (stage 0 считает чанк k+1, пока stage 1 считает k),
передача hidden — через канал с backpressure (2 чанка). Диагностика —
`LFM_PIPE_DEBUG=1` (печатает время каждого чанка по стадиям). Одиночный
длинный запрос теперь идёт через `prefill()` целиком (атомарный prefill), а не
через 64-токенные шаги; это включает конвейер и убирает накладные расходы шагов.

Замеры на промпте 414 токенов: один RX 6400 — **0.6 с** (и старым чанковым
путём тоже 0.6 с), `LFM_TIERS=96/4` (23 слоя GPU, 1 слой CPU) — 2.2 с,
`92/8` — 4.0 с, `60/40` — ~17 с. CPU-стадия в 30–80 раз медленнее GPU на слой,
поэтому добавлять её к GPU имеет смысл только на 1–2 слоя и только если нужен
параллелизм с другим устройством; на этой машине быстрее всего один GPU.

Decode в TP теперь батчевый: строки разных слотов одного шага склеиваются
в один проход по слоям (`tp_prepare_rows` + `tp_lmhead_rows`), по одному
проходу на `batch_cap` строк. Замер на 4 клиентах (GPU+CPU, 48 токенов):
9–11 tok/s агрегата против 4.3 при `LFM_TP_BATCH_DEC=0` (**2.1–2.6×**).
ids и `logits cos` на `gpu-tp` не изменились (equal: true, 0.999692).

TP поддерживает и три устройства: KV-головы (4) делятся как 2/1/1, поэтому
query-головы получаются 8/4/4; FFN — 2560 на стадию, словарь — 42667/42667/42666.
Ограничение остаётся: allreduce после внимания и FFN каждого слоя, поэтому
самая медленная стадия тормозит все; на разнородных устройствах pipeline
(`LFM_TIERS`) обычно быстрее. TP с kvarn/q4 несовместим (квантизованный KV
отклоняется при шардах).

## Проверки и производительность

Единый набор для любого бэкенда:
- `*-gen --tokens N` — greedy-ids/текст;
- `*-cmp --len N --batch B` — батч == последовательный (cos/top-5);
- `*-multi --seqs N` — mixed batch;
- `Generate` через порты (`gpu-port`);
- сервер: `/v1/chat/completions`, `tools/loadtest.py`, `/metrics`.

Перф-метрики: decode/prefill tok/s на ctx 512/2048/8192, агрегат 4–6 стримов,
заполнение VRAM, время загрузки и сборки ядер.

Регрессионный прогон корректности — `tools/bench_check.sh` (`just bench-check`,
`bench-check-igpu`, `bench-check-server`). Пороги cos зафиксированы по замерам и
проверяются именно split-пути (`gpu-cmp` при len > 512), где ошибки нормировки
kvarn не видны на коротких контекстах:

| проверка | порог | AMD | Intel |
|---|---|---|---|
| `gpu-check` f16 | 0.9975 | 0.998532 | 0.998242 |
| `gpu-check` kvarn | 0.9965 | 0.998435 | 0.998372 |
| `gpu-cmp` f16 1024/64 | 0.9980 | 0.999375 | — |
| `gpu-cmp` kvarn 1024/64 | 0.9880 | 0.990922 | — |
| `gpu-cmp` f16 2048/128 | 0.9970 | 0.998781 | — |
| `gpu-cmp` kvarn 2048/128 | 0.9920 | 0.995045 | — |
| `gpu-gen` (f16/kvarn) | текст «Paris…» | ok | ok |

Для iGPU split-пути проверяются отдельным медленным профилем
`bench-check-igpu-full` (единичный проход 1024 токенов занимает минуты).
