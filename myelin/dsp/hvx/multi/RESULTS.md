# Мульти-PD: измерения на устройстве

Дата: 2026-11-23. Устройство XQ-BC72 (SD888, v68), unsigned PD, adb по Wi-Fi.
Стенд: `myelin/dsp/hvx/multi` (`multi_test`), ядро — боевой `liblfmgemv_skel.so`.

## 1. Главное: несколько handle — это ОДНА PD

```
OPEN_PLAIN k=0..3 rc=0 (4 handles)
OPEN_PLAIN_TOTAL ok=4 of 4 (all in session 0 = one PD)
```

`remote_handle_open` на один и тот же skel в одном процессе всегда даёт
session 0, то есть одну и ту же PD. Чтобы получить несколько PD, нужны
**разные процессы** (или разные домены, но в нашем окружении их нет:
`/dev/fastrpc-*` отсутствует, домены не выставлены).

## 2. Heap

| что | значение |
|---|---|
| максимум на одно выделение | **512 МиБ** |
| суммарно в PD | **1592 МиБ** (600 МиБ одним куском уже `rc=-2147482622`) |

Вывод: 4 среза по ~217 МБ (866/4) влезают с запасом.

## 3. Полоса: один PD против четырёх процессов

Один процесс, полная матрица `7680×2048` int4, N=1:

```
kernel_us=359  gbs=21.91  tok_s_880MB=24.9
```

Четыре независимых процесса, каждый со своим срезом (1920 строк, 1.97 МБ):

```
8.70  6.72  8.04  5.37  GB/s (печатается относительно полной матрицы — величина завышена)
```

Реально: 1.97 МБ / 0.9–1.4 мс = **1.4–2.2 ГБ/с на процесс**, суммарно
**~6.6 ГБ/с** — то есть втрое хуже одного PD.

Четыре процесса, каждый с полной матрицей (одни и те же данные, L2 делится):

```
kernel_us=857  gbs=9.18
kernel_us=1179 gbs=6.67
kernel_us=1633 gbs=4.82
kernel_us=1671 gbs=4.71
```

Суммарно 31.4 МБ за ~1.67 мс = **18.8 ГБ/с** — меньше, чем 21.9 у одного PD.

## 4. Вывод

1. **Мульти-PD в текущем виде не даёт полосы.** Причина не в limitе PD, а в
   накладных на процесс: короткий срез (1.97 МБ) не успевает выйти на полосу,
   доминирует открытие/загрузка/паковка/синхронизация.
2. Заявленные ранее `12.2 / 22.3 / 33.3 ГБ/с` получены другим бенчмарком
   (крупные последовательные чтения, не наш доступ) и к нашему ядру
   не переносятся.
3. Один PD на нашем ядре даёт **21.9 ГБ/с**, что уже близко к практическому
   потолку шины для этого паттерна.
4. Следствие для плана: **25 tok/s через 4 PD не подтверждаются**. Чтобы
   мульти-PD заработал, нужен другой режим — персистентные воркеры с
   длинными батч-командами (чтобы накладные амортизировались), а не
   «открыл-посчитал-закрыл» на каждый срез.

## 5. Что мерить дальше (когда телефон вернётся)

1. Персистентный воркер: открыть PD один раз, загрузить срез один раз,
   дальше гонять 100–1000 итераций GEMV без переоткрытия. Это отделит
   накладные от полосы.
2. То же для 2/4 процессов одновременно — с длинной серией, а не 3 раундами.
3. Проверить, помогает ли разнесение данных по разным адресам (без L2-дублей).
