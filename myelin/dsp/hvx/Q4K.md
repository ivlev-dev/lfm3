# Q4_K на HVX: порт 1:1 из OpenCL-эталона

Статус: **сделано** — ядро, пак, численная сверка, host-стенд генерации,
ответ на вопрос про вырождение. Тайминги на железе — отложены (телефон
офлайн, счёт за QEMU).

## 0. Ответ коротко

1. **Вырождение текста на Q4_K-пути НЕ воспроизводится.** Q4_K (нативный
   формат GGUF, без переквантования) + те же int8/32 активации, что у
   эталона, даёт связный текст и совпадает с f32/CPU-эталоном по id
   **49/64 токенов**, дальше — равнозначная ветка («The capital of Germany
   is Berlin» вместо «…of the United States is Washington»).
2. **Причина вырождения — формат весов, а не пайплайн.** На одной и той же
   матрице `blk.0.ffn_gate.weight` и одних и тех же реальных активациях
   слоя 0: Q4_K → cos 0.999991, int8/32 → 0.999984, **int4/32 без min-терма
   → cos 0.808** (maxerr 2.11 при |y|max 3.2), int4 per-row → 16 % ошибки
   весов. 9.8 % ошибки весов int4/32 превращаются не в 9.8 % ошибки выхода,
   а в 60 %: min-терм `−dmin·m` держит **среднее значение группы**, без него
   ошибка складывается по `Σ_g μ_g·sum_g` и не усредняется.
3. **Что именно отвечает за качество в Q4_K** (по убыванию вклада):
   min-терм (asymmetric, per-32) ≫ per-32 масштаб ≫ f32-комбинация.
   Числа — в §6.

## 2. Раскладка: 144 B GGUF → 152 B HVX

```
GGUF Q4_K, 144 B / 256 весов          HVX pack: 24 B header + 128 B plane
 0  f16 d                                0   f32 d      (точное расширение f16)
 2  f16 dmin                             4   f32 dmin
 4  12 B sc/m (6 бит x 8 + 8)            8   u8 sc[8]   (распаковано)
16  128 B qs                            16   u8 m[8]
                                        24   128 B plane P (ниже)
                                       = 152 B = 4.75 бит/вес
```

Два изменения относительно эталонного препака (148 B), оба **без потерь**:

1. **`d`/`dmin` как f32** (+4 B/блок): fp16→f32 — точное расширение, зато в
   ядре нет конверсии half→float на каждый блок. 4.75 бит/вес против 4.625.
2. **Перестановка нибблов внутри блока** (32-байтовыми кусками):
   GGUF перемежает половины 64-весовой четверти, а HVX-вектору нужны 128
   подряд идущих активаций. В plane-байте `i` лежит вес `i` (младший ниббл)
   и вес `128+i` (старший):

```
P[ 0..31] = lo(qs[ 0..31]) | lo(qs[64..95])<<4     -> K[  0.. 31] / K[128..159]
P[32..63] = hi(qs[ 0..31]) | hi(qs[64..95])<<4     -> K[ 32.. 63] / K[160..191]
P[64..95] = lo(qs[32..63]) | lo(qs[96..127])<<4    -> K[ 64.. 95] / K[192..223]
P[96..127]= hi(qs[32..63]) | hi(qs[96..127])<<4    -> K[ 96..127] / K[224..255]
```

Проверено бит-в-бит на реальных блоках модели: `max|diff| = 0` против
`infra-quant::dequant_q4_k` (и на DSP, и на хосте). Смысл: `dot(q, xq)` для
групп 0..3 идёт по младшим нибблам с непрерывным окном `xq[0..127]`, для
групп 4..7 — по старшим с `xq[128..255]`.

Header и plane разделены (plane начинается с `align128(N·blocks·24)`), потому
что у HVX нет невыровненной векторной загрузки, а эталонный препак кладёт
`qs` со смещением 20.

## 3. Ядро

```
y[n] = Σ_b Σ_g xs[b*8+g] · ( d_b·sc[b*8+g]·dot32_g − dmin_b·m[b*8+g]·sum32_g )
```

* `dot32_g` — точный int32 по 32 весам; `sum32_g` — точная int32-сумма
  активаций группы (от строки не зависит, считается один раз на токен:
  `q4k_plan`).
* На блок (256 весов) на строку: 2 × `vrmpyacc` (128 B нибблов × 128 int8
  активаций каждая), 2 × (3 `vror` + 3 `vadd`) — сведение 8 int32-лейнов
  группы в лейн 0/8/16/24, затем 8 f32-операций `xs·(ds·dot − dm·sum)`.
* **int32 внутри группы, f32 только на комбинации.** Округлений в
  промежуточных шагах нет: `dot32` ≤ 32·15·127 = 60 960, влезает в int32 с
  запасом; `d·sc` и `dmin·m` — f32, как в эталоне.
* Порядок редукции **совпадает с эталоном по структуре**: `kernels/decode.cl`
  складывает `acc += xs·(dl·(d·sl) − sum·(dmin·ml))` по (блок, подгруппа), и
  HVX-ядро делает ровно то же в том же порядке — по этой причине
  HVX-результат **бит-в-бит равен скалярному двойнику** (`0/512` расхождений).
* Отличие от эталона одно: OpenCL-ядро разносит 4 строки по лейнам одной
  подгруппы и делает `sub_group_reduce_add` в конце (f32-дерево по 32 лейнам),
  HVX-ядро суммирует по блокам в один f32-аккумулятор на строку. Разница —
  только порядок f32-сложений, эффект 7·10⁻⁷ (см. §4).

## 4. Численная сверка

DSP-стенд (QEMU V68N_1024, `./q4k_build.sh`), реальные данные из модели:
512 строк `blk.0.ffn_gate.weight`, K=2048, реальная активация FFN слоя 0
для токена 597 («The»):

```
Q4K packer vs GGUF dequant             max|diff|=0.000e+00  OK
Q4K act_q8 vs host                     mismatches=0/2048 max|dscale|=0.000e+00  OK
Q4K HVX vs scalar twin                 mismatches=0/512 max|diff|=0.000e+00  OK
Q4K HVX vs f32w+q8act (weight fmt)     cos=1.000000000 maxerr=7.153e-07 rel=4.04e-07  OK
Q4K HVX vs f32 oracle (weights+act)    cos=0.999990191 maxerr=4.029e-03 rel=2.28e-03  OK
Q4K scalar twin vs f32 oracle          cos=0.999990191 maxerr=4.029e-03 rel=2.28e-03  OK
```

`f32 oracle` — де-квант всех весов в f32 × f32-активация (задание, п. 3).
**Цель cos ≥ 0.9999 достигнута: 0.9999902** (у эталона для нибблов
0.999906 — у нас выше, потому что сравнение с честным f32-оракулом той же
матрицы, а не с полным пайплайном).

Полная матрица 7680×2048 на хосте (`--selftest`, те же активации):
`cos=0.999990640, maxerr=5.3e-3`; вклад только формата весов (Q4_K против
f32-весов при тех же q8-активациях) — `maxerr=7.15e-07`, т.е. **весь
остаток — квантование активаций, а не Q4_K**.

## 6. Что именно в Q4_K отвечает за качество

Ошибка весов (относительный RMS по 512 строкам `blk.0.ffn_gate.weight`,
отсчёт от де-квантованных GGUF-весов — то есть от того, с чем модель
обучена работать):

| формат | бит/вес | rel-RMS весов | cos(y) vs f32-оракул | maxerr |
|---|---|---|---|---|
| Q4_K (GGUF, как есть) | 4.75 | 0 (эталон) | 0.999991 | 5.3e-3 |
| int8/32 sym | 8.0 + 1.0 | 0.54 % | 0.999984 | 7.3e-3 |
| int4/32 + per-group min | 4.0 + 1.0 | 4.31 % | **0.99956** | 4.0e-2 |
| int4/32 sym | 4.0 + 1.0 | 9.84 % | **0.808** | 2.11 |
| int4/32 sym + Hadamard H32 | 4.0 + 1.0 | 9.68 % | — | — |
| int4 per-row sym | 4.0 + 0.004 | 16.09 % | — | — |

Три вывода:

1. **min-терм — главное.** Разница «int4/32 sym» → «int4/32 + min» — это
   только `−dmin·m`: ошибка весов 9.84 % → 4.31 %, cos 0.808 → 0.99956.
   Причина нелинейная: симметричное квантование обнуляет среднее группы
   (μ_g), а вклад `Σ_g μ_g·Σ_{i∈g} x_i` складывается по группам с одним
   знаком (групповые суммы активаций не нулевые), поэтому ошибка не
   усредняется по K. Q4_K хранит `dmin·m` (6 бит на 32 веса) и вычитает её
   в ядре — это и есть «asymmetric» часть формата.
2. **per-32 масштаб** (6-битный `sc` в Q4_K) даёт меньше: int4 per-row
   16.09 % → int4/32 9.84 %.
3. **f32-комбинация** нужна, потому что `d`/`dmin` — плавающие (fp16 в GGUF)
   и их произведение на 6-битные целые не влезает в точный int; но сама по
   себе она ничего не «спасает» — спасает структура (min + per-32 sc).

Hadamard-поворот (`lfm_rot_blocks_f32`, как в HMX-пути) на этой матрице
почти не помогает (9.84 % → 9.68 %): веса уже квантованы Q4_K, выбросов,
которые поворот «размазывает», почти нет. Для сырых f16-весов эффект был бы
другим.

## 7. План перехода к w4a8/int4

Цель: 4 бита на вес в int4-пути без потери качества. Из §6 порядок мер:

1. **Ввести per-32 min (offset) в int4-путь.** Это то, что даёт 0.808 →
   0.99956 и совместимо с текущим HVX-ядром: `dot(u,x) − 8·sum(x)` уже
   считается, надо заменить `8` (фиксированный offset) на per-32 `m` и
   добавить член `−dmin·m·sum` — ровно как в `q4k_impl.c`.
2. **Перейти с per-row масштаба на per-32.** 16.1 % → 9.8 % ошибки весов;
   в HVX это `d·sc` на группу вместо одного Q16-множителя на строку (сейчас
   `set_scale`/`qp` в `lfmgemv_impl.c`). Побочно уходит проблема «выброс в
   строке убивает все 2048 весов».
3. **Масштабы хранить в fp16-парах `(d, dmin)` на 256 весов + 6-битные
   `(sc, m)` на 32**, а не в f32 на строку: это ровно Q4_K, 4.75 бит/вес, и
   уже реализовано — то есть **простейший путь к «int4, но качественно» это
   и есть Q4_K**, а не изобретение нового формата.
4. **Активации оставить int8/32** (q8): вклад квантования активаций —
   0.99999 cos, на текст не влияет.
5. Если нужен именно 4.0 бит/вес (без 6-битных sc/m): f32-масштаб на группу
   + int4 min/max (вариант `i4m`, 0.99956) — это +1 бит/вес на масштабы,
   дешевле по качеству, чем sym-int4.

## 8. Что проверено, а что нет

Проверено:
* пак и де-квант — бит-в-бит;
* HVX-ядро — бит-в-бит со скалярным двойником и cos 0.99999 против f32;
* текст на Q4_K-пути — связный, 49/64 id совпадают с f32/CPU;
* причина вырождения локализована по формату весов (§6).

НЕ проверено (и почему):
* **Полный HVX-пайплайн.** Стенд подменяет только матвеки; attention,
  shortconv, RMS, SiLU, rope — f32. Значит утверждение «Q4_K-путь даёт
  связный текст» верно для связки *Q4_K + q8-активации + остальное f32*.
  Реальный HVX-пайплайн дополнительно квантует attention (K — int4, **V —
  int2** с одним масштабом на голову) и shortconv — этим стендом не покрыто.
* По §6 видно, что 9.8 % ошибки весов уже дают cos 0.808 на FFN-матрице.
  int2-V (4 уровня, ~20 % ошибки на элемент) — самый вероятный оставшийся
  источник вырождения, и его надо проверять отдельно: это следующий
  эксперимент, а не следствие этого.
* Тайминги на железе: телефон офлайн (`adb devices` пуст), прогон только
  под QEMU. Числа вида «98.4 M pcycles на 512×2048» в QEMU бессмысленны;
  по числу операций (14 векторных + ~50 скалярных на блок-строку) Q4_K-ядро
  заметно дороже текущего int4-ядра — это цена «правильного» формата,
  оптимизация (вынос x-загрузок, lane-per-group раскладка, 2 строки за
  итерацию) оставлена на следующий шаг и в стенде не измерялась.

## 9. Как воспроизвести

```sh
cd myelin/dsp/hvx

# 1. численная сверка на хосте (Q4_K vs f32-оракул, форматы весов)
build/q4k_host --selftest              # или ./q4k_build.sh (соберёт и прогонит)

# 2. HVX-ядро под QEMU: пак, квантователь, HVX vs скаляр, cos/maxerr
./q4k_build.sh

# 3. текст (64 токена, префикс "The capital of France is")
build/q4k_host --mode f32 --tokens 64     # эталон
build/q4k_host --mode q4k --tokens 64     # Q4_K
python3 q4k_detok.py --ids-file build/gen_q4k.log

# эталон CPU (Rust, f32):
../../../target/release/lfm-bench ref-gen --tokens 64
```
