# REPORT21: int4 (`weight.n`) K>32 закрыт — виновата упаковка, не железо

Дата: 2026-11-22. Стенд `/home/ivlev_dev/Проекты/PC/lfm3/myelin/dsp/hmx`,
устройство XQ-BC72 (SD888, Hexagon v68, unsigned PD), adb по Wi-Fi.
Тулчейн: Hexagon SDK 6.7, hexagon-clang 21.0.04.

## 0. Итог

| | было | стало |
|---|---|---|
| int4 K=32 | 32 (MATCH) | 32 (MATCH) |
| int4 K=64…160 | только `32·ceil(ncr/2)` | **точное K**, `err=0` |
| int4 K=256…2048 | sat на половине | **sat 255**, `err=0` |
| вклад кроутона `cc` | только чётные | **все 64 из 64** при K=2048 |
| случайные веса (`amax=7/-2/-3`) | — | `bad=0/1024`, `cos=1.0` |
| int8 K=2048 | MATCH | MATCH |
| fp16 `href` | — | без изменений |

**Причина «половины» — ошибка в `i4_pack_wgt` (wl=4), а не режим железа.**
Для int4 формула `128*(k>>3)` уже даёт 512 Б на 32 K, а сверху добавлялся
`wstride*(k>>5)` (=512 Б). В результате логический кроутон `c` ложился по
адресу `1024*c`, а цикл читал его по `512*c`: нечётные инструкции читали
**дыру из нулей**. Отсюда ровно `32·ceil(ncr/2)` и «вклад только первых
`ceil(ncr/2)` кроутонов».

Рецепт (см. §4) — обычный цикл по кроутонам, но с **непрерывной** упаковкой
512 Б/32 K. Никаких новых control words не нужно: `art=0x3FF`, `wc=511`,
`bs=0x6000`, шаг активации 2048 Б, шаг веса 512 Б.

## 1. Постановка

REPORT20: `weight.n` 32×32 заведён побитово, но при K>32 в аккумулятор
попадали только первые `ceil(ncr/2)` кроутонов. Надо было либо найти рабочий
рецепт для K=2048, либо доказать недоступность. Дополнительно из реверса QNN
(`libQnnHtpV68QemuDriver.so`, символы `native_hmx_a16w4`,
`LayoutTensor<Ldefs::Crouton_16/32/16_DeepAR4/…>`, `set_hmx_params_convw4b1x1`)
пришли гипотезы про `art=0x198/0x19A`, `wc=2047`, 16-K кроутоны и fp16-
активации.

## 2. Диагностика: где именно теряется половина

Добавлены пробы (см. §7): карта вклада по k со стороны активации (`i4k`) и
веса (`i4w`), парная матрица (`i4pm`), явные `astep/wstep/aoff/woff`, режимы.

### 2.1. Карта вкладов при старом (багованном) раскладе

```
./deploy.sh i4k 32 128 4 0x6000 0 1
################################................................################################................................
  crouton hits (of 32): 32 0 32 0
```

По оси **активации** работают только чётные 32-K кроутоны (0, 2, 4…), а по
оси **веса** — первые `ceil(ncr/2)` логических кроутонов (`i4w`: 0,1,2 при
K=192). Это и есть подпись «чтение попало в дыру».

### 2.2. Одиночная инструкция — ровно 32 K

```
./deploy.sh i4 32 32 128 4 0x6000 -1 4096 1   # mode bit12 = одна инструкция
  head:  32 32 …                                # maxerr=96 → сложилось 32 из 128
```

`i4pm` (A one-hot `ka`, B one-hot `kb`, одна инструкция) даёт чистую
диагональ `ka==kb` для `ka=0..31` и **ноль** для `ka=32..63`. То есть одна
инструкция `activation.ub + weight.n` — это строго 32 K × 32 N, 512 Б весов,
2048 Б активации. Никакого «64 K за инструкцию» нет.

### 2.3. Сдвиг указателя веса

K=64, все единицы, две инструкции, явный `wstep`:

| wstep, Б | 0 | 64 | 128 | 256 | 384 | 448 | 512 | 576 | 1024 | 2048 |
|---|---|---|---|---|---|---|---|---|---|---|
| сумма | 64 | 64 | 56 | 48 | 40 | 40 | **32** | 32 | **64** | 32 |

Линейная часть (`0…448`) — это пересечение окна веса `[w, w+512)` с
активацией k=32…63. Ровно на `w=512` — ноль: это и есть дыра старой
упаковки. На `w=1024` снова 64, потому что там лежал следующий логический
кроутон (см. §3).

## 3. Корень: двойной шаг в `i4_pack_wgt`

Старая формула (wl=4):

```
bb = 128*(k>>3) + 4*n + (k&3);      // уже 512 Б на 32 K!
bb += wstride*(k>>5);               // +512 Б ещё раз
```

`128*(k>>3)` растёт на 512 Б каждые 32 K, поэтому добавка `512*(k>>5)` кладёт
логический кроутон `c` по адресу `1024*c`, оставляя 512-Б дыру. Цикл же читал
`vwgt + c*512`:

* `c=2m`   → `1024*m`     = логический кроутон `2m`   → вклад есть;
* `c=2m+1` → `1024*m+512` = дыра (нули)              → вклада нет.

Отсюда `32·ceil(ncr/2)` и «не строго по индексу»: проба `amax=-8-cc` кладёт
вес в `1024*cc`, его читает инструкция `2*cc`, а активация при этом берётся
из кроутона `2*cc` — при `A≡1` сумма всё равно 32, поэтому в REPORT20
казалось, что «кроутон 1 отвечает, а 2 нет».

Исправленная формула (кроутон `c` по `wstride*c`):

```
bb = wstride*(k>>5) + 128*((k&31)>>3) + 4*n + (k&3);
```

При `wstride=512` это ровно непрерывные 512-Б тайлы; при 1024/2048 —
тайлы с зазором (полезно только как проба).

## 4. Рецепт int4 K=2048

### 4.1. Раскладка веса (проверена для K=32…2048)

Один тайл = 32 K × 32 N = 512 Б, кроутон `c` лежит по `512*c`:

```
byte(k,n) = 512*(k>>5) + 128*((k&31)>>3) + 4*n + (k&3)     // 0..512*ncr
nibble    = старший, если ((k>>2)&1), иначе младший
value     = 4-бит two's complement (−8..7)
```

### 4.2. Активация

int8, раскладка `lay=3` (как у int8): 2048 Б на 32 K (32 K × 64 spatial;
при M=32 заполняется первая половина каждого 128-Б вектора).

### 4.3. Цикл и control words

```
for (c = 0; c < ncr; c++)                       // ncr = K/32
    activation.ub = mxmem(vact + c*2048, 0x3FF)
    weight.n      = mxmem(vwgt + c*512,  511)
bias = mxmem2(0x6000-слова);  mxmem(vout,0):after:sat.ub = acc
```

| поле | значение | смысл |
|---|---|---|
| `art` | `0x3FF` | dC = 0 → один 32-K чанк активации |
| `wc`  | `511`   | 512 Б int4-веса = 32 K × 32 N (1024 ниббла) |
| `bs`  | `0x6000`| масштаб 512.0 = identity для int8-конверта |
| шаг активации | 2048 Б | |
| шаг веса | 512 Б | |
| store | `sat.ub`, `srt=0` | |

CLI: `./deploy.sh i4 32 32 2048 4 0x6000 -1 0 <reps>` (mode=0 — чистый
режим; всё остальное в mode — только пробы).

### 5.2. Все 64 кроутона при K=2048

```
for cc in 0..63: ./deploy.sh i4 32 32 2048 4 0x6000 $((-8-cc)) 0 1
```

→ у всех `bad=0`, `head=32`. То есть **каждый** 32-K кроутон даёт свои 32

### 5.5. Скорость (32×32×K, режим 0)

| K | µs/rep | pcyc/rep |
|---|---|---|
| 32 | 0.05 | 53 |
| 128 | 0.10 | 113 |
| 512 | 0.35 | 379 |
| 2048 | **1.34–1.42** | ~1520 |

GEMV (N=1, K=2048): int4 **0.834 мкс**, int8 0.977 мкс (−15 %). Для N=32

(`:deep` оба, весь K одной инструкцией) тоже MATCH, но в установившемся
режиме той же скорости (~1.3–1.5 мкс).

## 6. Проверенные и отвергнутые гипотезы

| гипотеза | команда/режим | результат |
|---|---|---|
| H1 шаг активации 4096 | mode 1024 | то же `32·ceil(ncr/2)`; бит 11 адреса активации для `weight.n` игнорируется |
| H2 4096 + wstride 1024 | mode 1024+4 | без изменений |
| H3 `art` по кроутонам | mode 8192 | без изменений |
| H4 `acc:2x1` (srt=3) | mode 2048 | байты 0/32 через один, сумма та же → второго банка с K нет |
| H5 `wc` | 511/1023/2047/4095 | одна инструкция = 32 K при любом `wc` |
| H6 `weight.n:deep` + шаг 4096 + wc | mode 526336 | не MATCH |
| H16 16-K кроутоны | mode 2097152 | 32→16, 64→32, 128→64: снова половина (наш layout активации не 16-K) |
| H16b `:deep` | mode 1/32/262144/524288 | MATCH, но не быстрее; weight-deep «весь K одной инструкцией» (mode 64) даёт только 32 K |
| H16d `activation.hf` + `weight.n` | mode 1048576 | выход весь 0 (нужна другая связка весов/масштаба; `native_hmx_a16w4` этим путём не воспроизвёлся) |
| QNN `art=0x198/0x19A`, `wc=2047` | I4_ART/I4_WC + mode 4096 | одна инструкция даёт 8; `art=0x3FF` — 32; `(ncr−1)<<11|0x3FF` + `wc=512·ncr−1` — тоже 32 |

Вывод по QNN: поля `wgt_rt/act_rt` из `set_hmx_params_convw4b*` — это поля
структуры QNN для их собственного варианта инструкции/дескриптора; на нашу
пару `activation.ub + weight.n` они не переносятся. Резать QNN-бинарь дальше
не требуется: режим доступен и без него.

## 9. Что осталось

1. `native_hmx_a16w4` (fp16-активации + int4) нашим способом не завёлся;
   если понадобится, нужен реверс их дескриптора весов/масштаба (сейчас не
   нужно — ub-путь работает).
2. Для N=32 int4 не быстрее int8 (доминирует активация); выигрыш только на
   GEMV N=1/2.
3. `mode=1/32` (`:deep`) корректны, но замер при малых `reps` обманчив
   (работа уходит в очередь HMX и измеряется только при `hmx_sync`); мерить
   только `reps≥1000`.
