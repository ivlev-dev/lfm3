# REPORT18: HMX v68 заведён — fp16 (qhl_hmx) и int8 (рецепт реверса)

Дата: 2026-11-22. Стенд `/tmp/opencode/hmx4`, устройство XQ-BC72 (SD888, v68,
unsigned PD `fastrpc_shell_unsigned_3`). CDSP-клок измерен: **1132 pcycles/µs
(1.13 ГГц)** — команда `mx4_test clk`.

## 0. Итог

| что | результат |
|---|---|
| fp16 32xK x KxN | **работает**: cos=1.000000, err≤0.0075, K=32/64/128/256, N=32/64 |
| int8 32xK x KxN | **работает побитово**: err=0, cos=1.0, K=32…2048, N=32/64 |
| int8 32x2048x32 (FFN-тайл) | **1.075 мкс** на вызов (adeep), 1.95 TMAC/s полезных |
| int8 32x2048x64 | **1.612 мкс**, 2.60 TMAC/s |

Обе прошлые серии падали из-за **двух** вещей: неверной раскладки кроутона и
(для int8) **отсутствия bias/scale-блока** — без него saturating-store пишет
нули, потому что неявный множитель int8-конверта равен 1/512.

## 1. fp16: точные значения, которые заработали

Инструкции (ровно как в `$SDK/libs/qhl_hmx/.../qhblas_hmx_matrix_matrix_mpy_hf_sm.S`,
ветка `__HEXAGON_ARCH__ < 73`, т.е. без `cvt`):

```
{ activation.hf = mxmem(R0,R1):deep;   // :deep СТОИТ НА АКТИВАЦИИ
  weight.hf     = mxmem(R2,R3); }      // на весах :deep нет
{ mxmem(R4,R5):after.hf = acc; }       // store, R5 = 0
```

Контрольные слова (`ncr = K>>5` — число 2-КБ кроутонов = K/32 каналов):

```
act_rt = (ncr << 11) | 0x7C     // K=32 -> 0x0087C, K=256 -> 0x0407C
wgt_rt = (ncr << 11) - 1        // = nbytes-1: 0x7FF … 0x3FFF
store_rt = 0
```

Раскладки (элементные индексы fp16, байты = индекс*2; проверено `refdump`,
0 несовпадений на 1024/2048/4096/8192 элементах):

```
activation 32xK: elem(s,k) = 1024*(k>>5) + 64*(s>>1) + 2*(k&31) + (s&1)
weight Kx32:     elem(k,n) = 1024*(k>>5) + 64*((k&31)>>1) + 2*n + ((k&31)&1)
                 (столбцы n=32..63 — по смещению +4096 элементов = +8192 байт)
output 32x32:    16 HVX-векторов row-major, как отдаёт mpy_ahf
```

Формула из брифинга `(s>>1)*128 + (s&1)*64 + (c>>4)*32 + (c&15)*2` **неверна**
(32/1024 совпадений; в элементном виде она тождественна row-major). Старая
стендовая `(s>>1)*128 + c*4 + (s&1)*2` верна только для c<16 — отсюда «16
каналов» прошлых серий.

Последовательность (проверено, работает):

```
qurt_hvx_lock -> transfer_row -> transfer_column -> qurt_hvx_unlock
HAP_power_set(HAP_power_set_HMX, up=1)      // ОБЯЗАТЕЛЬНО до первой HMX-инстр.
compute_resource_hmx_lock(ctx)              // ОБЯЗАТЕЛЬНО
mxclracc.hf  ->  activation/weight pair  ->  store
compute_resource_hmx_unlock(ctx)
HAP_power_set(HMX, up=0)
```

Минимально необходимое (по одному варианту за раз):

| вариант | вердикт |
|---|---|
| `HAP_power_set(HMX)` | **обязателен**. Без него: точный exception в HMX-инструкции -> падение PD, дальше **CDSP SSR** (`ssr(cdsp)`, подсистема перезагружается, телефон целиком не ребутится). Проверено один раз, больше не повторяем |
| HMX lock (`compute_resource_hmx_lock` или `qurt_hmx_lock2`) | **обязателен**: без него precise exception в момент HMX-инструкции. `qurt_hmx_lock2(QURT_HMX_SHARED_LOCK)` работает так же |
| `mxclracc` перед парой | не обязателен: store `:after` сам очищает acc (reps=3 без clracc даёт 1x, не 3x) |
| `qurt_hvx_lock` вокруг упаковки | не обязателен в этом PD (`mode=8` без него корректен), оставлен |
| HVX lock на время HMX | не нужен (`mode=64` корректен) |
| bias-загрузка | fp16-путь её не использует (на v68 `bias` нужен только int8, см. §3) |

## 3. int8: рецепт (проверен, совпал с отчётом реверса)

```
mxclracc                                        ; целочисленный acc
for each chunk:  activation.ub = mxmem(act, art):deep   ; или просто пара
                 weight.b      = mxmem(wgt, wgt_rt)
bias = mxmem2(bias_ptr)                         ; 256 Б на 32 канала
mxmem(out, 0):after:sat.ub = acc                ; 2 КБ = 64 spatial x 32 N
```

Значения, которые заработали:

```
art    = 0x3FF   (ch_stop=31, маска 0)   ; 0x07C и 0x77C на 32 каналах тоже дают 32 MAC
wgt_rt = 1023    (1 КБ-1)                ; N=64 (weight.b:deep): 2047 (2 КБ)
store  = :after:sat.ub = acc, Rt = 0
bias   = scale = 0x6000 (fp16 512.0) в low-словах -> 1.0 (неявный множитель 1/512)
         uint32 word0[ch] = 0x6000, word1[ch] = 0; 32 слова (128 Б), затем 128 Б high
```

Раскладки (1 байт на элемент; проверено побитово — `err = 0`):

```
activation 64 spatial x 32 K (2 КБ): addr(s,k) = (s>>2)*128 + 4*k + (s&3)
   (наш кейс — 32 spatial: заполняем s=0..31, верхняя 1 КБ остаётся нулевой)
weight 32 K x 32 N (1 КБ):           addr(k,n) = (k>>2)*128 + 4*n + (k&3)
   N=64, weight.b:deep (2 КБ):       + 1024*(n>>5)
output 64 spatial x 32 N (2 КБ):     addr(s,n) = (s>>2)*128 + 4*n + (s&3)
   N=64: второй tile по +2048, bias перезагрузить (+0x100)
```

Накопление по K:

* `ncr` пар `(act+2048, wgt+1024)` до одного store — **побитово верно** для
  K=64/128/256 (err=0);
* `activation.ub:deep` с `dC = (#кроутонов-1) ≤ 31` (K≤1024 на инструкцию) —
  тоже верно, и по времени **то же самое** (обе ветки упираются в темп выдачи,
  ~19 тактов на кроутон). Для K=2048 — два `:deep` по dC=31.
* Семантика `dC` проверена отдельно (K=1024, 32 кроутона): `dC=31` — точно
  (err=0), `dC=30` — err=3.0 / cos=0.9927 (теряются последние 32 канала),
  `dC=32` — тоже точно. Т.е. **int8: dC = кроутонов-1**. У fp16 наоборот:
  `act_rt = ncr<<11` даёт точный результат при ncr=1..8 (девятый кроутон не
  читается), т.е. **fp16: dC = кроутонов**. Не переносить одно на другое.
* N=64: `weight.b = mxmem(w, 2047):deep` + два store'а, bias +0x100 — **верно**
  (err=0 на 2048 ячейках).

Что НЕ работает / грабли:

* без bias-загрузки store пишет **нули** (scale=0). `scale=0x3C00` (1.0 как
  обычный fp16) тоже даёт нули — нужен именно `0x6000`.
* `qhblas_hmx_transfer_column_ahf` для N≤32 заполняет только K*2 элементов
  вместо K*32 (см. §5).

## 5. Грабли SDK/стенда (не наши)

1. `qhblas_hmx_transfer_column_ahf`, ветка `N<=32`: цикл `row_iters = K>>5`
   копирует `K/32` векторов по 128 Б, т.е. `K*2` элементов вместо `K*32` —
   вес получается мусорным (cos=0.145). Рабочий путь: всегда паковать N=64.
2. `Q6_l2fetch_AP(input + (1+i)*4096, ...)` там же игнорирует реальный шаг
   строки: для K=224/256 префетч уходит на ~7 КБ за конец буфера. Если буфер
   кончается на границе страницы — **TLBMISS и падение PD** (поймано по
   `Bad VA = конец .bss + 0x1000`). Лечится guard-хвостом 64 КБ.
3. `pcycles` не тикает, пока ядро стоит в ожидании HMX: одиночный замер даёт
   170 тактов на K=2048, а честный темп (reps=1000) — 1217 тактов. Все цифры
   выше сняты в цикле.

## 6. tok/s (FFN-матмул)

Измерено: тайл 32x2048x32 = 1.075 мкс (N=32) / 32x2048x64 = 1.612 мкс (N=64).
Формула: `t(блок 32 строк, N_total) = ceil(N_total/64) * 1.612 мкс`.

* **Prefill** (M=128, FFN 128x7680x2048): 120 тайлов N=64 x 4 блока = **774 мкс**
  (2.0 GMAC) => 2.6 TMAC/s; у QNN было 2.44 мс -> **в 3.1 раза быстрее**.
* **Decode M=1** (строка дополняется до 32): 193 мкс/токен на одну FFN-матрицу
  -> потолок ~5 tok/s. HMX для M=1 **не годится**, декод остаётся на HVX/gemv.
* **Decode батчем 32** (спекулятивный/параллельный декод): 193 мкс / 32 =
  6.0 мкс/токен -> ~165 tok/s по compute.
* **Батч 64** (заполнить оба spatial-полублока, s=32..63 — сейчас не
  реализовано): кроутон и инструкция те же, MAC вдвое больше, т.е. ожидаемо
  ~330 tok/s. Это гипотеза (арифметика инструкции от заполнения не зависит,
  но проверять надо заполнением верхней 1 КБ активации и чтением второго КБ
  выхода) — самый дешёвый следующий шаг, потенциально +2x бесплатно.
