## 1. M=64 spatial: найдена и исправлена причина «половины тайла»

### Найденный дефект
Адрес store'а аккумулятора должен быть выровнен на **2 КБ** (`Rs[31:11]` — это
адрес тайла). При указателе со смещением +1 КБ HMX молча пишет только первые
1 КБ, т.е. spatial-строки 0..31. В старом стенде для K=32 выход лежал по
`base+3072` → верхняя половина тайла всегда оставалась нулевой, и «2 КБ =
64 spatial x 32 N» фактически не была проверена (проверялись только s=0..31).

Доказательство (новые пробы):
* `i8ramp K` — `A[s][k]=s`, `B[n][0]=1`: до правки `out[32..63] = 0`, после —
  все 64 строки дают `s+1`, `bad=0/64`.
* `i8one s0 k0` — единичный байт активации: до правки `act(s=40,k=5)` давала
  `hits=0`, после — `s=40`.

Правка: `vout` в `i8_core` выравнивается вверх до 2 КБ. Старые числа int8 не
меняются (они и раньше читали только первый КБ), но прежнее утверждение о
2 КБ-тайле было верно лишь для 32 строк.

### Сходимость (M=64)
| K | N | проверено ячеек | maxerr | cos |
|---|---|---|---|---|
| 32 | 32 | 2048 (s=0..63) | 0 | 1.0000000 |
| 64 | 32 | 2048 | 0 | 1.0000000 |
| 128 | 32 | 2048 | 0 | 1.0000000 |
| 512 | 32 | 2048 | 0 | 1.0000000 |
| 2048 | 32 | 2048 (sparse ±1/0) | 0 | 1.0000000 |
| 2048 | 64 | 4096 (layout6) | 0 | 1.0000000 |

### Время (reps=1000, один прогон = один вызов, pcyc/1133 = мкс)
| M | N | K | мкс/вызов | pcyc | TMAC/s |
|---|---|---|---|---|---|
| 32 | 32 | 2048 | 1.075 | 1217 | 1.951 |
| **64** | **32** | **2048** | **1.197** | **1356** | **3.504** |
| 64 | 64 | 2048 | 1.900 | 2153 | 4.415 |

Разброс M=64/K=2048/N=32 по 5 отдельным запускам: 1.197 / 1.197 / 1.198 /
1.197 / 1.198 мкс. Итог: **+2x MAC за +11% времени**, полезная скорость
1.95 → 3.50 TMAC/s (+79%). Гипотеза REPORT18 §6 подтверждена.

Команды: `mx4_test i8m M N K [bs amax mode reps mul npair]`,
`mx4_test i8ramp K N bs mul npair`, `mx4_test i8one s0 k0 K N`.

## 2. Prefill 128x7680x2048: что реально входит в замер

Новый метод `pref` — настоящий цикл по форме FFN (M строк, N%64, K%32),
активации и веса заранее упакованы в раскладку HMX, веса лежат в DDR,
тайл считается на VTCM. Режимы: bit0 — стейджинг весов DDR→VTCM,
bit1 — только стейджинг, bit3 — собрать C.

Сходимость полной формы с стейджингом: M=128, N=7680, K=2048 →
**983040 ячеек, maxerr=0, cos=1.0000000** (mode=9).

### Замеры (reps=3, 5 отдельных запусков)

| вариант | прогоны, мкс | медиана | что входит |
|---|---|---|---|
| A. только HMX-поток (веса резидентно в VTCM) | 376.4 / 376.8 / 376.8 / 377.0 / 377.2 | **376.8** | mxmem-пары + bias + store. Упаковка и любая перекладка — **вне** замера, веса одни и те же для всех 120 N-тайлов |
| B. только стейджинг 15.7 МБ DDR→VTCM | 7403.7 / 7542.3 / 7548.0 / 7587.3 / 7616.0 | **7548** | 120 x 128 КБ копий упакованных весов, HVX 128 Б |
| C. стейджинг + вычисление, без перекрытия | 7294.7 / 7306.3 / 7319.0 / 7350.7 / 7482.0 | **7319** | то же, что B, плюс HMX-поток (0.38 мс) |

Разброс B/C ~2–3% (перекрывается между собой: 0.38 мс счёта тонет в шуме
копирования). Раскладка/перекладка (pack в кроутоны) делается один раз до
таймера и **ни в одну** из цифр не входит; её время писалось в `info[13]`,
но распечатать не успел — устройство пропало.

### A: 376.8 мкс против 774 мкс из REPORT18
774 мкс были формулой (480 тайлов по 1.612 мкс, M=32 блоками). Реальный цикл с
64-spatial тайлами: 2 spatial-тайла x 120 N-тайлов x 64 кроутона, 376.8 мкс,
5.34 TMAC/s. Т.е. **в 2.05 раза быстрее формулы**, ровно за счёт M=64.

### Почему C в 20 раз хуже A (и это не ошибка замера)
FFN при M=128 обязан прочитать 15.7 МБ весов = 7.8 байт на MAC. Замеры
пропускной способности (`mx4_bw`):

| путь | ГБ/с |
|---|---|
| DDR чтение (16 МБ, 4 независимых HVX-аккумулятора) | 4.29 |
| DDR чтение (4 МБ / 64 МБ) | 3.80 / 3.83 |
| DDR→DDR | 2.22 |
| DDR→VTCM (1 загрузка в полёте) | 2.77 |
| L2-резидент (1 МБ) чтение | 40.0 |
| L2→VTCM | 19.5 |
| L2→DDR | 2.48 |

Отсюда: 15.7 МБ / 4.3 ГБ/с = **3.65 мс — нижняя граница** для prefill на этом
устройстве, наш измеренный стейджинг даёт 7.3 мс (2.08 ГБ/с). QNN-ные 2.44 мс
соответствуют ~6.4 ГБ/с, чего однопоточная in-order HVX-копия не даёт
(вероятно DMA длинными бёрстами + перекрытие с счётом).

**Вывод: 774 мкс из REPORT18 — это compute-only число, недостижимое при весах
в DDR. Честная цифра prefill: пол 3.65 мс, измерено 7.3 мс. Сравнение «в 3.1
раза быстрее QNN» из REPORT18 некорректно** — там сравнивался HMX без движения
данных с QNN целиком.

### Открытая аномалия (требует перепроверки)
Стейдж в VTCM «сырыми» HVX-векторными сторами (`*(HVX_Vector*)`) давал **неверный
результат HMX**, при этом содержимое VTCM при скалярном чтении совпадало с
источником байт в байт (`copycheck=0`); добавление `syncht`+`barrier` не помогло,
libc `memcpy` — побитово верно. На момент проверки буфер-источник был из
`malloc` (не 128 Б). Позже заменил на `memalign(128)`, но HVX-путь перепроверить
не успел. Практический вывод до перепроверки: **стейджинг в VTCM делать
memcpy/DMA, не HVX-сторами.**

## 3. int4 (`weight.n`): НЕ ДОВЕДЕНО, данных нет

Что сделано (и проверено только на уровне сборки):
* `weight.n = mxmem(Rs,Rt)` **ассемблируется** для v68 с `-mhmx`
  (hexagon-clang принял, объект получен; в objdump — `unknown`, ожидаемо для M8).
* Написан `mx4_i4` + host-команда `i4`:
  * A: MxK u8, пакуется раскладкой int8-act (lay 3, 64 spatial);
  * B: NxK int8, значения трактуются как 4-битные, пакуются в нибблы **4
    кандидатными перестановками** `wl = 0..3`:
    `byte=(k>>2)*64 + 2n + ((k&3)>>1)` (low=чётный k) / (high=чётный k) /
    `byte=(k>>2)*64 + n + 32*((k&3)>>1)` (low/high);
  * тайл 512 Б на 32 K x 32 N, `wgt_rt = 512*ncr-1` (511 на один кроутон),
    параметрический bias/scale (`bs`), store `:after:sat.ub`, плюс ветка
    chunked `:deep` по активации;
  * host: CPU-эталон, наборы данных `+1`, `-8..7`, `±7`, вывод err/cos/bad.
* Собрано в `/tmp/opencode/hmx4` и в репо (BUILD OK).

Что **не** получено: ни одной цифры. Неизвестны раскладка нибблов, `wgt_rt`,
масштаб (0x6000 или другой), знак/нуль-точка, поведение на ±7, время K=2048.
Первое, что надо прогнать при возврате устройства:
`mx4_test i4 32 32 32 0 0x6000 -1 0 100` (A=1,W=1,K=32 — найти identity-масштаб,
ожидание `out=32`), затем `mx4_test i4 32 32 32 {wl} {bs} -2 0 100` по wl=0..3.

## 4. Decode: M=1 vs 32 vs 64 (одна FFN-матрица, K=2048, N=7680)

reps=3, один прогон = полный проход матрицы (15.7 МБ весов).

| M | compute-only, мкс/проход | мкс/токен | tok/s | со стейджингом, мкс/проход | мкс/токен | tok/s |
|---|---|---|---|---|---|---|
| 1 | 126.3 | 126.3 | 7916 | 7357 | 7357 | **136** |
| 32 | 159.3 | 4.98 | 200837 | 7491 | 234.1 | **4272** |
| 64 | 189.7 | 2.96 | 337434 | 7340 | 114.7 | **8720** |
| 128 | 376.8 | 2.94 | 339883 | — (не снято) | — | — |

Как читать:
* «compute-only» — веса уже в VTCM (для 15.7 МБ недостижимо), это верхняя
  оценка. Реально достижимая колонка — «со стейджингом».
* M=1 платит те же 15.7 МБ за один токен: 136 tok/s, пол ~274 tok/s
  (3.65 мс). Батч 64 — 8720 tok/s, т.е. **64x на токен** (в 19x лучше M=32).
  Одиночный decode упирается в DDR, а не в HMX-арифметику.
* M=1 compute-only (126.3 мкс) на 33% быстрее M=64 (189.7 мкс) при
  **одинаковом числе инструкций** — аномалия, требует перепроверки (пока
  зафиксирована как измеренная).
* Это одна матрица FFN; в слое их две, плюс attention и остальное — таблица
  нужна для сравнения режимов, а не как tok/s модели.
