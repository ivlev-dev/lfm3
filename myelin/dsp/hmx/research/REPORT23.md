# REPORT23: int4-prefill на реальных весах LFM3 — compute против трафика

Дата: 2026-11-22. Стенд `myelin/dsp/hmx`, устройство XQ-BC72 (SD888, Hexagon v68,
unsigned PD), adb по Wi-Fi. Тулчейн: Hexagon SDK 6.7, hexagon-clang 21.0.04,
CDSP 1.13 ГГц (`clk` → 1133 pcycles/µs).

Форма замера — боевая FFN LFM3: `N=7680, K=2048` (`blk.0.ffn_gate.weight`,
Q4_K), плюс второй тип матрицы слоя `N=2048, K=7680` (`blk.0.ffn_down.weight`,
Q6_K). Веса — **реальные, из GGUF**, не синтетика.

---

## 0. Итог

| | int4 (этот отчёт) | int8 (`pref`) | QNN (референс) |
|---|---|---|---|
| вес матрицы 7680×2048 | **7.86 МБ** | 15.7 МБ | int4 = 7.86 МБ |
| стейджинг DDR→VTCM | **3.8–4.5 ГБ/с** | ~2.1 ГБ/с | ? |
| compute-only (M=128) | **386.7 мкс** (5.21 TMAC/s) | 735.3 мкс (2.74 TMAC/s) | ? |
| **prefill M=128, всего** | **2.13–2.53 мс**, медиана 2.37 | 7.57–8.39 мс, медиана 8.06 | 2.44 мс |
| слой FFN (gate+up+down) | **≈ 7.0 мс** | ≈ 24 мс | ≈ 7.3 мс (если 2.44 — одна матрица) |
| decode N=1 (GEMV) | 0.811 мкс | 0.962 мкс (−15.7 % у int4) | — |
| корректность | cos=1.0000000, maxerr=0 | cos=1.0000000, maxerr=0 | — |

**Главное.**

1. На реальных весах int4-prefill `128×7680×2048` = **2.4 мс** (медиана 2.37,
   лучший прогон 1.90). Это в **3.4 раза** быстрее нашего int8-пути (8.06 мс) и
   **в пределах шума равно QNN 2.44 мс** для одной матрицы.
2. Узкое место — по-прежнему **доставка весов**, а не HMX: compute-only
   386.7 мкс против 2.4 мс всего; при двойной буферизации счёт **почти
   полностью прячется** под копирование (`compute/rep` = total − copy ≈ 0.38 мс,
   ровно compute-only). Без двойной буферизации — 3.7 мс, см. §5.3.
3. int4 выигрывает дважды: **2× по трафику** (7.86 против 15.7 МБ) и, неожиданно,
   **1.9× по compute** на реалистичных активациях (386.7 против 735.3 мкс).
   Второе — не «половина K», а то, что int8-инструкция тянет 2 КБ веса на
   64 канала, int4 — 512 Б на 32 канала; при полном диапазоне активаций
   int8-поток упирается в свой вес (см. §5.4 — данные зависят от распределения
   активаций, у int8 сильнее).
4. Полный FFN-бюджет prefill на 128 токенов: **167 мс** (24 слоя × 3 матрицы
   × ~2.3 мс). Нижняя граница по трафику: 566 МБ / 5.0 ГБ/с = **113 мс**;
   потолок по compute, если бы веса были бесплатны: **27.8 мс**.
5. «QNN 2.44 мс на слой» арифметически не может быть целым FFN-слоем:
   23.6 МБ int4 / 2.44 мс = 9.7 ГБ/с, а измеренный потолок копирования
   DDR→VTCM на этом устройстве — 4.96 ГБ/с. Значит 2.44 мс — это **одна
   матрица** 7680×2048 (3.2 ГБ/с, реалистично), и наш результат её догоняет.

## 1. Постановка

REPORT19 закрыл int8-prefill: `128×7680×2048` = 376.8 мкс compute, но 7319 мкс
со стейджингом 15.7 МБ весов. Вывод: узкое место — DDR, пол 3.65 мс при потолке
4.29 ГБ/с. REPORT21 закрыл int4 `weight.n` (K>32 работает после исправления
упаковки: `byte(k,n) = 512*(k>>5) + 128*((k&31)>>3) + 4*n + (k&3)`, ниббл
старший при `((k>>2)&1)`, 4-бит two's complement).

Вопрос этого отчёта: **что даёт int4 на боевой форме с реальными весами** —
сколько мкс на слой FFN, сколько на все слои, и что это значит против QNN.
Отдельно: подтверждается ли выигрыш int4 на decode N=1 (~15 %).

Не входит: прод-путь (`myelin-npu`, `dsp/hvx`), коммиты, `myelin/docs`.

## 2. Веса: из GGUF в раскладку HMX

Новая утилита стенда `mkblob.c` (dev-машина, `cc`, включает
`../hvx/gguf_f32.h` — готовый Q4_K/Q6_K де-квантователь):

```
./mkblob models/LFM3-1.7B-Q4_K_M.gguf blk.0.ffn_gate.weight gate
./mkblob models/LFM3-1.7B-Q4_K_M.gguf blk.0.ffn_down.weight down
```

Что делает:

* читает тензор (`dim[0]=K`, `dim[1]=N`), де-квантует Q4_K/Q6_K → f32;
* квантует в **int4 симметрично, блочный масштаб на 32 K**
  (`scale = max|w|/7`, `q = round(w/scale)` в `−8..7`), упаковывает по
  раскладке стенда (512 Б = 32 K × 32 N, тайлы 32 N подряд);
* пишет `*.i4` (7.86 МБ на матрицу), `*.i4s` (масштабы f32),
  `*.i8` (int8 per-row, row-major — для пути `pref`), `*.i8s`, `*.meta`;
* считает точность на f32-активациях (32 столбца × 8 строк).

Точность квантования (cos к f32-эталону, `blk.0.ffn_gate.weight`):

| схема | cos |
|---|---|
| int4, блочный масштаб на 32 K | **0.995341** |
| int4, один масштаб на строку (как в проде `gemv_weights.rs`) | 0.988286 |
| int8, per-row | 0.999964 |

Блочный масштаб на 32 K выигрывает у per-row 0.7 п.п. cos — поэтому он и
заложен, но см. §8.2 про цену его применения.

Блобы уезжают на телефон один раз (`./deploy.sh weights`, 7.9 + 15.7 МБ),
модель на устройство не копируется.

## 3. Методика стейджинга (`i4pref`)

Новый метод стенда `i4pref M N K [mode] [reps]` (`mx4.idl`, `mx4_impl.c`,
`host.c`). Цикл ровно такой, как будет в проде:

```
для каждой 32-N плитки t (nt = N/32):
    копия страйпа весов t (K/32 * 512 Б = 32 КБ при K=2048) DDR -> VTCM
    для каждого spatial-тайла m (mt = ceil(M/64)):
        для каждого K-кроутона c (ncr = K/32):
            activation.ub = mxmem(vact + (m*ncr+c)*2048, 0x3FF)
            weight.n     = mxmem(slot + c*512, 511)
        bias = mxmem2(0x6000-слова);  mxmem(vout,0):after.sat.ub = acc
```

Флаги `mode`:

| бит | значение |
|---|---|
| 0 | стейджинг DDR→VTCM (без него веса резидентно — compute-only) |
| 1 | только стейджинг (без HMX) |
| 3 | собрать C (корректность; добавляет `hmx_sync` на плитку) |
| 4 | двойная буферизация: копия плитки t+1 идёт под счёт плитки t |
| 5 | стейджить прямо из FastRPC-буфера (иначе копия в DSP-heap, как `pref`) |
| 6 | вытеснить L2 (чтение 16 МБ) перед замером — холодный DDR |
| 12..15 | глубина стейджинга − 1 (сколько 32-N плиток за одну копию) |
| 8 (host) | sparse-активации вместо реалистичных |
| 10 (host) | нулевые активации (контроль «выход не пишется») |

Активации (host, `gen_act`):

* **реалистичные** (по умолчанию): `x ~ N(0,1)`, `y = SiLU(x) + 0.35`,
  per-token масштаб в uint8. Сдвиг нужен потому, что HMX-активация
  `activation.ub` **беззнаковая** — отрицательные значения читались бы как
  255 (это отдельно проверено нулевым контролем и первым прогоном, где
  `cos=0.11`: причина была именно в знаке активации, а не в весах);
* **sparse** (для точной сверки): 1/8 ненулевых = 1, остальное 0.

Учёт времени: `us_total` — вокруг всего цикла до `hmx_sync`; `us_copy` —
сумма `HAP_perf_get_time_us` вокруг каждой копии; `compute = total − copy`;
`pcyc_total`. Копирование — HVX 128-Б векторами (`copy_v2048`), **не libc
`memcpy`** (см. §7.1). Стейджинг — не более 32 КБ на шаг, VTCM под
M=128/K=2048 — 300 КБ из 4 МБ.

Протокол: `reps=1` в отдельном процессе × 3 запуска (холодный DDR, L2
вытеснена), плюс `reps=3` (тёплый). Разброс между запусками ±10 % (DVFS/тепло),
поэтому ниже медианы, а не лучший прогон (см. §5.7).

## 4. Корректность на реальных весах

Не «все единицы»: веса — 4-битные значения из Q4_K-тензора после
переквантования, K=2048 (все 64 кроутона), эталон — точный целочисленный
`sum_k A[s][k]*q[n][k]` по тем же q, что лежат в `.i4` (сатурация в uint8
применяется к обоим одинаково).

| прогон | проверено | maxerr | cos | sat |
|---|---|---|---|---|
| gate, M=128: срез 4×64 (`n=64..127`) | 256 | **0** | — | 0 |
| gate, M=128: 8 строк × N=7680 | 61440 | **0** | **1.0000000** | 0 |
| gate, M=32: 8 строк × N=7680 | 61440 | **0** | **1.0000000** | 0 |
| down, M=128: 8 строк × N=2048 | 16384 | **0** | **1.0000000** | 50 |
| int8 (`pref8`), M=128: 8 строк × N=7680 | 61440 | **0** | **1.0000000** | 29203 |

`copycheck=0` (VTCM совпадает с блобом побайтово, первая плитка), `sat` в
uint8-стор — ожидаемое ограничение *стенда*: `:after:sat.ub` пишет 8 бит,
реальные суммы префилла туда не влезают, прод читает аккумулятор и применяет
масштаб. На корректность это не влияет: эталон сатурирует так же.

## 5. Числа

Все — одна матрица, веса в DDR, стейджинг в замер входит.

### 5.1. int4 gate, холодный DDR (L2 вытеснена), двойная буферизация, reps=1

| M | прогоны, мкс | медиана | copy/rep | GB/s | compute-only |
|---|---|---|---|---|---|
| 32 | 2185 / 2207 / 2036 | **2185** | 1889–2061 | 3.8–4.2 | 147.3 |
| 64 | 2096 / 2173 / 2148 | **2148** | 1919–2014 | 3.9–4.1 | 193.7 |
| 128 | 2534 / 2361 / 2366 | **2366** | 1970–2176 | 3.6–4.0 | 386.7 |

(в предыдущем прогоне того же бинаря M=128 дал 2132 / 2381 / 2426 — разброс
±15 % между прогонами, поэтому в таблицах медианы.)

Скейлинг по M почти плоский: считается всё равно один и тот же объём весов,
рост M добавляет только счёт (147→387 мкс), который прячется под копию.

### 5.2. Глубина стейджинга (M=128, холодный)

| плиток за копию | прогоны, мкс | медиана |
|---|---|---|
| 1 (32 КБ) | 2534 / 2361 / 2366 | 2366 |
| 4 (128 КБ) | 2265 / 2211 / 2312 | **2265** |
| 16 (512 КБ) | 2360 / 2383 / 2396 | 2383 |

Глубина 4 (128 КБ за копию) даёт −4 %, это на грани разброса.
Дальше увеличивать смысла нет: 4.96 ГБ/с — потолок копирования
(`bw2 kind=3`, 128 КБ чанки: 8 МБ → 4.98 ГБ/с, 16 МБ → 4.96 ГБ/с, то есть L2
уже не помогает), и 32 КБ его почти достигают.

### 5.3. Разделение compute / copy / total (M=128, K=2048)

| режим | прогоны, мкс | медиана |
|---|---|---|
| только счёт (веса резидентно, reps=3) | 386.7 | **386.7** (5.21 TMAC/s) |
| только стейджинг (двойная буферизация, L2 вытеснена) | 1905 / 1975 / 1903 | **1905** (4.18 ГБ/с) |
| стейджинг + счёт, **двойная буферизация** | 2534 / 2361 / 2366 | **2366** |
| стейджинг + счёт, **без** буферизации (mode 65) | 3783 / 3779 / 3678 | **3779** |
| `pcyc_total` при полном прогоне | — | 2.4–2.9 М, ~1133 cycles/мкс |

Три вывода:

* **двойная буферизация обязательна: 3.78 → 2.37 мс (1.6×).** Без неё
  «compute» в учёте раздувается до 1.77 мс (вместо 0.39) — ровно тот случай,
  когда HMX читает только что записанный HVX-копией VTCM и ждёт слива записи;
  с перекрытием этот штраф уходит под следующую копию. Это же объясняет
  расхождение учёта у `pref` (§5.4).
* с двойной буферизацией `total ≈ copy + 0.38 мс`, т.е. остаток — честный
  счёт (386.7 мкс) плюс контеншн за VTCM-порты.
* дальше прятать нечего: 1905 мкс упирается в 4.2 ГБ/с копирования, потолок
  `bw2` — 4.96 ГБ/с.

### 5.4. Почему int8-compute вдвое хуже на тех же весах

`pref8` (тот же протокол, те же веса после int8-квантования):

| M | холодный reps=1 | тёплый reps=3 | compute-only (реалистичные акт.) | compute-only (sparse) |
|---|---|---|---|---|
| 32 | 7786 | 4653 | 255.0 | — |
| 64 | 7909 | 4670 | 368.0 | — |
| 128 | **8059** | **4812** | **735.3** (2.74 TMAC/s) | 388.9 |

У int4 на тех же реалистичных активациях compute-only 386.7 мкс, на sparse —
293.4 мкс. То есть **оба пути data-dependent**, но int8 сильнее (735 → 389,
+89 %), int4 слабее (387 → 293, +32 %). Причина, наиболее вероятная: int8
тянет 2 КБ веса на инструкцию (64 канала × 32 K) против 512 Б у int4, и при
полном диапазоне активаций упирается в подачу веса в HMX-массив.

Практически: сравнивать int8 и int4 надо на одном распределении активаций
(у нас — реалистичный uint8-SiLU для обоих).

Замечание по учёту: у `pref` внутренний таймер копирования даёт 3.1–3.9 мс,
а полное время 7.8–8.4 мс, т.е. учёт не сходится (у `i4pref` с двойной
буферизацией сходится: copy 1.97–2.18 + compute 0.38 ≈ total; без буферизации
— тоже не сходится, см. §5.3). Для сравнения берём total.

### 5.5. Вторая матрица слоя: down (N=2048, K=7680)

| | прогоны, мкс | медиана | GB/s |
|---|---|---|---|
| стейджинг + счёт (M=128, холодный) | 2193 / 2206 / 2276 | **2206** | 4.2–4.4 |
| только стейджинг | 1926 | 1926 | 4.1 |
| только счёт | 384.3 | 384.3 (5.23 TMAC/s) | — |
| корректность | 16384 ячейки, maxerr=0, cos=1.0 | — | — |

Важно: `pref` (int8) сюда не применим — у него `PREF_MAXK 2048`, K=7680 не
проходит валидацию (`rc=512` = 2×256, FastRPC так передаёт удалённый код −2).
int4-путь K=7680 держит (ncr=240, VTCM 1.2 МБ).

### 5.6. Повторяемость (шум)

Основной кейс (`i4pref 128 7680 2048 81 1`, холодный DDR) снят **6 раз
независимыми запусками** в двух сессиях:

| прогоны, мкс | медиана | разброс к медиане |
|---|---|---|
| 2132 / 2361 / 2366 / 2381 / 2426 / 2534 | **2374** | −10 % … +7 % |

int8 (`pref8 128 7680 2048 1 1`), 6 запусков: 7566 / 7995 / 8053 / 8065 /
8101 / 8387 → медиана **8059**, −6 % … +4 %. int8 стабильнее (дольше работает,
успевает выйти на полку DVFS), int4-прогоны короче и сильнее зависят от того,
на какой частоте стартовали.

Повторные прогоны «только счёт» (веса резидентно) детерминированы:
386.7 / 386.2 / 386.7 мкс (int4 M=128), 735.3 / 735.2 мкс (int8) — то есть
шум даёт именно DDR/DVFS, а не HMX.

Итого для бюджета: **2.37 ± 0.10 мс** на матрицу 7680×2048 (int4, M=128,
холодный DDR).

### 5.7. Decode N=1 на реальных весах

```
$ mx4_test dec 2048 2000
dec N=1 K=2048 reps=2000 real row0 of blk.0.ffn_gate.weight
  int4: 0.811 us  pcyc=918   int8: 0.962 us  pcyc=1089   delta=-15.7%
```

Ожидание «~15 %» **подтверждается**: −15.7 % на реальной строке
`ffn_gate.weight` (в двух независимых запусках −15.6 % и −15.7 %), ровно как
в REPORT21 на синтетике (−15 %). Но это
compute-only на резидентных весах; в реальном decode на слой всё равно
доминирует чтение весов из DDR.

## 6. Бюджет prefill

Архитектура LFM3-1.7B по GGUF: **24 слоя** (`blk.0..blk.23`), hidden 2048,
FFN 7680. На слой три FFN-матрицы по 2048×7680 (gate, up, down) — по
2.01 Г MAC на токен каждая, по 7.86 МБ int4-веса.

### 6.1. Один слой, M=128

| | время | трафик весов |
|---|---|---|
| gate | 2.37 мс | 7.86 МБ |
| up (та же форма) | 2.37 мс | 7.86 МБ |
| down (N=2048, K=7680) | 2.21 мс | 7.86 МБ |
| **FFN-слой** | **≈ 6.95 мс** | **23.6 МБ** |
| из них compute | 1.16 мс (17 %; прячется под копию) | — |

### 6.2. Все слои, prefill 128 токенов

| | FFN (24 слоя) | комментарий |
|---|---|---|
| измерено (int4) | **167 мс** | 566 МБ весов, 3.6–4.2 ГБ/с |
| пол по трафику | 113 мс | 566 МБ / 5.0 ГБ/с (потолок копии) |
| потолок по compute | 27.8 мс | 24 × 3 × ~0.386 мс |
| int8, тот же путь | **580 мс** | 8.06 мс/матрица × 72 |

Это только FFN. Не-FFN матрицы слоя (shortconv `in_proj` 6144×2048, `out_proj`
2048×2048, attention q/k/v/o) добавляют ≈ 10.5 МБ int4 на слой (≈ +2.6 мс при
той же скорости), их в этом отчёте не мерили.

Итого по FFN: **128 токенов / 0.167 с ≈ 765 tok/s** (prefill, только FFN).
Если бы веса были бесплатны — 4600 tok/s, т.е. всё упирается в DDR.

### 6.3. Против QNN 2.44 мс

Арифметика, которая закрывает вопрос:

| гипотеза о «2.44 мс на слой» | требуемая скорость | возможно? |
|---|---|---|
| одна матрица 7680×2048, int4 | 7.86 МБ / 2.44 мс = **3.2 ГБ/с** | да, мы мерим 3.6–4.5 |
| одна матрица, int8 | 15.7 МБ / 2.44 мс = 6.4 ГБ/с | на грани (потолок 4.96) |
| весь FFN-слой, int4 | 23.6 МБ / 2.44 мс = **9.7 ГБ/с** | нет |
| весь FFN-слой, int8 | 47.2 МБ / 2.44 мс = 19.3 ГБ/с | нет |

Значит 2.44 мс — это **одна** матрица. Тогда слой FFN у QNN ≈ 7.3 мс, у нас
≈ 6.95 мс: **мы на уровне QNN** по FFN-prefill, и оба упираются в DDR, а не в
HMX. Наш прежний int8-путь (≈ 24 мс/слой) проигрывал QNN в 3.3 раза — ровно
потому, что вёз вдвое больше байт и копировал их вдвое медленнее.

## 7. Что выяснилось попутно

### 7.1. libc `memcpy` в VTCM в 5 раз медленнее HVX-копии

| способ | ГБ/с (7.86 МБ, 32 КБ шаг) |
|---|---|
| `memcpy(dst_vtcm, src, 32768)` | **0.9** |
| HVX `copy_v2048` (16×128 Б на 2 КБ) | **3.8–4.5** |

Это меняет вывод REPORT19 §2 («стейджинг делать memcpy, не HVX-сторами»):
HVX-путь в этом стенде **корректен** (`copycheck=0` побайтово и полная сверка
61440 ячеек с `maxerr=0`) и впятеро быстрее. Ту аномалию, видимо, давало
что-то ещё (невыровненный источник), а не HVX-запись как таковая. В `i4pref`
стейджинг — HVX, `memcpy` оставлен только как исторический путь.

### 7.2. Учёт «copy/compute» врёт, если мерить только копию

Без двойной буферизации `i4pref` даёт 3.78 мс при том же объёме копий 1.9 мс:
`syncht` не ждёт фактического слива VTCM-записи, и штраф проявляется в
следующей HMX-операции, а не в таймере копии. Поэтому в таблицах — **total**
(и `total` сходится с `copy + compute` только при двойной буферизации, §5.3).
Тот же эффект, похоже, стоит за расхождением учёта у `pref` (§5.4).

### 7.3. Знак активации

`activation.ub` — беззнаковая. Активации с отрицательными значениями
(`int8`-коды) читаются как 255; первый прогон дал `cos=0.11` именно из-за
этого, а не из-за весов. Для int4/uint8-пути квантизатор активаций должен быть
беззнаковым (zero-point 0 или сдвиг), иначе нужен компенсирующий bias.

## 8. Ограничения и открытые вопросы

1. **Блочный масштаб 32 K в замер не входит.** Измерен целочисленный GEMM
   (все 64 кроутона, точная сверка) + стейджинг. Блочный масштаб требует
   отдельного прохода по 64 частичным суммам на плитку: объём — 64 × 2048
   int32 = 512 КБ на плитку, 480 плиток на матрицу → **245 МБ VTCM-трафика**.
   При VTCM ~40 ГБ/с это ~6 мс на матрицу, при ~290 ГБ/с — ~0.9 мс; т.е. от
   «незаметно» до «сравнимо со всем стейджингом». В цифрах §5–6 это
   **не учтено**. Прод (`gemv_weights.rs`) обходит проблему per-row
   масштабом — ценой 0.7 п.п. cos (0.9883 против 0.9953) и одним умножением
   на выходную строку. Если блочный масштаб обязателен, бюджет prefill надо
   увеличить на эту величину (и мерить отдельно).
2. **uint8-стор стенда** насыщается на реальных активациях; прод читает
   аккумулятор. На время это не влияет (стор тот же), на корректность — учтено
   (§4).
3. **int8-путь не вытеснял L2** (в `pref` нет такого режима), поэтому его
   холодная цифра — оптимистичная нижняя граница; на вывод это не влияет
   (int8 и так в 3.4 раза медленнее).
4. **Разброс ±10 %** между запусками (DVFS/тепло). Медианы приведены; для
   «сколько на слой» берите 6.95 ± 0.25 мс. Финальные контрольные прогоны
   снять не удалось — телефон ушёл из adb-сети сразу после серии; шум оценён
   по 6 независимым прогонам основного кейса (§5.6), что строже двух
   запланированных.
5. **Не-FFN матрицы** (attention, shortconv) не мерили — их ≈ 10.5 МБ int4 на
   слой добавляют ~2.6 мс.
6. **Стейджинг из FastRPC-буфера** (mode bit5) не мерили отдельно: все цифры —
   из DSP-heap копии, как в `pref`, чтобы сравнение было честным.
7. **Куда расти дальше:** 3-битные веса (5.9 МБ) дадут ~1.8 мс/матрицу при том
   же потолке копии; либо L2-резидентные горячие матрицы; либо DMA вместо
   HVX-копии — потолок 4.96 ГБ/с уже виден, значит выигрыш только в
   перекрытии, а оно при двойной буферизации уже почти полное.

## 9. Изменённые файлы и воспроизведение

`myelin/dsp/hmx/`:

* `mkblob.c` — **новый**: GGUF → int4 (блочный 32 K) / int8 блобы + метрики;
* `mx4.idl` — метод `i4pref` (форма `pref`, int4-веса);
* `mx4_impl.c` — `mx4_i4pref` (+ `i4p_copy`, вытеснение L2, двойная
  буферизация, глубина стейджинга); существующие пути не тронуты;
* `host.c` — команды `i4pref`, `pref8`, `dec`; загрузка блобов (`$WNAME`,
  `$I4DIR`), реалистичные/`sparse` активации, эталон и cos;
* `build.sh` — собирает `mkblob` системным `cc`;
* `deploy.sh` — `./deploy.sh weights` (генерация + пуш блобов), `WNAME`
  пробрасывается в `mx4_test` на устройстве;
* `research/run23.sh` — скрипт прогона матрицы замеров;
* `research/run23.txt` — полный лог этого отчёта.

Воспроизведение:

```bash
export MADB=<adb-серийник>
HEXAGON_SDK_ROOT=/opt/hexagon-sdk-6.7.0.0 ./build.sh
./deploy.sh push
./deploy.sh weights
TENSOR=blk.0.ffn_down.weight WBLOB=down ./deploy.sh weights
./research/run23.sh                     # пишет research/run23.txt

# вручную:
./deploy.sh i4pref 128 7680 2048 81 1   # int4, холодный DDR, двойной буфер
./deploy.sh i4pref 128 7680 2048 265 1  # корректность (sparse, сбор C)
./deploy.sh pref8  128 7680 2048 1 1    # int8 на тех же весах
./deploy.sh dec 2048 2000               # decode N=1
```

Регрессии существующих путей после правок (проверены):

```
i4 32 32 2048 4 0x6000 -1 0 200     → 1.345 мкс, maxerr=0 cos=1.0 MATCH
i8 32 2048 3 3 0x3FF 1023 ... 200   → MATCH (cand2)
href 32 32 0 3                      → err=0.00191 cos=1.000000 (как было)
pref 128 7680 2048 9 1              → 983040 ячеек, maxerr=0 cos=1.0 MATCH
```
