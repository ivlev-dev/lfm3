# Deep-рецепт PRM §4.2 проверен в 5 конфигурациях — накопление 32 каналов не работает

## Что сделано

Реализован `:deep`-вариант по PRM §4.2:
```c
act_rt  = ((ncr-1) << 11) | (spatial mask) | (31 << 2);   // dC=1
wgt_rt  = wgt_size - 1;                                   // 2047 или 4095
activation.hf = mxmem(act, act_rt):deep;  weight.hf = mxmem(wgt, wgt_rt);
bias = mxmem2(...);  mxmem(out, 0):after.hf = acc;         // один store
```
Активация переложена в «два непрерывных кроутона по 16 каналов» (1 КБ каждый:
`1024*(c>>4) + (s>>1)*64 + (c&15)*4 + (s&1)*2`), веса непрерывны
(`(k>>1)*128 + n*4 + (k&1)*2`, k=0..15 → 1 КБ, k=16..31 → второй 1 КБ).

## Результаты (fp16 32×32×32, случайные A/B)

| конфигурация | max_abs_err | bad |
|---|---|---|
| split-кроутоны, dC=1, wgt 2047 | 74.999 | 1004/1024 |
| исходная раскладка, dC=1, wgt 2047 | 71.001 | 929/1024 |
| split, dC=1, wgt 4095 | 74.999 | 1004/1024 |
| исходная + spatial mask 0b11100, wgt 2047 | 71.001 | 929/1024 |
| исходная + mask, wgt 4095 | 71.001 | 929/1024 |

Ни один вариант не меняет картину: **суммируются только 16 из 32 k**. При этом:
* `A=2.0, B=I` → ровно `1.999 ≈ 2.0` во всех 1024 ячейках (умножение и store верны);
* `A[s][c]=s+c/32, B=I` → карта `(s_read,c_read)` точная (`s=0: 0:0 0:1 …`,
  `s=1: 1:0 1:1 …`) — раскладки активации/весов/выхода **совпадают с PRM**;
* store покрывает весь тайл 2 КБ одной инструкцией (проверено маркером).

Т.е. единственное, что не работает — multi-crouton накопление на этом устройстве
(v68, unsigned PD): ни `dC`-вариант, ни второй pair с `Rs[6:2]=16` не добавляют
вторые 16 каналов.

## int8 / S4

* int8 S1: не закрыт (один pair = 16 MAC; `16×16×32` → 80/256, полный → max_abs_err=32).
* 128×7680×2048: не замерял — нет корректного полного K.

## Вердикт

**HMX (v68, int8 и fp16) — не готов**, уходит в R&D. Что снято и подтверждено:
питание (`HAP_power_set_HMX`), формат 16-битных ячеек, раскладки
act/wgt/out (совпали с PRM), покрытие store (2 КБ одной инструкцией), bias.
Что осталось: **накопление >16 входных каналов** — на этом чипе/прошивке
документированный `deep`-путь не даёт ожидаемого; вероятно, требует иной формы
(например, `:deep` на весах + непрерывные веса, как в QNN-кернелах
`hmx_convhbh1x1deep_stride1`, где `weight.b = mxmem(...):deep`).

Prefill — на QNN/HVX (2.44 мс / 0.83 TMAC/s). Устройство здорово, 0 зависаний.
