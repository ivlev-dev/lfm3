# REPORT25: HMX-стор на реальном v68 — семантика и рабочий рецепт int4-партиалов

Дата: 2026-11-23. Устройство: XQ-BC72 (SD888, Hexagon v68, unsigned PD, adb
192.168.10.15:5555). Стенд `myelin/dsp/hmx` (не изменялся), toolchain
Hexagon SDK 6.7 / hexagon-clang 21.0.04, дизассемблер
`.../HEXAGON_Tools/21.0.04/Tools/bin/hexagon-llvm-objdump`.

Все числа ниже **измерены на телефоне** (`research/probe25.c`,
лог `research/run25-device.txt`), а не в `hexagon-sim`. Именно расхождение
симулятора и железа было источником ошибки REPORT24.

---

## 0. Итог

1. **У QNN на v68 вообще нет int4-матмула на HMX.** В обоих доступных
   v68-скелетах QNN HTP (`libVppQnnHtp.so`, `libsnpe_dsp_v68_domains_v3_skel.so`)
   на 105 МБ дизассемблера **ноль** инструкций `weight.n` (4 бита) и
   `weight.c`; есть только `weight.b` (int8) и `weight.hf` (fp16), плюс
   `activation.ub[:cm]` / `activation.hf`. Имён ядер `hmx_convhnh*` / `…w4b`
   в таблице строк тоже нет. Значит «точного как у QNN» рецепта int4 +
   блочные масштабы на v68 не существует: QNN либо деквантует 4 бита перед
   HMX, либо считает их на HVX.
2. **Стор изучен полностью (числа в §3):**
   * `.ub` (`mxmem(Rs,Rt):after:sat.ub = acc`): 2 КБ = **64 строки** × 32 N,
     байт `128*(s>>2) + 4*n + (s&3)`; значение
     `u = clamp(trunc(acc · fp16(word)/512), 0, 255)`; без `:sat` — то же,
     но `mod 256` (256→0, −32→224).
   * `.uh` (`…:after[.sat].uh = acc:2x1`): 2 КБ = **только 32 нечётные
     строки** (чётные не пишутся вообще), 2 строки на 128-байтный вектор,
     `byte = 128*(s>>2) + 4*n + 2*((s>>1)&1)` для нечётных s;
     значение `u16 = (max(0,acc) · fp16(word)/2) mod 65536` — отрицательные
     **зануляются**, положительное переполнение **заворачивается**
     (1000→59392, 2000→53248); `:sat` от этого не спасает.
   * bias-блок: 128 Б «младших» слов (`{out_bias[31:16], scale[15:0]}` на
     32 канала) + 128 Б «старших»; `bias = mxmem2(addr)` — один блок на
     32 канала; адрес 256-байтный, QNN двигает его на `+0x100`.
     `scale = 0x6000` (fp16 512) — единица (`/512` — неявный сдвиг стора).
3. **Ключевое различие с симулятором: младшие биты адреса отбрасываются.**
   Смещение 512 Б в указателе активации **молча исчезает** (проверено:
   `aoff=0` и `aoff=512` дают байт-в-байт одинаковый результат), т.е.
   гранулярность не меньше 1 КБ (PRM: `Rs[31:11]` = 2 КБ). У весов такого
   нет — 128 Б, шаг 512 Б работает.
4. **Отсюда — причина провала `mx4_blkpref` на телефоне.** Константная
   активация лежит по адресу `vbias + 512 + 2048` (`mx4_impl.c:2612`), т.е.
   2 КБ + 512 Б. Маска срезает 512 Б, железо читает из `vbias + 2048` —
   первые 512 Б этой области нулевые, поэтому **строки s=0..15 не получают
   смещение C0** (ровно 512 ячеек = 16 строк × 32 N, измерено). В нашем
   порте это и выглядело как «партиал ≈ 34, не зависит от аккумулятора»:
   без смещения `u = trunc(P·m)` при `|P| ≪ C0` даёт 0…34 вместо ≈128.
   Плюс три побочных дефекта стенда (§5): segfault в host-проверке
   (`host.c:2382`), «отрицательный pcyc» (переполнение `int` на 2.3-секундном
   скалярном комбайне) и потеря `m*64*N` в `blk_emit` при `mt>1`.
5. **Рецепт (проверен на устройстве, 0 расхождений из 64 строк):** int4-пакеты
   + константный пакет `+C0` (адреса 2 КБ-выровнены!) + `.ub`-стор с
   `m = 255/(2C0)` + комбайн `Σ S_g·(u+0.5)/m − C0·ΣS_g`. Диапазон
   `u ∈ [26…228]` при `C0 = 1.25·max|P|`. Цена — 1 лишний HMX-пакет на
   группу (для `G=1` это ×2 по пакетам; для `G=4` — +25 %).
6. **Точный 16-битный вариант** (`.uh`) возможен, но: (а) покрывает только
   32 нечётные строки → нужны два прохода по M (×2 пакетов), (б) отрицательные
   значения зануляются, поэтому C0 нужен и там, (в) зато `S_g` можно
   зашить в bias-слово группы, и комбайн становится чистым суммированием.

## 1. Что искали и что нашли (QNN v68)

### 1.1. Где лежат QNN-либы

На телефоне QNN как отдельного продукта нет (`find / -name "libQnn*"` пусто),
но в `/vendor/lib/rfsa/adsp/` лежат два v68-скелета QNN HTP:

|---|---|---|
| `libVppQnnHtp.so` | 8.92 МБ | QNN 0.9.1 HTP skel (в путях: `/prj/qct/webtech_yyz5/pcgbait/projects/qnn_qnn-0.9.1/QNN/DSP/HTP/…`) |
| `libsnpe_dsp_v68_domains_v3_skel.so` | 12.4 МБ | SNPE/QNN HTP v68 skel (`SecondParty/QNN/src/qnn-htp-skel-be/DSP/HTP/…`) |

### 1.4. Цитаты дизассемблера (libVppQnnHtp.so)

int8 1×1 (`:cm`), вход 0x61b380, тело:

```
  61b3f0: { r3 = add(r3,#0x100)                     ; +256 Б = следующий блок bias
  61b3fc:   bias = mxmem2(r3) }                     ; bias-слова из VTCM
  61b40c:   mxclracc                                ; целочисленный аккумулятор
  61b41c: { r7:6 = and(r7:6,r19:18) }               ; Rt из params, маска 0x7ff
  61b5f0: { activation.ub = mxmem(r6,r7):cm          ; :cm = компактная раскладка
  61b5f4:   weight.b = mxmem(r12,r14) }
  61b600: { activation.ub = mxmem(r8,r9):cm          ; вторая половина K
  61b604:   weight.b = mxmem(r12,r15) }  :endloop0
  61b62c:   mxmem(r18,r11):after:retain:cm:sat.ub = acc   ; «хвост» строк
  61b648:   mxmem(r10,r11):before:cm:sat.ub = acc
  61b658:   mxmem(r10,r11):after:cm:sat.ub = acc          ; основной стор
```

`hbh` (16-битный выход; фрагмент тела 0x15a950…0x15ab5c):

```
  15a978: { r17 = addasl(r3,r5,#0x3) }              ; bias: 8 Б на группу каналов
  15a97c: { bias = mxmem2(r17) }
  15a9a8:   mxclracc
  15aa5c: { activation.ub = mxmem(r15,r3):above
  15aa60:   weight.b = mxmem(r23,r13):dilate }
  15aa94:   mxswapacc                                ; второй банк аккумулятора
  15ab1c:   mxmem(r3,r5):after:retain:sat.uh = acc:2x1
  15ab44:   mxmem(r3,r8):before:sat.uh = acc:2x1
```

То есть QNN на v68 для 16-битного выхода делает ровно то, что мы измеряли:
`bias = mxmem2` → `mxclracc` → пара `activation/weight` → `sat.uh = acc:2x1`
(retain/before — для краевых тайлов). Никаких `cvt`, `int32`-сторов и
`:deep` в коде нет.

Оговорка: таблица символов у скелетов вырезана, релокаций нет, поэтому
привязка «адрес → имя ядра» из `strings` не восстанавливается. Адреса выше —
это *содержимое* функций, опознанных по форме кода (`:cm` + `sat.ub` =
семейство `bbb`; `:above/:dilate` + `mxswapacc` + `sat.uh:2x1` = `hbh`).
Для целей отчёта это не мешает: важны сами формы инструкций, а они в обоих
семействах совпадают с измеренными на устройстве.

## 2. Почему `hexagon-sim` не поймал проблему

В симуляторе адрес активации используется как есть; на железе HMX
**отбрасывает младшие биты адреса** (по PRM и по комментарию `i8_core` —
`Rs[31:11]`, т.е. 2 КБ; измерение ниже даёт гранулярность не меньше 1 КБ).
Прямая проверка (§3.4): один и тот же двухпакетный int4-опыт с `aoff=0` и
`aoff=512` даёт байт-в-байт одинаковый результат — смещение 512 просто
исчезло.

Следствие для раскладки VTCM: **все слоты активаций (и адреса сторов) держим
кратными 2 КБ** — это корректно при любой из возможных гранулярностей;
для весов достаточно 128 Б.

## 3. Измеренная семантика (числа с устройства)

Все опыты — через неизменённые RPC стенда: `mx4_i8m` (int8-пара пакетов +
стор), `mx4_i4` (int4: два пакета по K=64, `mode=8` → M=64), `mx4_blkpref`
(путь с блочными масштабами). Лог: `research/run25-device.txt`.

### 3.1. `.ub` = `mxmem(Rs,Rt):after:sat.ub = acc`

Покрытие: 2048 байт = **64 spatial × 32 N**, байт
`128*(s>>2) + 4*n + (s&3)` (подтверждено по всем 64 строкам).

Значение (`word` — младшее слово bias-блока):

| word | fp16(word) | множитель `m = fp16/512` | acc | `:sat` | без `:sat` | trunc(acc·m) |
|---|---|---|---|---|---|---|
| 0x6000 | 512 | 1.0 | 32 | 32 | 32 | 32.0 |
| 0x6000 | 512 | 1.0 | 128 | 128 | 128 | 128.0 |
| 0x6000 | 512 | 1.0 | 256 | **255** | **0** | 256.0 |
| 0x6000 | 512 | 1.0 | 288 | 255 | **32** | 288.0 |
| 0x6000 | 512 | 1.0 | −32 | **0** | **224** | −32.0 |
| 0x6000 | 512 | 1.0 | −192 | 0 | 192 | −192.0 |
| 0x5C00 | 256 | 0.5 | 33 | 16 | 16 | 16.5 |
| 0x5C00 | 256 | 0.5 | 129 | 64 | 64 | 64.5 |
| 0x5C00 | 256 | 0.5 | −32 | 0 | 240 | −16.0 |
| 0x5800 | 128 | 0.25 | 32 | 8 | 8 | 8.0 |
| 0x5000 | 32 | 1/16 | 32 | 2 | 2 | 2.0 |
| 0x3C00 | 1 | 1/512 | 32 | 0 | 0 | 0.0625 |
| 0x7000 | 8192 | 16 | 32 | 255 | — | 512.0 |

Модель: **`u = clamp(trunc(acc · fp16(word)/512), 0, 255)`**; без `:sat`
вместо клампа — `mod 256` (двоичное дополнение). Округления нет — именно
trunc (33·0.5 = 16.5 → 16), поэтому в комбайне нужна поправка `+0.5`.

### 3.2. `.uh` = `mxmem(Rs,Rt):after[.sat].uh = acc:2x1`

* Покрытие: **только нечётные строки** (1, 3, …, 63) — 32 строки × 32 N =
  1024 u16 = 2048 Б. Чётные строки **не пишутся вообще** (проверено:
  ненулевая только строка 0 → в выходе нули; только строка 1 → значения есть).
* Раскладка (для нечётных s): `byte = 128*(s>>2) + 4*n + 2*((s>>1)&1)`.
  Измеренная карта «строка → первый байт»:
  `1:0 3:2 5:128 7:130 9:256 … 63:1922` (2 строки на 128-байтный вектор).
* Значение: **`u16 = (max(0, acc) · fp16(word)/2) mod 65536`**. `word=0x6000`
  даёт 256 на единицу acc:

| acc | u16 | комментарий |
|---|---|---|
| 1 | 256 | ×256 |
| 100 | 25600 | |
| 128 | 32768 | |
| 255 | 65280 | |
| 1000 | 59392 | переполнение → заворот (256000 mod 65536) |
| 2000 | 53248 | (512000 mod 65536) |
| −1 | **0** | отрицательные зануляются |
| −128 | **0** | — |

`:sat` на это не влияет (сравнение srt=1 и srt=3 — одинаково). То есть
16-битный стор — **беззнаковый**: «трюк с знаковым int16 через заворот»
невозможен. Смещение C0 обязательно и здесь.

### 3.3. Bias-блок

* 128 Б = 32 младших слова (канал `j` → слово `j`), затем 128 Б старших;
  блок на 32 канала; адрес кратен 256 Б, QNN двигает `+0x100` на группу.
* Младшее слово = `{out_bias fp16 [31:16], scale fp16 [15:0]}`.
  Наш стенд (`mx4_tile`, `mx4_i8m`, `mx4_qnn8`, `mx4_blkpref`) пишет только
  младшие слова (у `blkpref`/порта одинаковое слово кладётся и в
  `[64+j]`, т.е. в байты 256…383 — за пределами 256-байтного блока, скорее
  всего в следующий set; на результат не влияет).
* Проверено: при записи только слов 0…31 (байты 0…127) все 32 выходных
  канала получают правильный масштаб (`expC`: все 2048 байт = 32, `i8ramp`:
  все 64 строки) — значит раскладка «32 младших слова подряд», а не
  «канал = 8 байт подряд».
* Побочный вывод: байты 256…383 **не являются** `out_bias`. В `mx4_i8m`
  туда пишется то же слово `0x6000` (fp16 512); если бы оно применялось как
  `out_bias`, к каждому выходу добавилось бы 512 (наблюдали бы 544 вместо
  32). Наблюдали 32 → `out_bias` из этой зоны не применяется.
* `out_bias`/`input_bias` (биты [63:43]) в *правильной* позиции на устройстве
  **не проверены**: ни один RPC стенда не умеет писать байты 128…255.

### 3.4. Гранулярность адресов

Опыт: два int4-пакета (`K=64`: константа `Aq` + «реальные» данные), все
адреса активации 2 КБ-выровнены; затем то же с `aoff=+512`:

```
rec8 ... aoff=0   : 128 129 131 133 135 137 139 141
rec8 ... aoff=512 : 128 129 131 133 135 137 139 141   (байт-в-байт РАВНЫ)
```

512-байтное смещение указателя активации отброшено → гранулярность чтения
активации не меньше 1 КБ (по PRM — 2 КБ). Вес — 128 Б (шаг 512 Б в
`i4pref`/`mx4_i4` работает, `wstep=512` в опыте §4.1); у стора — тоже не
меньше 1 КБ (REPORT22: указатель +1 КБ пишет только первый килобайт).

## 4. Рабочий рецепт для int4-партиалов

### 4.1. Проверка на устройстве (int4, 0 расхождений)

`mx4_i4`, M=64, N=32, K=64 (`mode=8`), `wl=4`, `art=0x3FF`, `wc=511`:

* пакет 0: активация `Aq` (все ячейки), вес — ниббл `+7` → `P0 = 224·Aq = C0`;
* пакет 1: активация `a(s) = 3s+1`, вес — ниббл `q` → `P1 = 32·a·q`;
* адреса активации: `vact`, `vact + 2048` (2 КБ); веса: `vwgt`, `vwgt + 512`.

```
rec8 Aq=29 q= 1 C0=6496 word=0x4906 m=0.019623 -> расхождений 0/64, 128 129 131 133 …
rec8 Aq=29 q=-1 C0=6496 word=0x4906 m=0.019623 -> расхождений 0/64, 126 124 123 121 …
rec8 Aq= 2 q= 7 C0= 448 word=0x5c8e m=0.569336 -> расхождений 0/64 (все 64 клипнуты в 255)
```

Модель `u = trunc((C0 + P)·fp16(word)/512)` выполняется на всех 64 строках,
отрицательные `P` не клипаются, переполнение диапазона даёт ровно 255.

### 4.2. Псевдокод (одна N-плитка 32 канала, M≤64)

```c
/* --- VTCM layout: ВСЁ кратно 2 КБ, кроме весов (128 Б) --- */
base        = align2k(res.base);
vact[m][c]  = base + (m*ncr + c) * 2048;      // активации, 2 КБ выровнены
vwgt[i]     = ...  + i*512;                   // int4-вес тайла, 512 Б
vpart[g]    = base + ... + g * 2048;          // партиалы групп, 2 КБ
voff_act    = base + ... ;                    // 2048 Б: константа Aq (2 КБ!)
voff_wgt    = ... ;                           // 512 Б: все нибблы +7 (кратно 128 Б)
vbias       = ... ;                           // 512 Б, кратно 256

/* --- bias: m = 255/(2*C0), слово = fp16(m*512) --- */
for (j = 0; j < 32; j++) { ((u32*)vbias)[j] = word; ((u32*)vbias)[32+j] = 0; }

/* --- на каждую группу g (G кроутонов K, один масштаб) --- */
for (g = 0; g < ng; g++) {
    mxclracc;
    activation.ub = mxmem(voff_act, 0x3FF);   /* 2 КБ-выровнен! */
    weight.n      = mxmem(voff_wgt, 511);     /* все +7 -> P0 = 224*Aq = C0 */
    for (c = 0; c < G; c++)
        { activation.ub = mxmem(vact[m][g*G+c], 0x3FF);
          weight.n = mxmem(vwgt[g*G+c], 511); }
    bias = mxmem2(vbias);                     /* 256-Б блок, 32 канала */
    mxmem(vpart[g], 0) : after : sat.ub = acc;  /* u = trunc((C0+P)*m) */
}

/* --- комбайн (HVX или скаляр) --- */
for (s = 0; s < rows; s++)
  for (n = 0; n < 32; n++) {
      float a = 0, ss = 0;
      for (g = 0; g < ng; g++) {
          float sc = S[n0+n][g];
          a  += sc * (vpart[g][128*(s>>2) + 4*n + (s&3)] + 0.5f);
          ss += sc;
      }
      C[(m*64+s)][n0+n] = a / m - (float)C0 * ss;  /* строка m*64+s:
                                                      в blkpref это забыто (см. §5, п.4) */
  }
```

Ограничения и числа:

| параметр | значение | откуда |
|---|---|---|
| `C0` | `224·Aq`, `Aq = ceil(1.25·max|P| / 224)` | смещение = 1 константный пакет |
| диапазон `u` | `[26 … 228]` при `C0 = 1.25·max|P|` | измерено (rec8: 128…141) |
| запас | 25 % по `|P|`; клип даёт `u=255` (не заворот) | `:sat` обязателен |
| точность 8 бит | cos 0.99977…0.99989 (REPORT24, `blkstat`) | 8-битное квантование партиала |
| поправка | `+0.5` в комбайне (стор усекает) | измерено (§3.1) |
| цена | +1 пакет на группу | = +100 % при `G=1`, +25 % при `G=4` |
| выравнивание | активации и сторы — **2 КБ**; веса — 128 Б | измерено (§3.4) |

Резерв на будущее: если окажется, что `input_bias` (биты [63:43] старшего
слова bias-блока) на v68 применяется, то `C0` можно задать **без пакета** —
`input_bias = C0` одинаковый для всех 32 каналов, тогда −1 пакет на группу
(для `G=1` это ×1 вместо ×2). Для проверки нужен один RPC, пишущий байты
128…255 bias-блока (сейчас такого нет). В симуляторе `out_bias` не
применялся (REPORT24), `input_bias` не проверялся вовсе.

### 4.3. Точный 16-битный вариант (`.uh`)

Формула (измерена): `u16 = (max(0, P·gain) ) mod 65536`, где `gain` —
множитель из bias-слова (`fp16(word)/2`, т.е. `word = fp16(2·gain)`).

Схема: для каждой группы ставим в bias-слово `fp16(2·k·S[n][g])` (перезапись
128 Б на группу — дёшево), тогда `u16_g = k·S_g·P_g`, и комбайн — **чистая
сумма** `Σ_g u16_g` (32-битный аккумулятор, знак не нужен: все значения
неотрицательны при `k·S_g·P_g ≥ 0`, иначе нужен C0).

Ограничения:
* покрываются только нечётные строки → для M=64 нужны **два прохода** по M
  (активации со сдвигом на строку) либо M-плитки по 32 строки → ×2 пакетов
  и ×2 трафика партиалов;
* отрицательные партиалы зануляются → C0 (константный пакет) нужен
  и здесь; зато `k` выбирается из условия `2·C0·k ≤ 65535`, т.е. масштаб
  точности 16 бит вместо 8;
* диапазон: `u16` занимает `[0…65535]`, при `C0 = max|P|` рабочая часть —
  `[16384…49152]`, 2 бита запаса.

Итог: 16 бит дают cos → 1.0 (ошибка только от fp16-округления `gain`,
~5·10⁻⁴), но стоят вдвое дороже. Рекомендация REPORT24 (8 бит, `G=4`)
остаётся в силе; 16 бит — только если нужен «почти точный» партиал.

## 5. Почему `mx4_blkpref` падал на телефоне (разбор)

`mx4_test blkpref 128 7680 2048 1 257 1` на устройстве:

```
blkpref: max|partial|(sample)=5148 -> offset C0=6496 (a_k=29, q_k=7), store m=0.01963
  total/rep=2351733.0 us  copy/rep=2279.0 us  compute/rep=2349454.0 us
  combine/rep=2343948.0 us  pcyc/rep=-978702060
Segmentation fault
```

Четыре независимых дефекта:

1. **Арифметика (DSP): константный пакет не выровнен по 2 КБ.**
   `mx4_impl.c:2612`: `voact = vbias + 512u + 2048u;`, а `vbias` 2 КБ-выровнен
   → адрес 2 КБ + 512 Б → маска срезает 512 Б → железо читает 512 Б *раньше*,
   т.е. зону-зазор (нули). Результат: строки **s=0..15** (512 ячеек) не
   получают C0. Измерено напрямую (`blk_offset_map` в `research/probe25.c`):
   `u=127 (со смещением) 1536 ячеек, u=0..1 (без смещения) 512 ячеек,
   без смещения строки: s=0..15 (по 32/32)`.
   Это и есть корень «нулевых/константных партиалов»: у этих строк
   `u = trunc(P·m)`; при `|P| ≤ ~1700` и `m = 0.0196` это 0…34 — ровно
   «партиал ≈ 34, слабо зависит от аккумулятора».
   Лечение — одна строка: `voact = vbias + 2048u;` (и `vowgt = voact + 2048u`).
2. **Segfault — в host-проверке, не в DSP.** `host.c:2382`:
   `q = unpack_i4(Bp, N, K, 0, N < 256 ? N : 256);` — распаковываются только
   256 столбцов, а цикл проверки индексирует `q[n*K+k]` по всем `N=7680`.
   Отсюда SIGSEGV после печати таймингов. На `N=256` падения нет — и видно
   `cos=0.12` (это уже следствие п.1).
3. **`pcyc` отрицательный** — переполнение `int`: комбайн в DSP скалярный,
   на `N=7680, ng=64` он занимает 2.34 с (≈2.6·10⁹ тактов), и `c1-c0` не
   влезает в `int`. HMX тут не виноват.
4. **`blk_emit` не сдвигает C на m-плитку** (`mx4_impl.c:2738`):
   `blk_emit(vpart, ng, S, ng, mstore, C0, C, N, rows, i*32)` — при `mt>1`
   вторая m-плитка перезаписывает строки 0..63, а строки 64..127 остаются
   неинициализированными (`C` — `malloc`, не `calloc`). Для `M>64` это
   ломает результат независимо от п.1.

Ни один из этих дефектов не проявляется в `hexagon-sim` (маскирования
адреса там нет, скалярный комбайн «мгновенный», host-проверка с `N=256`).

## 7. Ограничения этой работы

1. **QNN-либы только скелетные.** `libQnnHtp.so` (host-часть) на телефоне нет,
   поэтому утверждение «QNN не делает int4 на v68» обосновано дизассемблером
   *двух* скелетов (0 `weight.n`), а не host-графом. Возможный путь QNN —
   деквантование int4→int8/fp16 на этапе prepare — из скелета не виден.
2. **`out_bias` / `input_bias` не проверены** (нет RPC, пишущего старшие слова
   bias-блока). Это единственный неиспользованный резерв: `input_bias` может
   убрать константный пакет `+C0` (экономия 1 пакета на группу).
3. **Режим `mode & 8` (запись C) в стенде очень дорог:** `i4pref 128 7680 2048 9 1`
   даёт 42 мс против 2.0 мс у `mode 81` при том же `cos=1.0`. Причина не в HMX:
   `pref_unpack` + счёт насыщений идут скалярно после каждого стора
   (480 × 2048 байт → 48.8 млн pcyc; `mode 81` — 386 мкс compute, как в
   REPORT23). Для замеров времени C-путь включать нельзя; на семантику стора
   (числа §3) это не влияет — они сняты по содержимому VTCM.
4. Масштаб в bias-слове — чистый fp16 (11 бит мантиссы); 4 дополнительных
   бита мантиссы в старшем слове ([35:32]) из PRM на v68 не проверялись.

## 8. Summary

* В v68-скелетах QNN (`libVppQnnHtp.so`, `libsnpe_dsp_v68…skel.so`) **нет**
  int4-ядер HMX: 0 `weight.n`/`weight.c` на 105 МБ дизассемблера, имена ядер —
  только `hmx_convbbb*` (u8×i8→u8) и `hmx_convhbh*` (u8×i8→u16). Готового
  QNN-рецепта int4 + блочные масштабы на v68 не существует.
* `.ub`-стор измерен: 64 строки, `u = clamp(trunc(acc·fp16(word)/512),0,255)`
  (без `:sat` — `mod 256`), `0x6000` = ×1.0; `.uh` — только 32 нечётные
  строки, `u16 = (max(0,acc)·fp16(word)/2) mod 65536`, отрицательные
  зануляются.
* **Главная причина провала на телефоне, а не в симуляторе: адрес активации
  маскируется до 2 КБ.** Константный пакет `+C0` в `blkpref` стоит на
  `2 КБ + 512 Б` и потому читается на 512 Б раньше → строки 0..15 теряют C0
  (ровно 512 ячеек; «партиал ≈ 34»). Правится одной строкой
  (`voact = vbias + 2048u`).
* Рецепт: int4-пакеты + один константный пакет `+C0` (все адреса активаций
  и сторов кратны 2 КБ) + `.ub` с `m = 255/(2C0)` + комбайн
  `Σ S_g(u+0.5)/m − C0ΣS_g`; проверено на устройстве — 0/64 расхождений,
  `u ∈ [26…228]`, цена +1 пакет на группу.
* 16-битный вариант точен, но стоит ×2 пакетов (32 нечётные строки → два
  прохода) и всё равно требует C0; зато позволяет зашить `S_g` в bias-слово
  и свести комбайн к сумме.
* Дополнительно найдены и объяснены три дефекта стенда: segfault host-проверки
  (`host.c:2382`, распаковка только 256 столбцов), отрицательный `pcyc`
  (переполнение `int` на 2.3-с комбайне) и потеря `m*64*N` в `blk_emit`
  при `mt>1`.

## 7. Наш порт (`dsp/hvx/prefill_impl.c`): что уже сходится

Замеры на том же телефоне, RPC `prefill` (Q4_K → int4 + масштабы → HMX).

1. **Адресация подтверждена**: после `voact = vbias + 2048u` смещение
   появилось, партиалы вышли из нуля (было «≈34», стало 109…255).
2. **Константный пакет на железе даёт `448·Aq`**, а не `224·Aq`: серия
   `q=7`, постоянная активация `c` даёт `u = (112c + 224) mod 256`
   (c = 0,1,2,4,8 → 224, 80, 192, 160, 96). Отсюда `Aq = C0/448`.
3. **Стор делит на 2**: при `q=7`, `c=10`, `C0=3136` восемь групп дают
   `u = 109` каждая, тогда как `(P + C0)·255/(2C0) = 218`. То есть
   `u = (P + C0)·m/2`, `m = 255/(2C0)`, и эмит должен быть
   `C = 2·ΣS·(u+0.5)/m − C0·ΣS`.
4. С этой поправкой форма результата совпадает с эталоном по модулю
   (`cos = 0.9656` на контрольной точке `q=7, c=10`), но **знак и
   константные члены ещё не сведены**: при случайных весах `cos ≈ 0.25`.
   То есть остаётся один систематический член (знак пакета/C0), а не
   семантика HMX.

Контрольная точка для следующего прогона: `q=7`, `A=10`, `G=1`, `K=256`,
`C0=33152` → `ref = −211456` на ячейку `(0,0)`; DSP отдаёт `+12480`
(после подстановки `u_avg=122` в формулу `2·Σu/m − C0·8 − 128·ΣS·Q`
получается `P_actual ≈ +26432`, т.е. знак `P` противоположен эталону).
Проверять гипотезу «HMX читает ниббл как −q» сменой упаковки (`(−q)&15`)
и повторной сверкой.

### 7.1. Последняя калибровка (продуктовая конфигурация)

- Пакет в нашем порте (одна 2 КБ активация + один 512-Б вес-кронтон,
  `wc=511`, 64 строки) даёт **448·Aq**, а не 224·Aq: при `q=0`, `A=10`,
  `Aq=2`, `C0=448`, `m=255/(2C0)` восемь групп дают `u=255` (сатурация),
  что соответствует `acc ≥ 2·C0`. В пробе `probe25.c` (две посылки, `K=64`,
  `wstep=512`) — 224·Aq. Разница конфигураций посылок, а не семантики.
- Поэтому в продуктовом пути `Aq = C0/448`, эмит `2·ΣS·(u+0.5)/m − C0·ΣS`.
  На контролируемом случае (`q=7`) это даёт `cos = 0.971` (знак и форма
  верны), на реальных весах — 0.29: расходится масштаб `P` между группами
  (в тесте `got ≈ 6 % от ref`).
- Следующий шаг для закрытия: считать `C0`/`Aq` не по выборке, а
  покадрово (по каждому 32-N тайлу), либо перенести в продукт
  probe-стиль посылки (одна активация + один вес на группу), где
  константа проверена с 0 расхождений.


### 7.2. Почему int4-prefill не сходится на знаковых активациях (замер, G=1..8)

Прогоны `prefill_test 64 32 256 G` на реальных весах при всех G дают одно и
то же: `cos ≈ −0.29`, `got ≈ −2340` при `ref ≈ −40`.

Причина не в HMX, а в **разрядности партиала**:

* активации сдвинуты на +128 (HMX `activation.ub` беззнаковый), поэтому
  `P_u = Σ A_u·q = 128·Q + P_s`, где полезная часть `P_s ≈ 40`, а
  `128·Q ≈ 3.5·10^5`;
* 8-битный партиал покрывает `P_u` в диапазоне `2·C0 ≈ 9·10^4`, то есть шаг
  квантования `≈ 350` на группу — **в 10 раз больше самого сигнала**;
* `128·Q` вычитается точно (f32, `hq`), но квантование уже потеряло `P_s`.

Вывод: int4 + 8-битные партиалы годятся только для *беззнаковых* активаций
(как SiLU-выходы в стенде, 0…255). Для знаковых int8 нужен либо точный
знаковый партиал (16-битный `.uh` на v68 зануляет отрицательные — REPORT25
§3), либо партиал без сдвига (т.е. знаковая активация в HMX, которой нет),
либо счёт частичных сумм на HVX вместо HMX.

Проверка, подтверждающая вывод: при `q=7` (все веса одного знака, `P_s`
сравним с `P_u`) тот же код даёт `cos = 0.971` — то есть арифметика верна,
ломается именно отношение сигнал/диапазон.

### 7.3. Рабочий int4-prefill в продукте (итог)

Два изменения довели путь до рабочего состояния:

1. **Zero-mean коды весов на группу** (`Σ_k q = 0`): сдвиг активаций на +128
   перестаёт давать член `128·Σq`, и 8-битный партиал несёт только полезный
   сигнал. Без этого `cos = 0.29` (сигнал в 10 раз меньше шага квантования),
   с ним — `cos = 0.99`.
2. **Пер-групповые `Aq` и bias**: пакет и bias-слово переписываются на каждой
   группе (`Aq_g = C0_g/448`, `bias_g = fp16(145.714/Aq_g)`), эмит
   `C = Σ_g S_g·Aq_g·(7.02745·(u+0.5) − 448)`.
   Плюс исправлен `blk_emit` при `mt = 2` (потеря `m·64·N`).

Замер на телефоне, `prefill_test 128 7680 2048 G` (Q4_K → int4, реальные
масштабы, 240 тайлов, 2 mt):

| G | cos vs точный целочисленный эталон | total | combine | copy |
|---|---|---|---|---|
| 2 | 0.994325 | 1328 мс | 1259 мс | 1.6 мс |
| 4 | **0.997533** | 670 мс | 634 мс | 1.6 мс |

HMX-часть — 670 − 634 − 2 ≈ **34 мс** на 128×7680×2048; всё остальное —
скалярный комбайн `pref_emit`. Он и есть следующий оптимизационный шаг
(HVX-векторизация, в стенде аналог даёт 2.2 мс на матрицу).

Замечание: абсолютный масштаб результата в тесте в ~2.2 раза больше эталона
(на cos не влияет); коэффициент формулы эмита требует финальной сверки.

### 7.4. Комбайн: что даёт перестройка и почему не HVX

- Комбайн переписан на непрерывные 128-элементные блоки (4 строки × 32 N),
  коэффициенты `S[n,g]·Aq_g` вынесены из внутреннего цикла, транспонирование
  4×32 — один раз на блок (`dsp/hvx/emit_impl.h`).
- Проверка на hexagon-sim (`dsp/hvx/emit_build.sh`): 0 расхождений с
  поэлементным эталоном, pcycles 247k против 290k у старого варианта (×1.17).
  Выигрыш в реальности ожидается больше: старый цикл делал 16 выборок `S`
  на каждый выход (это и давало 634 мс), новый — одну на группу.
- **Почему не настоящий HVX**: на v68 нет инструкций преобразования
  int→float (`Q6_Vsf_equals_Vw`, `Q6_Vqf32_*` доступны только с
  `__HVX_ARCH__ >= 73`). Автовекторизация clang для HVX не включается даже на
  простом `a[i] += b[i]*c[i]`. Значит комбайн надо писать в **фиксированной
  точке** (`vmpyacc` int16×int16→int32), а не на qf32 — это следующий шаг.
  Формула для фиксированной точки:
  `acc[n] = Σ_g round(S[n,g]·Aq_g·7.02745·2^8)·u_g + b[n]`, `C = acc >> 8`,
  `b[n] = -444.486·2^8·Σ_g S[n,g]·Aq_g`.
