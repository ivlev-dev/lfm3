# HMX-слой LFM3: int4 / int8 GEMM и prefill

Статус: хостовый слой собран и проверен; Hexagon-ветка реализована, но на
устройстве и в `hexagon-sim` не прогонялась (в окружении нет `hexagon-sim`;
`qemu-hexagon` есть, но HMX он не эмулирует).

## 1. Файлы

| файл | роль |
|---|---|
| `hmx_util.h` | VTCM, раскладки `weight.n` / `activation.ub` / `weight.b` / bias-блока, int32-аккумулятор, упаковщики, `#if __HEXAGON__` asm-путь |
| `hmx_ops.h` | публичный API и точные контракты входов |
| `hmx_impl.h` | внутренний интерфейс между `gemm_i4.c` и `prefill.c` |
| `gemm_i4.c` | `lfm_hmx_gemm_i4`: образ `common/q4.h` -> `weight.n` на лету |
| `gemm_i8.c` | точный int8-путь `lfm_hmx_gemm_i8` и int32-срез `lfm_hmx_gemm_i8_acc` |
| `prefill.c` | M-чанки 128/64/32, двойная буферизация весов DDR->VTCM, цикл по слоям |
| `gemm_main.c` | хостовые гейты: int8 `err=0`, int4 `cos >= 0.99`, prefill == gemm |
| `mx4.idl` | FastRPC: `init`, `load_buf`, `gemm_i4`, `gemm_i8`, `prefill`, `reset` |
| `mx4_impl.c` | DSP-скелет FastRPC поверх публичного API |
| `build.sh` | хостовый `cc`; при наличии SDK — `qaic` + `hexagon-clang -mv68 -mhmx` |
| `run.sh` | `./build.sh && ./gemm_test` |

## 2. Сборка и прогон

```
cd myelin/dsp/hmx
./build.sh
./gemm_test
```

`build.sh` по умолчанию: `cc -std=c11 -O2 -Wall -Wextra -ffp-contract=off
-fno-fast-math`. `-ffp-contract=off` обязателен: без него GCC/Clang может
слить `acc * scale` и `+=` в FMA и сломать побитовое сравнение int8-пути с
CPU-эталоном. `-ffast-math` нигде не используется.

Hexagon-сборка включается автоматически, если найден SDK
(`HEXAGON_SDK_ROOT` или `/opt/hexagon-sdk-6.7.0.0`):

```
HEXAGON_SDK_ROOT=/path/to/Hexagon_SDK/6.7.0.0 ./build.sh
```

На выходе `libmx4_skel.so` (v68, `-mhmx -mhvx`). В проверочном окружении SDK
6.7 найден: `qaic` сгенерировал `mx4.h` / `mx4_skel.c`, `hexagon-clang -mv68
-mhmx` собрал `libmx4_skel.so` без предупреждений. Исполнение HMX-инструкций
не проверялось: `hexagon-sim` отсутствует, `qemu-hexagon` HMX не эмулирует.

## 3. Раскладки

Все размеры — из `myelin/docs/hmx.md` (проверены на CDSP v68).

```
activation.ub, 2 КБ на 32 K:     addr(s,k) = 2048*(k>>5) + 128*(s>>2) + 4*(k&31) + (s&3)
weight.n int4, 512 Б на 32 K:    byte(k,n) = 512*(k>>5) + 128*((k&31)>>3) + 4*n + (k&3)
                                 ниббл: старший при ((k>>2)&1), иначе младший
weight.b int8, 1 КБ на 32 K:     byte(k,n) = 1024*(k>>5) + 128*((k&31)>>2) + 4*n + (k&3)
output 64 spatial x 32 N:        addr(s,n) = 128*(s>>2) + 4*n + (s&3)
```

`weight.n`: значение — 4-битный two's complement. В образе `common/q4.h`
ниббл хранится как `q+8`, поэтому упаковщик делает `v ^ 8` (для 4 бит
`(q+8) ^ 8 = q mod 16`).

Bias-блок — 256 Б, выровнен на 256 Б:

```
word0[0..31]  scale: fp16 в младших 16 битах, 0x6000 = 512.0 = тождество
              (у целочисленного конверта неявный множитель 1/512)
word1[0..31]  int32 input_bias; для zero-point: -128 * sum_k w[n][k]
```

Активации в `activation.ub` беззнаковые: `u = q + 128`, `q` — int8 из
`common/quant.h`. Компенсация `dot(w,q) = dot(w,u) - 128*sum(w)` уходит в
`input_bias`.

## 4. Контракты ядер

`lfm_hmx_gemm_i4(w, n, k, act, ascale, m, y)`:

* `w` — образ `common/q4.h` (`[f16 scales][pad 128][planes]`), строки уже
  повёрнуты `R = H128 D / sqrt(128)` (`lfm_q4_pack_matrix(..., rot=128)`);
* `act` — int8 `[m][k]`, повёрнут теми же блоками 128
  (`lfm_act_i8_rot(..., rot=128)`);
* `ascale` — `[m][k/32]`;
* `y` — f32 `[m][n]`.

`lfm_hmx_gemm_i8(w, wscale, n, k, act, ascale, m, y)`:

* `w` — int8 `[n][k]` row-major, повёрнут;
* `wscale` — `[n][k/32]`;
* `act`, `ascale`, `y` — как выше.

Оба ядра считают каждую группу 32 K в int32-аккумуляторе и комбинируют
результат в f32 в фиксированном порядке:

```
y[t][j] = sum_g ((float)acc[t][j][g] * wscale[j][g]) * ascale[t][g]
```

`g` возрастает, каждое умножение округляется до f32 до следующего. Для int8
это даёт побитовое (`err = 0`) совпадение с CPU-эталоном; `lfm_hmx_gemm_i8_acc`
дополнительно отдаёт точный int32-срез `sum_k w[j][k]*act[t][k]`.

`M` тайлится по 64 spatial (аппаратный `activation.ub` — 64 строки); 32/64/128
из контракта покрываются как 32, 64, 2x64. `K` обязан быть кратен 32.

## 5. Prefill

`lfm_hmx_prefill_i4`:

* M-чанки 128/64/32, внутри — 64-строчные HMX-тайлы;
* веса пакуются из DDR-образа в VTCM блоками по 8 кроутонов x 32 N x 512 Б
  = 128 КиБ, два чередующихся буфера (двойная буферизация);
* порядок «префетч следующего блока -> счёт текущего»;
* VTCM: 2 x 128 КиБ + 4 КиБ, аллокация через `lfm_hmx_vtcm_alloc`
  (host — `aligned_alloc(2048)`, Hexagon — HAP compute-res acquire с HMX);
* `lfm_hmx_prefill_layers` — цикл по слоям с общим VTCM.

Хостовый прогон доказывает, что prefill даёт побитово тот же результат, что
`lfm_hmx_gemm_i4` (копирование синхронное; перекрытие на хосте не моделируется).

## 6. Результаты хостовых гейтов

Условия: `M=32`, `K=2048`, `N=256`, гауссовы `W` и `X`, `rot=128`,
seed `0x9E3779B97F4A7C15`.

| проверка | результат |
|---|---|
| int4 cos против f64-оракула `W·X` | **0.995229245** (гейт 0.99) |

| int8 M=32 max_abs_err / int32_err | **0 / 0** |

## 7. Неопределённости и отличия от железа

1. **Аккумулятор int32 против `sat.ub`.** На v68 нет `cvt.*`; единственный
   путь acc->память — слитный `mxmem(...):after:sat.ub = acc` (u8). Поэтому
   «int32 накопление + f32 комбинация» — контракт эмулятора/эталона. На железе
   точность `err=0` достижима только в диапазоне 0..255 на выходе тайла; для
   широких dot-произведений нужен per-channel масштаб или разбиение, чего в
   этом слое нет. `sat.uh` (`u16`) как расширение не реализован.
2. **Округление конверта.** `lfm_hmx_store_u8` применяет
   `trunc((acc + input_bias) * scale/512)` и насыщение 0..255. Точное
   округление/насыщение v68 для нецелых `acc*scale` не проверялось; при
   `scale = 0x6000` (тождество) расхождения нет.
3. **Масштабы на группу 32.** У HMX один scale на 32 выходных канала, а
   контракт `q4`/int8 — scale на группу 32 K. Комбинация по группам сделана в
   f32 после точного int32-накопления. Аппаратный путь потребовал бы стора
   после каждого кроутона или свёртки масштабов; это не реализовано и не
   измерялось.
4. **Один pair на кроутон.** `lfm_hmx_tile_u8` под `__HEXAGON__` выдаёт по паре
   `activation.ub` + `weight.b/n` на кроутон с `act_rt=0x3FF`, `wc=511/1023`.
   `:deep`/`dC` не используются, поэтому поведение `dC` (для int8
   `кроутонов-1`, для fp16 `кроутонов`) в этом коде не задействовано и не
   перепроверялось.
5. **VTCM и адреса.** HW-функции требуют указателей в VTCM: bias — 256-Б
   выравнивание, store — 2 КиБ (иначе HMX молча пишет половину); проверок в
   `hmx_util.h` нет, это обязанность вызывающего. DDR-указатели в `mxmem`
   недопустимы.
6. **Стейджинг.** На хосте копирование DDR->VTCM — обычная упаковка в память,
   без DMA и без реального перекрытия. Замеров полосы нет; цифры `~5.3 ГБ/с`
   из `docs/hmx.md` здесь не воспроизводятся.
7. **Hexagon-ветка не исполнялась.** `hexagon-sim` в окружении отсутствует;
   `qemu-hexagon` не поддерживает HMX. Компиляция `libmx4_skel.so` через
   `hexagon-clang -mv68 -mhmx` и генерация IDL через `qaic` прошли, но HAP
   power/lock, `qurt_hmx_lock2`, `mxmem`/`mxmem2` и точное поведение VTCM на
   устройстве не проверены.
8. **FastRPC IDL.** `sequence<float>` для `ascale`/`wscale`/`y` поддержан
   `qaic` 6.7: сгенерированный `mx4.h` даёт `const float*`/`float*` и
   `int *Len`, сигнатуры совпадают с `mx4_impl.c`. Сквозной RPC на устройстве
   не измерялся.
9. **Rotation.** Ядро не проверяет и не применяет поворот: образ весов и
   активации обязаны быть повёрнуты одним и тем же `R`. Для `K`, не кратного
   128, `common/q4.h` оставляет хвост без поворота; `lfm_act_i8_rot` делает то
   же, поэтому контракт сохраняется, но гейт качества проверен только на
   `K=2048`.
10. **Производительность.** Не измерялась и не моделировалась. Ядра —
    функциональная эмуляция; `~5 TMAC/s`, `~19 тактов/кроутон` из
    `docs/hmx.md` к этому коду не относятся.
11. **M > 64 и N не кратное 32.** Поддерживаются тайлингом/частичным
    последним тайлом, но гейты прогонялись на `M=32/64/128`, `N=256`.
12. **int8-веса.** Формат `wscale[n][k/32]` выбран этим слоем; в `CONTRACT.md`
    отдельного образа int8-весов нет, поэтому при интеграции его надо
    согласовать с пакером.

