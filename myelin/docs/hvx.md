# HVX на Hexagon v68: внутренности и грабли

Практические заметки по HVX (128-байтные векторы) на CDSP v68 Snapdragon 888,
полученные на стендах `/tmp/opencode/gemv` и `/tmp/opencode/conv`. Источник
ISA — HVX PRM (см. [bibliography.md](bibliography.md)).

## 1. Контексты

* В user PD доступно **2 HVX-контекста**. Определяются так:

```c
int units = (int)((qurt_hvx_get_units() >> 8) & 0xFF);   /* = 2 */
```

* `qurt_hvx_reserve()` на этом стенде возвращает **−1** («резервировать нечего»),
  и попытка резерва, судя по поведению, ломает создание потоков. Рабочий путь —
  не резервировать, а брать контекст на время работы:

```c
qurt_hvx_lock(QURT_HVX_MODE_128B);
... HVX-код ...
qurt_hvx_unlock();
```

* **Нельзя держать контекст на протяжении жизни потока**: при контекстов
  меньше, чем потоков, остальные встают намертво. В `team_worker` лок берётся
  на каждую работу, а не на поток.
* Больше 2 одновременных контекстов на одном PD не будет: 4 и 8 потоков дают
  то же время, что 2 (упор в `hvx_units`). Масштабирование сверх 2 — только
  несколькими PD (процессами): 1 ctx 12.2 ГБ/с, 2 ctx 22.3, 4 PD 33.3 ГБ/с
  (измерено, `gemv/README.md`).

## 2. Потоки и стеки

`qurt_thread_create` возвращает **−1**, если entry-функция содержит HVX-код,
**пока не задан явный адрес стека**. Тривиальная entry (`sem_worker`) при этом
создаётся нормально. Проверено: размер стека 8…64 КБ, приоритет и
`qurt_hvx_reserve` на это не влияют.

Рабочий рецепт (как в `libs/worker_pool`):

```c
qurt_thread_attr_init(&attr);
qurt_thread_attr_set_name(&attr, "gemvhvx");
qurt_thread_attr_set_stack_addr(&attr, w->stack);   /* memalign, не NULL */
qurt_thread_attr_set_stack_size(&attr, 96 * 1024);
qurt_thread_attr_set_priority(&attr, qurt_thread_get_priority(qurt_thread_get_id()));
qurt_thread_create(&w->tid, &attr, team_worker, w);
```

* Стек выделяется заранее на каждого воркера (в рабочем варианте — 96 КБ;
  `worker_pool` использует 8…64 КБ). Размер стека 8…64 КБ на исход `−1` не
  влиял — важен был сам факт явного `stack_addr`, а не его размер.
* Приоритет берётся у вызывающего потока.
* Координация — `qurt_sem_t go/done`: главный поток будит воркеров, сам считает
  свою долю, затем ждёт `done`.
* Диапазоны строк делятся кратно 4 (M=1 GEMV), последняя доля забирает хвост.
* Счётчики производительности при многопоточности выключаются: воркеры не
  трогают общее изменяемое состояние (в `attn_group_tm` — 0 ссылок на `g_at`).

## 3. Полезные инструкции

| приём | что делает | где |
|---|---|---|
| `Q6_Vw_vrmpyacc_VwVubVb` | 32 lane × 4 байта: unsigned × signed, накопление в int32 | GEMV, conv, PV |
| `Q6_V_vsplat_R(0x0f0f0f0f)` + `vand` | младшие нибблы сразу в 4 байтах lane | int4 decode |
| `Q6_Vub_vlsr_VubR(v, 4)` | старшие нибблы (байтовый сдвиг) | int4 decode |
| `Q6_Vw_vadd_VwVw` + `Q6_V_vror_VR` | горизонтальная сумма: 64/32/16/8/4, затем `s[0]` | `vsum_w` |
| `Q6_l2fetch_AP` | префетч окна в L2 | GEMV, attention |
| `Q6_V_vzero` | нулевой аккумулятор | везде |

`vrmpyacc` — основной «кирпич»: 128 умножений-накоплений на инструкцию
(32 lane × 4 байта). int4 GEMV сознательно считает `unsigned × signed`, а
смещение −8 снимает скалярной коррекцией `−8·sum(a)`.

## 4. l2fetch

```c
static inline void pf_window(const void *p, int bytes) {
    uint64 ctl = ((uint64)128 << 32) | ((uint64)128 << 16) | (uint64)(bytes / 128);
    Q6_l2fetch_AP((Address)p, ctl);
}
```

* Окно — **8 КБ**, выдаётся каждые 8 строк (100 % покрытие тензора).
* Эффект на 7680×2048 int4: 3.08 мс → **0.71 мс** (2.55 → 11.0 ГБ/с) на одном
  контексте; с двумя — **22.7 ГБ/с** (347 мкс).
* Префетч — главный рычаг: без него ядро упирается в латентность DDR, а не в
  арифметику. Выигрыш от 2/4 строк за итерацию после prefetch — в пределах
  шума (0.63 мс).

## 5. Чего нет на v68

* **Нет векторного умножения 32×32 с 64-битным результатом.** `(a·b)>>16`
  приходится делать вручную:

```c
/* |a|,|b| < 2^23; ошибка <= 0.03 реальных единиц */
int32_t mulq16(int32_t a, int32_t b) {
    int32_t hi = a >> 16;
    uint32_t lo = ((uint32_t)a >> 8) & 0xFFu;
    return hi * b + (int32_t)(((uint32_t)lo * (uint32_t)b) >> 8);
}
```

* **Нет HVX-float и gather.** Поэтому SiLU/exp — только целочисленно, а
  выборка из таблицы — дерево константных выборок (`vshuffe/vshuffo` или
  сравнения), а не `vgather`.
* **Нет общего `vshuff`.** Есть только `Q6_Vh_vshuffe_VhVh` /
  `vshuffo`, чего не хватает для halfword-interleave при on-DSP расширении
  V из 2 бит. Отсюда V в тестах де-квантуется на хосте.
* `Q6_Vw_vmpyieacc_VwVwVuh` (упаковка int8) дал неверные lanes — упаковка
  выхода сделана скалярно.

## 6. exp

Два варианта, оба целочисленные, выход Q8 `[0,255]`:

* **bit-trick exp2** (по умолчанию): `y = x·log2(e)` в Q16, целая часть —
  сдвиг, дробная — 3-членный Горнер, затем переменный сдвиг. Mean|err| на
  `[-16,0]` — **8.1e-4**.
* **таблица 256·2^(f/256)** + сдвиг: mean|err| **1.7e-2**, обрезается ниже
  x = −6.5 (для сравнения, не как рабочий путь).

Оба варианта не требуют float и укладываются в int32; `mulq16` используется
вместо 64-битного умножения.

## 7. Грабли

1. **Выравнивание 128 Б.** Все буферы под `HVX_Vector` — `memalign(128, …)`.
   Невыровненное чтение через `*(const HVX_Vector*)p` даёт исключение или мусор.
2. **Страйды важнее объёма.** Раскладка «канал через 8 Б» (conv) и «2 spatial
   на 32-байтный блок» (HMX-активация) меняют не только скорость, но и
   корректность: ядро читает ровно те байты, которые ему разрешает геометрия.
3. **Маски little-endian.** `0x0f0f0f0f` — это младшие нибблы в каждом из
   4 байтов lane; `vlsr 4` — старшие. Перепутать порядок = получить нечётные
   k вместо чётных.
4. **Байтовый сдвиг vs словный.** `Q6_Vub_vlsr_VubR` сдвигает каждый байт;
   `Q6_Vw_vasl_VwR` — 32-битные слова. Для нибблов нужен первый.
5. **Дублирование значения в 2 байтах — не нужно.** Так упаковывали на старых
   int8-попытках HMX; рабочий int8-путь — байтовый (`activation.ub` /
   `weight.b` / `sat.ub`, один байт на элемент) — см. [hmx.md](hmx.md), §4.3.
6. **Скалярные хвосты.** `bx_write` (2048 итераций), `pack_out_i8`, `pack_y`
   оставлены скалярными осознанно: ~1 % слоя, векторизация не окупается.
7. **Стек воркера.** Без `stack_addr` поток с HVX не создаётся вообще (не
   «падает позже», а `rc = −1`).
