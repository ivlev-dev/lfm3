# Архитектура v2: ядра, KV, батчинг, мульти-PD

Рабочий документ Оркестратора. Фиксирует постановку и решения, по которым
пишется код. Детали — в контрактах:

| документ | что фиксирует | статус |
|---|---|---|
| `kernel-contract.md` | форматы весов/активаций, GEMV/FFN/attention по OpenCL-эталону | в работе |
| `kv-batch-contract.md` | paged KV, радикс, continuous batching, API батчера | в работе |
| `multipd-contract.md` | раскладка по PD, редукция, протокол, лимиты | в работе |
| `paged-kv.md` | предыдущий дизайн KV (не отменяется без явного расхождения) | действует |
| `decode-plan.md` | разложение 109 мс и приоритеты O1–O6 | действует |

## 1. Цель и порядок приоритетов

Цель: рабочий рантайм, который на одном запросе (decode) даёт максимум,
а на батче — пропускную способность.

Приоритет скорости: **25 tok/s → 20 → 18** (решение пользователя).
Ниже 18 не опускаемся: тогда считаем архитектуру неудачной и возвращаемся
к пересмотру.

## 2. Принятые допущения (до явного изменения)

1. **Формат хранения весов — собственный int4/32** (баг упаковки исправлен
   в `74238fc`, K=32…2048 сходится). Q4_K **окончательно отменён**
   (2026-11-23): остаёмся на int4/32, качество поднимаем не сменой формата,
   а блочными масштабами и **Hadamard-ротацией** (как в эталонных `q4`/`kvarn`:
   `R = (1/√128)·H·D`). int8/32 и int16 — опции для сравнения.
   *Следствие:* per-32 масштабы нужны и на HVX (дёшево, арифметика после
   int32-dot), и на HMX (партиалы; стоимость меряется в REPORT24).
   **Масштабы весов: блок 256 (G=8)** — решение 2026-11-23. Компромисс:
   51 % выгоды блока-32 за +13 % к prefill (cos 0.9919 против 0.9883 у
   per-row и 0.9953 у блока-32). Единый формат для HVX и HMX; откат на
   блок 128 (G=4), если текстовый гейт не пройдёт.
   Ротация: веса хранятся уже повёрнутыми (офлайн), активации поворачиваются
   на лету тем же `R`; для int4 это снижает ошибку на выбросах.
2. **Квантование активаций:** int8 по умолчанию, int16 — опция.
   На HMX целочисленного int16 нет (только `ub`, `hf`, `f8`), поэтому
   «int16 на HMX» = `activation.hf` (fp16). Целочисленный int16 — только HVX.
3. **KV:** `k4v2` — дефолт (требование пользователя), `k4v4` и `k8v8`
   переключаемые. `k8v8`/без квантования обязательны как эталон качества.
4. **PD:** целевые 4, проверяем 6/8. Если 6/8 недоступны — остаёмся на 4.
5. **Батчинг:** M до 64 (spatial HMX). При M≥32 int4-HMX становится
   основным движком; при M=1 — HVX.
6. **Совместимость:** всё, что делает эталон `backend-opencl`, должно
   воспроизводиться нашими ядрами бит-в-бит (или с документированным
   допуском по int32-аккумулятору).

## 3. Гейты (без них шаг не считается сделанным)

| гейт | критерий | где |
|---|---|---|
| G1 бит-в-бит | ядро против CPU-эталона, `maxerr=0` на int32 | `dsp/*/sim` |
| G2 текст | жадный пробник даёт `4741` (« Paris») на эталонном префиксе | телефон |
| G3 качество | `quality_probe` cos ≥ эталона OpenCL на тех же весах | телефон |
| G4 скорость | мкс/токен и tok/s, медиана ≥20 прогонов | телефон |
| G5 регресс | один скрипт прогоняет все стенды, PASS | локально |

Правило: гейт G1 обязателен до интеграции; G2–G3 — до объявления шага
готовым; G4 — до перехода к следующей оптимизации.

## 4. Фазы

**Ф0. Контракты** (идёт). Три агента, три документа. Код не пишется.
Выход: согласованные `kernel-contract.md`, `kv-batch-contract.md`,
`multipd-contract.md`. Оркестратор сводит расхождения.

**Ф1. Ядра.** Четыре потока с владением файлами:
- HVX GEMV/FFN: w4a8, w8a8, int16 — владелец `dsp/hvx/*`;
- HMX prefill/батч: int4×int8, per-32 масштабы — владелец `dsp/hmx/*`;
- paged attention (k4v2/k4v4/k8v8, varlen) — новый `dsp/attn/*`;
- квант/деквант, масштабы — новый `dsp/quant/*` (общий, владелец один).

**Ф2. Интеграция.** Один `exec` на слой (O5 из `decode-plan.md`),
радикс на хосте, планировщик батчей, редукция по PD.

**Ф3. Симулятор.** Прогон всех ядер и exec-протокола на срезах реального
слоя; регресс одним скриптом. Полную модель в симуляторе не гоняем:
880 МБ/токен и 27 слоёв делают это бессмысленно медленным.

**Ф4. Телефон, один прогон.** Полная модель, замеры prefill/decode,
G2–G4. Дальше — только точечные итерации по результатам.

**Ф5. FFI, сервер, TUI, APK.** UniFFI, сервер, TUI, сборка APK, установка
и тест на устройстве.

## 5. Владение файлами (во избежание конфликтов)

| область | владелец на время фазы |
|---|---|
| `dsp/hvx/*` | поток HVX |
| `dsp/hmx/*` | поток HMX |
| `dsp/attn/*` | поток attention |
| `dsp/quant/*` | один владелец, изменения только через него |
| `crates/myelin-npu/*` | интегратор |
| `crates/myelin-core/src/backend/dsp.rs` | интегратор |
| `docs/*` | Оркестратор |

Общие файлы (`method.rs`, `executor.rs`, `lfmgemv.idl`) меняет только
интегратор, после согласования контракта.

## 6. Не-цели

- Полный forward модели в симуляторе (только срезы).
- GPU/OpenCL в продукте (эталон остаётся эталоном).
- QNN в продукте.
- Оптимизация качества текста beyond исправления блочных масштабов —
  отдельная задача после скорости.
