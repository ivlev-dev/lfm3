# HMX на Hexagon v68: рабочая спецификация

**Статус: работает.** На CDSP v68 (Snapdragon 888) заведены оба пути — fp16
(через SDK-путь `qhl_hmx`) и int8 (по рецепту, снятому с дизассемблера QNN
и проверенному на устройстве). int8 считается **побитово** (`err = 0`,
`cos = 1.0`), fp16 — с точностью fp16 (`cos = 1.000000`, `err ≤ 0.0075`).

Это заменяет прежний вердикт «HMX на v68 не заводится» (REPORT17/FINAL6):
он был получен на неверной раскладке кроутона и без bias-блока, разбор — в
разделе 7.

Важная оговорка: сам матричный блок работает и считает быстро, но сквозной
prefill упирается в доставку весов из DDR — **~3190 мкс** против 2.44 мс у QNN
(§9.1), т.е. **в 1.31 раза медленнее**, а не втрое. «×3.1 быстрее QNN» из
REPORT18 относится к compute-only числу и некорректен; «7319 мкс» из REPORT19
тоже неверны — в цикл замера входил `copycheck` (~4.2 мс), см. REPORT20 §1.3.

Условия всех замеров: XQ-BC72 (SD888, CDSP v68), unsigned PD
`fastrpc_shell_unsigned_3`, VTCM 4 МБ, стенд `/tmp/opencode/hmx4`
(`REPORT18.md`, `REPORT19.md`, `REPORT20.md`, 22.11.2026). Клок CDSP измерен там
же: **1132–1421 pcycles/µs (1.13–1.42 ГГц, DVFS гуляет)**; в прогонах с
голосованием за шину падал до 375 pcycles/µs.

## 2. Минимальное состояние: power + lock

Рабочая последовательность (проверена):

```c
/* упаковка тайлов — HVX, HMX не нужен */
qurt_hvx_lock(QURT_HVX_MODE_128B);
transfer_row(...); transfer_column(...);
qurt_hvx_unlock();

/* ОБЯЗАТЕЛЬНО до первой HMX-инструкции */
HAP_power_request_t req = {0};
req.type          = HAP_power_set_HMX;
req.hmx.power_up  = TRUE;
HAP_power_set(0, &req);                   /* так в стенде: handle = 0 */

qurt_hmx_lock2(QURT_HMX_SHARED_LOCK);    /* ОБЯЗАТЕЛЬНО (или compute_resource_hmx_lock) */
... mxclracc / mxmem-пары / store ...
qurt_hmx_unlock2(QURT_HMX_SHARED_LOCK);

req.hmx.power_up = FALSE;
HAP_power_set(0, &req);
```

Что обязательно, а что нет (по одному варианту за раз):

| вариант | вердикт |
|---|---|
| `HAP_power_set` с `type = HAP_power_set_HMX`, `power_up = TRUE` | **обязателен**. Без него — precise exception в HMX-инструкции, падение PD, дальше **CDSP SSR** (`ssr(cdsp)`: подсистема перезагружается, телефон целиком не ребутится). Проверено один раз, повторять не нужно |
| HMX-lock (`qurt_hmx_lock2(QURT_HMX_SHARED_LOCK)` или `compute_resource_hmx_lock`) | **обязателен**: без него — precise exception в момент HMX-инструкции. Оба варианта эквивалентны |
| `mxclracc` перед парой | **не обязателен**: store `:after` сам очищает acc (reps=3 без `mxclracc` даёт 1×, не 3×) |
| `qurt_hvx_lock` вокруг упаковки | формально не обязателен в этом PD (`mode=8` без него корректен), оставлен |
| HVX-lock на время HMX-инструкций | **не нужен** (`mode=64` корректен) |
| bias-загрузка (fp16) | fp16-путь её не использует; на v68 `bias` нужен только int8 (§4.4) |

Замечание про историю: в ранних сериях отсутствие питания выглядело как
«store никогда не завершается» → watchdog → SSR. Наблюдаемый механизм по
REPORT18 — precise exception, но исход один: без `HAP_power_set` PD не живёт.
Ни `compute_resource_attr_set_hmx_param`, ни `HAP_compute_res_acquire`, ни
`compute_resource_hmx_lock` питание не включают.

## 3. fp16

### 3.1. Паттерн (ровно как в SDK, ветка `__HEXAGON_ARCH__ < 73`)

`$SDK/libs/qhl_hmx/src/qhblas_hmx/qhblas_hmx_matrix_matrix_mpy_hf_sm.S`:

```
{ activation.hf = mxmem(R0,R1):deep;   // :deep СТОИТ НА АКТИВАЦИИ
  weight.hf     = mxmem(R2,R3); }      // на весах :deep нет
{ mxmem(R4,R5):after.hf = acc; }       // store, R5 = 0
```

### 3.2. Control-слова

`ncr = K >> 5` — число 2-КБ кроутонов (по 32 канала K в каждом):

```
act_rt   = (ncr << 11) | 0x7C     // K=32 -> 0x0087C, K=256 -> 0x0407C
wgt_rt   = (ncr << 11) - 1        // = nbytes-1: 0x7FF … 0x3FFF
store_rt = 0
```

`dC` для fp16 (поле в битах ≥11) = **число кроутонов**, т.е. `ncr`, а не
`ncr-1`: `act_rt = (ncr<<11)|0x7C` даёт точный результат при `ncr = 1…8`
(девятый кроутон не читается). Это расходится с PRM и с комментарием в SDK —
приоритет у эмпирики (см. §6).

### 3.3. Раскладки

Элементные индексы fp16, байты = индекс × 2. Проверено `refdump`: 0
несовпадений на 1024/2048/4096/8192 элементах.

```
activation 32×K:  elem(s,k) = 1024*(k>>5) + 64*(s>>1) + 2*(k&31) + (s&1)
weight     K×N:   elem(k,n) = 1024*(k>>5) + 64*((k&31)>>1) + 2*n + ((k&31)&1)
                  (N=32 — один тайл; N=64 — второй блок столбцов по
                   смещению +4096 элементов = +8192 байт)
output     32×32: 16 HVX-векторов row-major, как отдаёт mpy_ahf
```

В байтах та же активация: `2048*(k>>5) + 128*(s>>1) + 4*(k&31) + 2*(s&1)`,
т.е. на 128-байтный вектор — 2 spatial и 32 канала с шагом 4 Б.

### 3.4. Замеры (reps=200, один процесс, mode=0)

| K | N | max_abs_err | cos | bad | pcyc/вызов | мкс |
|---|---|---|---|---|---|---|
| 32 | 32 | 0.00191 | 1.000000 | 0/1024 | 361 | 0.32 |
| 32 | 64 | 0.00195 | 1.000000 | 0/2048 | 367 | 0.32 |
| 64 | 32 | 0.00225 | 1.000000 | 0/1024 | 394 | 0.35 |
| 64 | 64 | 0.00389 | 1.000000 | 0/2048 | 398 | 0.35 |
| 128 | 32 | 0.00375 | 1.000000 | 0/1024 | 485 | 0.43 |
| 128 | 64 | 0.00390 | 1.000000 | 0/2048 | 523 | 0.46 |
| 256 | 32 | 0.00567 | 1.000000 | 0/1024 | 656 | 0.58 |
| 256 | 64 | 0.00462 | 1.000000 | 0/2048 | 736 | 0.65 |

Расчёт по этой таблице: K=256/N=32 — 262 144 MAC за 656 тактов ≈ 400
MAC/такт ≈ **0.45 TMAC/s**. Для сравнения, int8 на своём тайле даёт
1.95 TMAC/s полезных (§4.7): fp16-путь на v68 медленнее и требует вдвое
больше байт на элемент.

Известный край: `A=2.0, B=I` даёт во всех ячейках `1.999` — систематический
−1 ulp при конверте. Для целочисленных значений это надо учитывать (история:
REPORT7/FINAL6, снято вместе с раскладками).

## 4. int8

Рецепт снят с дизассемблера QNN (`hmx_convbbb1x1_stride1`, `0x36fdc0`) и
проверен на устройстве побитово.

### 4.1. Паттерн

```
mxclracc                                        ; целочисленный acc (без .hf)
for each chunk:
    activation.ub = mxmem(act, act_rt):deep     ; deep по K; либо просто пара
    weight.b      = mxmem(wgt, wgt_rt)
bias = mxmem2(bias_ptr)                          ; 256 Б на 32 канала
mxmem(out, 0):after:sat.ub = acc                 ; 2 КБ = 64 spatial × 32 N
```

### 4.2. Control-слова

Значения, которые заработали на устройстве:

```
act_rt  = 0x3FF   (dC=0, ch_stop=31)   ; 0x07C и 0x77C на 32 каналах дают тот же результат
wgt_rt  = 1023    (1 КБ-1)             ; N=64 weight.b:deep -> 2047 (2 КБ)
store   = mxmem(...):after:sat.ub = acc, Rt = 0
bias    = scale = 0x6000 (fp16 512.0) в младших словах -> множитель 1.0
```

Для накопления по K одной инструкцией `dC` кладётся в биты ≥11 поверх
младших 11 бит базового `art = 0x3FF` — так это делает стенд
(`act_rt = (dC << 11) | (art & 0x7FF)` в `mx4_impl.c`, `i8_core`). Литерала
`(dC<<11)|0x3FF` в REPORT18 нет: это композиция полей, а не снятое значение.
Проверено на устройстве следствие — `dC=31` даёт точный результат,
`dC=30` теряет хвостовые каналы, `dC=32` тоже точен (§4.5).

### 4.3. Раскладки

Проверено побитово (`err = 0`), 1 байт на элемент:

```
activation 64 spatial × 32 K (2 КБ):  addr(s,k) = (s>>2)*128 + 4*k + (s&3)
   (наш случай — 32 spatial: заполняем s=0..31, верхняя 1 КБ остаётся нулевой)
weight     32 K × 32 N (1 КБ):        addr(k,n) = (k>>2)*128 + 4*n + (k&3)
   N=64, weight.b:deep (2 КБ):        + 1024*(n>>5)
output     64 spatial × 32 N (2 КБ):  addr(s,n) = (s>>2)*128 + 4*n + (s&3)
   N=64: второй тайл по +2048, bias перезагрузить (+0x100)
```

`activation.ub` — unsigned u8, `weight.b` — signed int8, выход `sat.ub` —
saturating u8. Никакого «значение в оба байта» (это артефакт прежних
int8-попыток с 16-битными ячейками): int8-кроутон — байтовый.

### 4.4. Bias/scale — обязателен

```
uint32 word0[ch] = 0x6000;   /* scale = fp16 512.0 -> тождество (неявный 1/512) */
uint32 word1[ch] = 0;
/* 32 низких слова (128 Б), затем 128 Б высоких слов: всего 256 Б на 32 канала */
```

Без загрузки bias **store пишет нули** (scale = 0). `scale = 0x3C00`
(1.0 как обычный fp16) тоже даёт нули — нужен именно `0x6000`: у
целочисленного конверта неявный множитель 1/512, реальный коэффициент
квантования надо домножать на 512. Это же место — для zero-point
(`input_bias = -zp*sum(w)` на канал, PRM §2.3.1).

### 4.5. Накопление по K и `dC`

| способ | вердикт |
|---|---|
| `ncr` пар `(act+2048, wgt+1024)` до одного store | побитово верно для K=64/128/256 (err=0) |
| `activation.ub:deep` с `dC = (#кроутонов - 1) ≤ 31` | верно, K ≤ 1024 на инструкцию; по времени то же самое (~19 тактов на кроутон) |
| K=2048 | два `:deep` по `dC=31` |

Семантика `dC` проверена отдельно (K=1024, 32 кроутона): `dC=31` — точно
(err=0), `dC=30` — err 3.0 / cos 0.9927 (теряются последние 32 канала),
`dC=32` — тоже точно. Т.е. **int8: `dC = кроутонов-1`** (плюс один
допускается). У fp16 наоборот, `dC = кроутонов` (§3.2) — не переносить одно
на другое.

### 4.7. Темп

**19 тактов на кроутон** (65536 MAC) — это ~3.9 TMAC/s «сырых». Полезных при
32 spatial — 1.95 TMAC/s: массив 64-wide, заполнена половина. При N=64
(второй банк аккумулятора через `weight.b:deep`) — 2.60 TMAC/s. При M=64
(заполнены все 64 spatial) — **3.50 TMAC/s** на N=32 и **4.42 TMAC/s** на N=64
(REPORT19). Это потолок одного ядра; сквозной prefill упирается не в него, а в
доставку весов — см. §9.1.

### 4.8 int4 (`weight.n`): раскладка найдена, 32×32 работает

Раскладка снята импульсной пробой (`mx4_i4map`: один ниббл в байте `b`,
`A[s][k]=k+1`, отклик по столбцам/строкам):

```
byte(k,n) = 128*(k>>3) + 4*n + (k&3)          (0..511)
nibble    = high, если ((k>>2)&1), иначе low
```

То есть на 128-байтный вектор — 8 ic (k-блок), как в PRM. Формула из брифинга
`(k>>3)*128 + 4*n + (k&7)` **неверна** (даёт 515 байт на тайл). Проверка:
одиночный ниббл откликается ровно в одном столбце `n = (b>>2)&31`.

| параметр | значение | как проверено |
|---|---|---|
| значение | **4-бит two's complement** (−8…7) | `A=1`: `v=1..3` → 1..3, `v=8..15` → ≤0 (сатурация в 0); `1+(−1)→0`, `1+(−8)→0` |
| масштаб | **`0x6000` (=512.0)**, множитель = `bs/512` | свип `bs`: 0x5C00 и ниже → 0; 0x6000 → ×1; 0x6400 → ×2 … 0x7000 → ×16 |
| `Rt` | **511** (на один 32 K × 32 N кроутон) | 1023/2047/4095 результат не меняют |
| вес | **512 Б** против 1 КБ у int8 (вдвое компактнее) | — |

Сходимость (`mx4_test i4 32 32 K 4 0x6000 …`, `wl=4` — новая раскладка):
K=32, все 1; K=32, W∈−8..7/A∈0..3; K=32, W=±7 — во всех случаях `err=0`,
`cos=1.0000000`, 0/1024 bad. Время: **0.026 мкс** на 32×32×32 (29 pcyc) →
**1.28 TMAC/s** против 0.028 мкс / 1.16 TMAC/s у int8 на том же тайле.

**Не закрыто: K>32.** Из `ncr` кроутонов суммируются только первые
`ceil(ncr/2)`: при `A=W=1` выход 32 (K=32), 32 (K=64), 64 (K=96), 64 (K=128),
96 (K=160), 128 (K=256) вместо 32/64/96/128/160/256. Проверено, что это не
адресация: шаг веса 512/1024/2048 Б, `:deep` на весе и/или активации, второй
store (`vout+2048`), `Rt` 511…8191, сдвиг активации 0/1024/2048 — без
изменений. Проба «только кроутон 1» даёт 0, «только кроутон 0» — 32: пары с
нечётным индексом не доходят до аккумулятора. int8-путь на 64 парах при этом
работает (REPORT18). Дальше — реверс QNN-ядра `hnh` (`Rt=0x1FF`, возможно
другой режим) либо отказ от int4 при K>32.

непригоден без реверса режима `hnh`.

## 6. Чем v68 отличается от v73+

PRM 80-N2040-62 Rev AA описывает V81; на v68 часть путей отсутствует. Что важно
для кода:

1. **Нет `cvt.*`** (`cvt.hf = acc`, `cvt.ub = acc`, `mxmem = cvt`): ассемблер
   отвечает «instruction requires: -mv73 or higher». На v68 есть только
   слитный `mxmem(...):after.<fmt> = acc` — конверт и store одной инструкцией.
   Подтверждено и в LLVM (кодировки `cvt`/`mxmem=cvt` помечены `Requires HasV73`).
2. **Нет `:2x2`** (`sat.uh = acc:2x2`): «requires -mv69».
3. **Нет `weight.c`**: в v68-скелете QNN 0 сигнатур с `c`; 2-битный вес
   появляется только в v81 (`hmx_v81_convhch…`). Имена (`n` = nibble,
   `c` = crumb) намекают, что `c` = 2 бита, но это гипотеза.
4. **`dC` считается по-разному**: fp16 — `dC = кроутонов` (`ncr<<11`),
   int8 — `dC = кроутонов-1` (§3.2, §4.5). Одно правило на оба типа не
   переносится; проверять на своём типе.
5. **int8-deep в v68-скелете QNN — заглушки**: `hmx_v73_convbbb1x1deep_stride1`
   (`0x370300`) = `r0 = #-1; jumpr r31`. Deep для int8 у QNN есть только в
   `hbh`/`hnh` (16-битный выход). Это ограничение **скелета QNN, а не
   железа**: `activation.ub:deep` с `dC = кроутонов-1` на v68 даёт `err = 0`
   (§4.5).
6. **QNN в int8 ходит через `:cm`** (`activation.ub:cm`, `Crouton_8` =
   `s*32 + k`). Обычный `activation.ub` — другая раскладка
   (`(s>>2)*128 + 4*k + (s&3)`), и именно она нам нужна для плоского GEMM.
7. **`sat.ub` без bias-блока пишет нули** — на v73+ это не так заметно,
   потому что bias приходит из графа; на v68 без явной загрузки 256 Б
   выхода не будет вообще (§4.4).

## 7. Почему прежний вердикт «не заводится» был неверен

Прежняя серия (REPORT1–17, FINAL6) закрылась выводом «HMX на v68 не готов,
R&D» и «накопление >16 каналов не работает». Причины ошибки:

1. **Неверная формула раскладки активации.** Формула из брифинга
   `(s>>1)*128 + (s&1)*64 + (c>>4)*32 + (c&15)*2` тождественно равна
   `64*s + 2*c`, т.е. плоскому row-major — а не HMX-раскладке; совпадений
   32/1024. Стендовая `(s>>1)*128 + c*4 + (s&1)*2` верна только для `c < 16`.
   Отсюда «потолок 16/24 канала» (REPORT17: 24 = 16+8) — артефакт упаковки,
   а не геометрия кристалла. Верная формула — §3.3/§4.3.
2. **int8 без bias/scale-блока.** `scale = 0` → `sat.ub` пишет нули. В
   прежней серии из этого сделали вывод «`sat.ub` не работает / нужны
   16-битные ячейки», и int8 гоняли через `sat.uh` с дублированием байта.
   С `scale = 0x6000` работает штатный байтовый путь.
3. **«MAC = 16»** — неверная интерпретация. Одна int8-пара на v68 — это
   **64 spatial × 32 N × 32 K = 65536 MAC**. Число «16» и формула
   `MAC = (stop+1)/2` (REPORT17) — вывод из неверной 16-канальной упаковки;
   что именно там суммировалось, отчёты не фиксируют. Отсюда же попытки
   «добить 32 канала» через `mxswapacc` и второй plain-pair.
4. **`:deep` «не суммирует»** — проверялся на split-кроутонах
   (`1024*(c>>4) + …`, два килобайта на 16 каналов), которых HMX в таком
   виде не читает, плюс с `dC = ncr-1` для fp16. Итог FINAL6 («суммируются
   только 16 из 32 k») — следствие раскладки, а не deep.
5. **`transfer_column` при `N <= 32`** пакует `K*2` элементов вместо `K*32`
   (ветка `row_iters = K>>5` в SDK) → вес мусорный, cos=0.145. Это читалось
   как «раскладка веса не та».
6. **`l2fetch` за буфером** в том же сэмпле роняет PD по TLBMISS; падение
   списывалось на HMX. Отдельно: в этом unsigned PD `l2fetch` как префетч в L2
   **не работает** — 5 экспериментов, эффект 0 (REPORT20 §1.2); на него больше
   не рассчитываем.
7. **`pcycles` не тикает, пока ядро ждёт HMX**: одиночный замер давал 170
   тактов на K=2048 вместо честных 1217 в цикле — отсюда заниженные оценки
   и ощущение «не масштабируется».

Общий вывод: железо работало всё время; не работала упаковка (п.1, 5) и
конверт (п.2). Ни один из «структурных» барьеров (16 каналов, отсутствие
накопления, `sat.ub`) не подтвердился.

## 8. Грабли

1. **Раскладка кроутона — единственный источник «потолка 16/24 канала».**
   Любая формула, которая для `c ≥ 16` уводит адрес за 128-байтную линию,
   даёт ровно 16 верных каналов. Проверять картой входов
   (`A[s][c]=s+c/32, B=I`), а не на «правдоподобных» числах.
2. **Без bias-блока int8-выход нулевой.** `scale = 0x6000`, не `0x3C00`;
   блок 256 Б на 32 канала, младшие слова первыми, адрес выровнен на 256 Б,
   младшие 2 бита адреса — номер set'а (у нас 0).
3. **`qhblas_hmx_transfer_column_ahf` при `N ≤ 32` пакует 1/16 веса**
   (`K*2` элементов вместо `K*32`). Рабочий путь — всегда паковать N=64
   (или писать свою упаковку).
4. **`Q6_l2fetch_AP` в `transfer_row/column` игнорирует реальный шаг строки**:
   для K=224/256 префетч уходит ~7 КБ за конец буфера. Если буфер кончается
   на границе страницы — **TLBMISS и падение PD** (`Bad VA = конец .bss +
   0x1000`). Лечится guard-хвостом 64 КБ.
5. **`pcycles` не тикает во время ожидания HMX.** Мерить только в цикле
   (reps ≥ 200), иначе получите заниженное время в разы.
6. **M=1 на HMX невыгоден**: тайл — 32 spatial (fp16) / 64 (int8), при
   декоде заполнена 1 строка, остальные 31/63 простаивают; плюс вес надо
   тянуть из DDR на каждый токен. Декод — на HVX (§9).
7. **Power on/off на RPC стоит ~70 мс.** Держать питание включённым на весь
   вызов, а не включать/гасить вокруг каждой матрицы.
8. **Адреса — только MMU/VTCM.** Передача смещений вместо адресов даёт
   `AEE_EBADPERMS` (78); DDR-указатели в `mxmem` невозможны; `mxmem2` (bias)
   требует 256-Б выравнивания.
9. **Адрес store аккумулятора обязан быть выровнен на 2 КБ.** При указателе
   со смещением +1 КБ HMX молча пишет только первую 1 КБ — 32 spatial-строки
   из 64, без ошибки и без исключения. В стенде до REPORT19 выход для K=32
   лежал по `base+3072`, поэтому «тайл 2 КБ = 64 spatial × 32 N» фактически
   проверен не был. Выравнивать `vout` вверх до 2 КБ и проверять заполнением
   **обеих** половин (`i8ramp` → `bad=0/64`).

## 9. Использование в Myelin

| фаза | движок | почему |
|---|---|---|
| prefill (M=128) | **HMX** | compute-only 376.8 мкс на 128×7680×2048 (5.34 TMAC/s) — быстрее QNN по арифметике; со стейджингом весов **~3190 мкс**, т.е. **1.31× медленнее** QNN (2.44 мс); узкое место — копирование весов, не HMX (§9.1) |
| decode (M=1) | **HVX** (int4 GEMV) | тайл HMX на 32/64 spatial при одной строке простаивает; декод упирается в DDR, а не в арифметику, и HVX уже даёт 45 GMAC/s / 22.7 ГБ/с на двух контекстах |

ADR-010 (prefill — HMX, decode — HVX) остаётся в силе, но обоснование
уточнено: HMX выигрывает по compute, а не по доставке весов. Для одиночного
decode 15.7 МБ весов на токен читаются из DDR на каждый токен — дороже, чем
HVX-путь с резидентными int4-весами. Прежний аргумент «потолок DDR 4.29 ГБ/с,
пол 3.65 мс» **неверен**: полоса чтения масштабируется потоками (§9.1), а
дорогая операция — копирование в VTCM.

Практическая форма prefill (REPORT19 §2, пересчитано в REPORT20 §1.3):
настоящий цикл по форме FFN, M строк × N%64 × K%32, веса пакуются в раскладку
HMX заранее и лежат в DDR. Замеры для M=128, N=7680, K=2048 (REPORT20):

| вариант | мкс | что входит |
|---|---|---|
| только HMX-поток, веса резидентно в VTCM | **376.8** (376.4–377.2) | пары + bias + store; перекладка вне замера |
| только стейджинг 15.7 МБ DDR→VTCM | **2918–2966** | **5.3–5.4 ГБ/с**; 120 × 128 КБ копий, HVX 128 Б |
| стейджинг + вычисление, последовательно | **3180–3219** | то же плюс 0.38 мс счёта |
| стейджинг (двойная буферизация) + счёт | 3189–3195 | перекрытие даёт ~1 % |
| ~~7319~~ | **было/неверно** | в цикл входил `copycheck` ~4.2 мс (REPORT20 §1.3) |

Сходимость полной формы со стейджингом: 983 040 ячеек, `maxerr=0`,
`cos=1.0000000`. Время упаковки весов в кроутоны делается один раз до
таймера и ни в одну из цифр не входит.

### 9.1. Где узкое место

**«Потолок 4.29 ГБ/с» — артефакт одного последовательного потока, а не
железа.** Полоса чтения DDR масштабируется числом потоков: 1 → **5.84**,
2 → **11.32**, 4 → **21.30**, 8 → **38.68 ГБ/с** (12 МБ, `mx4_bwt`, турнир 18
способов в одном процессе; REPORT20 §1.2).

Узкое место prefill — **копирование DDR→VTCM**, и оно **не масштабируется**:
любая схема (2 КБ кроутоны, блоки 128 КБ, 2/4/8 потоков, `l2fetch`, два
прохода) даёт **3.3–6.0 ГБ/с**. Копия из L2 в VTCM — **55 ГБ/с**, т.е. запись
в VTCM не виновата: тормозит связка «загрузка из DDR → зависимая запись»
(каждая запись держит store-buffer на всё время латентности DDR). Наш честный
стейджинг — 5.35 ГБ/с.

`l2fetch` в этом unsigned PD **не работает**: после `l2fetch` + `syncht`
чтение идёт с той же скоростью, что холодное (28.49 vs 28.49 ГБ/с на 512 КБ;
19.78 vs 19.64 на 1 МБ; 14.14 vs 15.35 на 2 МБ); 5 независимых экспериментов,
эффект 0. Голосование за шину (`HAP_power_set_mips_bw`, `HAP_power_set_DCVS_v3`
+ TURBO) полосу не поднимает (4.62 → 4.74 → 3.41 ГБ/с), зато роняет клок ядра
(1133 → 375 pcycles/µs).

QNN укладывается в 2.44 мс, значит ему нужно **~6.4 ГБ/с**. Это на грани: наш
лучший кратковременный замер копии — 6.5 ГБ/с, устойчивый — 4.5–6.0. Разница с
QNN — **1.31×** и это ровно разница скоростей копирования, **а не матричного
блока** (по compute HMX быстрее). Гипотеза «QNN держит веса резидентными»
невозможна: 15.7 МБ > 4 МБ VTCM, а кэш context binary — это DDR.

Следующие шаги: zero-copy весов из ION (`attach_out` в стенде уже работает),
крупные блоки ≥4 МиБ, DMA `dmstart` (дескриптор не документирован в SDK, не
проверялся) и перекрытие копии со счётом.
