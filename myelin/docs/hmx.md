# HMX на Hexagon v68: внутренности и статус

HMX — матричный сопроцессор Hexagon (целочисленный и fp16). На v68 доступен,
но документация (PRM 80-N2040-62) написана для **v73**, и часть путей на v68
отсутствует. Ниже — то, что снято экспериментально на стенде
`/tmp/opencode/hmx4` (22.11.2026), с честным статусом: **int8- и fp16-S1 не
закрыты, HMX в R&D**.

Условия: Snapdragon 888, CDSP v68, unsigned PD, VTCM 4 МБ. Каждый вызов
включает и гасит HMX, поэтому RPC с power on/off стоит ~70 мс; для реального
замера питание держат включённым на весь вызов.

## 1. Питание: без него DSP уходит в SSR

`compute_resource_attr_set_hmx_param(...)` + `HAP_compute_res_acquire` +
`compute_resource_hmx_lock` **не включают HMX**. Это подтверждено кодом QNN для
того же чипа: `nn_os_hmx_power_on()` дергает
`HAP_power_set(HAP_power_set_HMX, { power_up = TRUE })` и только потом
`os_hmx_lock()`.

Поведение без питания (воспроизведено):

| инструкция | результат без power-on |
|---|---|
| `mxclracc` | «проходит» (регистровая операция) |
| `bias = mxmem2(vtcm)` | проходит, но данные недостоверны |
| `mxmem(...):after:sat.ub = acc` | **никогда не завершается** → поток CDSP висит → watchdog → SSR/ребут |

Отсюда исходный «краш на первом GEMM»: дело не в раскладке тайлов, а в том,
что transfer `acc → VTCM` не ретирится.

Рабочий порядок:

```c
res_get(need, &r);
hmx_power(1);                       /* HAP_power_set_HMX, power_up = TRUE */
compute_resource_hmx_lock(r.ctx);
... HMX ...
compute_resource_hmx_unlock(r.ctx);
hmx_power(0);
res_put(&r);
```

После фикса: 12+ вызовов подряд без зависаний, устройство здорово
(`sys.boot_completed=1`). До фикса было 8 зависаний user PD, каждое лечилось
`adb reboot`.

## 2. Ячейки и раскладки

### 16-битные ячейки

HMX читает **16-битные ячейки**. int8-значение должно быть в **обоих байтах**
ячейки: одиночный байт даёт 0, пара `0x0101` даёт 1. Это объясняет все прежние
«нули при верной раскладке».

### fp16 (проверено картой входов)

```
act_off(s,c) = (s>>1)*128 + c*4 + (s&1)*2
wgt_off(n,k) = (k>>1)*128 + n*4 + (k&1)*2
out_off(s,n) = (s>>1)*128 + n*4 + (s&1)*2
```

Контроль: `A[s][c]=s+c/32, B=I` даёт точную карту `(s_read, c_read)`:
`s=0: 0:0 0:1 …`, `s=1: 1:0 …`. `A=2.0, B=I` → все 1024 ячейки `1.999 ≈ 2.0`
(систематический −1 ulp при convert — учитывать для целых значений).

### int8: веса

```
weight_off(n,k) = 1024*(n>>4) + 128*(k>>2) + 8*(n&15) + 2*(k&3)
                  (значение писать в оба байта)
```

Проверка `A=1, B[n][k]=n+1` даёт `16·(n+1)` в **каждом** слове каждой
8-байтной группы: `16 16 16 16 | 32 32 32 32 | … | 240 240 240 240`.
4 k-ячейки на 128-байтную линию, 8 линий = 32 k на 1 КБ, 16 каналов на линию,
`n >= 16` — второй КБ (+1024).

### int8: выход

```
out(s,n) = 2 + 1024*(n>>4) + 128*(s>>1) + 8*(n&15) + 2*(s&1)
```

2 spatial на 128-байтную линию, 16 линий = 32 spatial × 16 каналов = **2 КБ за
одну инструкцию**. `Rt` (srt 0…0x200) на spatial не влияет.

### int8: активация — единственное, что не снято

Карта каналов показывает: hardware читает **4 ячейки активации на 128-байтную
линию с шагом 32 Б**, и это группы каналов 0..3; остальные 12 групп не читаются.
Перебрано 30+ комбинаций `1024*(c>>2) + 128*(s>>2) + 32*(c&3) + 2*slot(s&3)` и
варианты со сдвигом канала: лучший результат — 8 верных ячеек из 1024.
Вывод: раскладка активации структурно иная (похоже, spatial-major внутри
4-канального 32-байтного блока с нетривиальной перестановкой), и чёрный ящик её
дальше не берёт. Для сравнения, у fp16 раскладка совпала с PRM.

## 3. Store: 2 КБ одной инструкцией

Эксперимент «покрытие»: `A=1, B=I` → каждая записанная ячейка = `0x3C00`
(fp16) или известный маркер (int8). Считали такие слова в 2 КБ после прогона:

| вариант | заполнено |
|---|---|
| fp16 `:after.hf = acc` | 1024/1024 |
| int8 `:after:sat.uh = acc:2x1` | 1024/1024 |

Сдвиг адреса на 128 Б выносит часть записи за тайл (минус 64 слова) — форма
покрытия ровно 2 КБ на инструкцию. Второй store только портит тайл.

| вариант store | результат |
|---|---|
| `:after:sat.ub = acc` (8-битный) | пишет **нули** при любых данных |
| `:after:cm:sat.ub = acc` | тоже нули |
| `:after:sat.uh = acc:2x1` | **работает**, 16-битные ячейки |
| `:after:sat.uh = acc:2x2` | не кодируется для v68 (`requires -mv69`) |
| `:before`, `:retain`, `:cm` | для покрытия не нужны |

## 4. MAC-геометрия

| тип | MAC на multiply | как получено |
|---|---|---|
| int8 | **16** | `A=B=1` → 16; `stop=31` → 16, `stop=15` → 8, MAC=(stop+1)/2 |
| fp16 | **2** | `A=B=1`, 32 канала → 1.999; насыщение при cnt=2 |

int8: k=0..15 — первая пара, k=16..31 — вторая (веса +1024, отдельный регион).
fp16: ни `channel stop` (0x1C/0x3C/0x7C), ни `wgt_rt` (127…4095), ни
`mxswapacc` число MAC не меняют.

Итог по S1:

* fp16 32×32×32: `max_abs_err = 71.0`, 929/1024 — **не закрыт**.
* int8 32×32×32: `max_abs_err = 32`, лучший `16×16×32` — 80/256 — **не закрыт**.
* S2 (K=256), S3 (128×64×256), S4 (128×7680×2048) не запускались: нет
  корректного тайла.

## 5. Накопление 32 каналов: `:deep` на весах

Найдено в дизассемблере QNN (`hmx_convhbh1x1deep_stride1`, `0x371ec0`):

```
mxclracc;
for i in 0..ncr-1:
    { activation.ub = mxmem(act + astep*i, 0x7C)
      weight.b     = mxmem(wgt + wstride*i, 2047):deep }
bias = mxmem2(bias_buf);
mxmem(out, 0):after:sat.uh = acc:2x1;
```

Проверено: `ncr=2, wstride=2048, wgt_rt=2047, astep=1024` → `A=1,B=1` даёт
**32.0** (16+16). Это единственная форма, которая суммирует два 16-канальных
кроутона на v68.

Что **не** работает:

| попытка | результат |
|---|---|
| `dC` на активации (PRM §4.2, 5 конфигураций) | max_abs_err 71…75, без изменений |
| второй plain-pair (`Rs[6:2]=16`) | те же 71.0 |
| `mxswapacc` между парами | значение не меняется |
| `cvt.hf = acc` + отдельный store | **нет на v68**: `instruction requires -mv73` |
| два независимых кроутона (act +1024/+2048, wgt +1024/+2048) | второй читается как нули → 16, а не 32 |
| оба указателя на один кроутон (маска) | 32 (накопление есть, но данных второго нет) |

Остался адресный вопрос: как положить второй 16-канальный кроутон активации,
чтобы `activation.ub … :deep` его прочитал. Наиболее вероятная гипотеза —
32 канала в одной линии (4 байта на канал × 32 = 128 Б), а не два отдельных
килобайта.

## 6. Bias

Блок 256 Б: сначала 32 младших 32-битных слова (`scale` fp16 в `[15:0]`,
`output bias` в `[31:16]`), затем 32 старших. Нулевой bias-блок → весь выход
нулевой: путь `sat` реально применяет bias/scale.

Требования: адрес выровнен на 256 Б; младшие 2 бита — номер bias-набора.

## 7. Адресация и VTCM

* VTCM 4 МБ, страница до 1 МБ, MMU-адрес базы `0xfec00000`.
* HMX ходит по тем же MMU-адресам, что и скалярный код: передача **смещений**
  вместо адресов даёт `AEE_EBADPERMS` (78). Гипотеза «нужны физические адреса»
  снята.
* В `mxmem` адрес активации — это `Rs[31:11]` (2 КБ), а `Rs[10:2]` — spatial
  offset / channel start. Поэтому int8-кроутоны нельзя класть подряд по 1 КБ:
  нужен слот 2 КБ на кроутон; хвост 1 КБ зануляется (защита от чтения за
  границу, иначе `AEE_EBADPERMS`/SSR).
* `mxmem2` (bias) требует 256-Б выравнивания; проверка в коде (`-33`).
* Передача DDR-указателей в `mxmem` невозможна; проверка адреса/выравнивания —
  `-30/-31/-32`.

## 8. Что подтвердилось как «не причина»

* Кодировки инструкций совпадают побайтово с QNN v68:
  `activation.ub=mxmem` `9200_41ec`, `:cm` `9200_41ed`, `weight.b=mxmem`
  `9202_e3e0`, `mxmem(...):after:cm:sat.ub=acc` `a6e0_c105` (у QNN
  `a6ea_cb05`), `bias=mxmem2` `9200_c3fe`, `mxclracc` `a6e0c011`.
* `mxmem2` сам по себе не вешает PD; `activation.ub + weight.b` без store —
  тоже.

## 9. Что дал бы HMX и что осталось

Оценка потолка QNN: 2.44 мс на 128×7680×2048 = 2.01 GMAC ⇒ ≈**0.83 TMAC/s**
(в задании 2.4 TMAC/s — видимо, с паддингом N до 8192). Свой HMX-замер S4
не сделан: нет корректного тайла, а мерить GMAC/s на неверных данных
бессмысленно.

Осталось (по приоритету):

1. Снять точную раскладку второго кроутона активации — из
   `libQnnHtpPrepare.so`
   (`hnnx::tileExt_priv::tile_methods_r4crouton<Ldefs::Crouton4x1_8>::tile_write`,
   `0x28b4f50`) или дампом VTCM работающего QNN-графа; оценка 1–2 дня.
2. После S1 — S2 (K=256, 8 кроутонов), S3, S4 (128×7680×2048) на каркасе
   `mx4_gemm`, затем S5 (M=1).
3. Учесть power on/off ~70 мс на RPC: для S4 держать питание включённым на
   весь вызов и мерить внутри.

Пока prefill остаётся на QNN (2.44 мс / 0.83 TMAC/s) или HVX.
