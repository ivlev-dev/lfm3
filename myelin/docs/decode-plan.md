# План decode (N=1): от 9.15 к 25 tok/s

Документ отвечает на три вопроса: из чего состоят текущие 109 мс/токен,
что из этого устранимо и каким должен быть бюджет трафика, чтобы 25 tok/s
были физически возможны. Код не менялся; всё ниже — разбор существующего
пути и план.

Метки источника: **[замер]** — есть артефакт в репозитории или на стенде;
**[код]** — следует из кода (можно пересчитать); **[оценка]** — вывод из
замеров, требует подтверждения. Отдельно помечено, что надо померить.

---

## 0. Резюме

1. **109 мс = 51 DSP + 58 накладных.** DSP-часть уже почти на пределе
   измеренной эффективности ядер (C-стенд `exec_test` даёт 47.4 мс на том же
   наборе матриц, но без `lm_head`; с ним ≈ 54 мс). Значит весь запас — в
   58 мс накладных, а не в арифметике.
2. **Накладные — это 82 FastRPC-вызова на токен**, а не «транспорт вообще».
   C-стенд на том же графе платит 0.335 мс/вызов, Rust-рантайм — 0.82 мс/вызов
   (в 2.4× больше). Первый подозреваемый — несуществующая переиспользуемая
   пара буферов входа/выхода (каждый вызов несёт 4 незарегистрированные
   последовательности) и, возможно, заморозка процесса в фоне (стенд это
   прямо документирует: 120–190 мс wall на вызов при тех же 47 мс DSP).
3. **Главный рычаг — не «ускорить RPC на 10 %», а убрать вызовы.** C-стенд
   уже измерил: тот же граф одним `exec` — **47.7 мс wall** против 76.6 мс
   на 85 вызовах (**+8 tok/s**), при побитовой идентичности результата.
   В Rust граф разорван на 82 вызова хост-математикой (norm/rope/kv_write).
4. **25 tok/s на текущей архитектуре недостижимы.** Честный трафик —
   **≈880 МБ/токен** при ctx 2048. При измеренных 20.6 ГБ/с это 42.7 мс →
   **23.4 tok/s** при *нулевых* накладных и *идеальных* ядрах. Плюс
   compute-потолок 45.3 GMAC/s → 38 мс (26 tok/s). Оба потолка сходятся
   около 23. Для 25 нужно одновременно ≥22 ГБ/с и ≥43 GMAC/s — выше
   измеренного пика, без запаса на SiLU/conv/attention.
5. **Что сделать, чтобы 25 стали возможны:** (а) 1 `exec` на токен,
   (б) ≥22 ГБ/с эффективно — это либо второй unsigned PD (замерено
   22.3 ГБ/с на 2 PD / 33.3 на 4 PD), либо сокращение трафика на ~15 %
   (shortlist для `lm_head` — 131 МБ, 15 % трафика), (в) накладные ≤2 мс.
   Ближайший реальный ориентир без смены архитектуры — **19–22 tok/s**.

## 1. Что именно исполняется на токен

Путь: `apps/lfm` — это OpenCL/APU-приложение, DSP-путь живёт в
`myelin/crates/myelin-npu/src/bin/dsp-generate.rs` → `myelin-core`
`Session::step_with` → `DspBackend` → `Executor` → `Cdsprpc`.

Модель: LFM3, hidden 2048, ffn 7680, 24 слоя (13 conv + 11 attention),
16 q-голов / 4 kv-головы × 128, vocab 128 000, окно 256
(`crates/myelin-core/src/arch/lfm3.rs:42-57`). Все веса int4, резидентны
в ION (`alloc_in`, zero-copy), 866.2 МБ **[код]**.

### 1.1 Бюджет вызовов на токен **[код]**

| источник | вызовов | что внутри |
|---|---|---|
| FFN, 24 слоя | 24 | `exec` из одной команды `FFN` |
| conv, 13 слоёв | 13 | `exec` из 3 команд (`GEMV` → `CONV` → `GEMV`) |
| attention, 11 слоёв | 33 | `exec` ×3: qkv-проекции, `ATTN`, o_proj |
| `lm_head` | 1 | `exec` из одной `GEMV` (N=128 000) |
| `kv_write`, 11 слоёв | 11 | прямой `invoke`, не `exec` |
| **итого** | **82 RPC** (71 `exec` + 11 `invoke`) | |

`map_arena`/`unmap_arena` в установившемся режиме — 0 (кэш списков),
`reserve_scratch`/`reset_state` — один раз за сессию. Это важно: «71 exec»
и «82 RPC» — одно и то же явление, просто `kv_write` не попал в счётчик
`exec`.

### 1.2 Почему attention — три вызова

`DspBackend::attention_layer_full` (`crates/myelin-core/src/backend/dsp.rs:1537`)
делает на хосте между вызовами:

1. после qkv-проекций: де-квант int8 → f32, per-head RMSNorm, rope,
   повторный квант в int8, `kv_write` (запись K/V в резидентные образы);
2. после `ATTN`: q12 → f32 с **поканальным** масштабом V (512 значений)
   и гейтом, квант в int8 для o_proj.

Пока это на хосте, склеить три команды в один список нельзя. Это и есть
структурная причина 33 вызовов вместо 11.

## 2. Разложение 109 мс

### 2.1 Таблица

| статья | мс/токен | источник | комментарий |
|---|---|---|---|
| DSP-команды (сумма `times[0]`) | **51.0** | [замер] `MYELIN_TRACE` | включает SiLU, conv, attention, `lm_head`; **не включает** `memcpy` активации в scratch, маршалинг и пробуждения |
| FastRPC round-trip, фиксированная часть | 11–13 | [замер] пустой вызов 0.117–0.164 мс × 82; `rpc_test` median 0.150 | пол, ниже которого один вызов не опускается |
| Маршалинг/pin последовательностей | **≈42–46** | [оценка] = 58 − (11–13) − (1.5–2.5) − (~1) | главный подозреваемый; 0.55 мс на вызов при полезной нагрузке 2–8 КБ |
| host glue (norm, rope, dequant/quant, KV-зеркало, аллокации, `var_os`) | 1.5–2.5 | [оценка] по коду | см. §2.3, требует замера |
| `map_arena` (амортизировано) | ~0 … 1 | [замер] 2.2 мс за список | 0 в установившемся режиме; при переходе через границу страницы — 11 ремапов раз в 32 токена (см. §5, O2) |
| **итого** | **109** | [замер] | 51 DSP + 58 накладных |

Проверка арифметики: 51 + 82×0.15 + 45 + 2 = 110 ≈ 109. Сходится, но
распределение между «маршалингом» и «заморозкой/шедулером» — гипотеза.

> Осторожно с знаменателем: 58 мс / 82 RPC = **0.71 мс на вызов**;
> 58 / 71 = 0.82 мс, если 58 мс — это только счётчик `invoke` из
> `MYELIN_TRACE` (он считает лишь `exec`, без `kv_write`). Дальше в тексте
> «0.82» относится к `exec`-вызовам, «0.71» — ко всем RPC.

### 2.2 Сверка с C-стендом (главный независимый источник)

`dsp/hvx/README.md`, раздел «Время (`exec_test 6`)»: граф 85 команд
(24 FFN + 11 ATTN + 11 QUANT + 13×(in_proj+CONV+out_proj)), реальные размеры,
671 МиБ int4 в ION **[замер]**:

| | 1 `exec` | 85 `exec` |
|---|---|---|
| DSP, сумма команд | 47.4 мс | 48.2 мс |
| wall (min, экран включён) | **47.7 мс** | 76.6 мс |
| накладные RPC | 0.42 мс | 28.5 мс |
| tok/s | **20.97** | 13.05 |

Три вывода:

1. **Потолок накладных при 1 вызове — 0.4 мс**, а не 58. Разница между
   47.7 и 76.6 мс — это ровно цена 85 round-trip'ов.
2. **0.335 мс/вызов в C против 0.82 в Rust** на exec формы FFN
   (act 2 КБ, out 2 КБ, rt 16 Б, times 32 Б). Значит дело не в FastRPC как
   таковом, а в том, *что* и *как* передаёт Rust.
3. В этом графе **нет `lm_head`** (85 = 24+11+11+39). 131 МБ головы — это
   ещё ≈6.4 мс при 20.6 ГБ/с, т.е. честный эквивалент 20.97 tok/s для полной
   модели — **≈18.2 tok/s**. Это лучший измеренный ориентир «идеального
   транспорта на текущем графе».

### 2.3 Что померить, чтобы закрыть неопределённость

| # | что | как | что даст |
|---|---|---|---|
| E1 | реальная цена вызова в Rust | `MYELIN_TRACE=1`, 32 токена, **экран включён, процесс на переднем плане** (`am start`, не из фона) | отделит «заморозку» от маршалинга: если `invoke` упадёт с 0.82 до ~0.3 мс/вызов — 58 мс были артефактом фона |
| E2 | цена вызова vs размер/число последовательностей | микробенч: `exec` 1 команды; act 0/2К/8К, out 2К/8К; (a) `Vec`, (b) rpcmem, (c) `remote_register_buf` | подтвердит/опровергнет pin-per-call; даст константу для планирования |
| E3 | per-op DSP | сейчас `times[0]` — сумма по списку, `lfm_run_cmd` не прокидывает `times` в ядра (`dsp/hvx/lfmgemv_impl.c:3462`) | разложить 51 мс на FFN/ATTN/CONV/GEMV/LM_HEAD, а не оценивать |
| E4 | host glue | `exec_host_micros` (`dsp.rs:1954`) vs wall шага | отделит 1.5 мс гипотезы от факта |
| E5 | дрейф списков на длинном контексте | 128 токенов при ctx 512+, счётчик `map_arena` | увидит ли cliff из §5/O2 (кэш 128 < 71 + 11×(ctx/32)) |

Пока E1–E3 не сделаны, цифры §2.1 остаются оценкой в пределах ±10 мс.

## 3. Exec-вызовы: 82 → 1

### 3.1 Что можно устранить и чем

| шаг | RPC/токен | что нужно | выигрыш (при 0.335 мс/вызов) | риск |
|---|---|---|---|---|
| сейчас | 82 | — | — | — |
| S1: `kv_write` внутрь списка qkv | 71 | новые команды `KVSTORE` (K/kt/V уже лежат в scratch; DSP копирует их в образы) | 3.7 мс | низкий, чистая пересылка |
| S2: `ATTN` + `ATTN_SCALE` + o_proj в один список | 60 | команда `ATTN_SCALE` = q12 × поканальный масштаб V (512 f32 резидентно) × гейт → int8 | 3.7 мс | средний: новая арифметика, нужен побитовый/косинный гейт |
| S3: qkv + norm/rope + ATTN в один список | 49 | команды `NORMQ` (RMSNorm f32 + квант) и `ROPE` (f32, таблица sin/cos на позицию — 512 Б в act) | 3.7 мс | средне-высокий: numerics, нужен слой-в-слой гейт |
| S4: весь токен одним списком | **1** | `NORMQ` + `RESIDUAL` на DSP; активации слоёв — в scratch; один статичный список на всю сессию | **−16 мс** (48 × 0.335) + исчезают провалы DSP между вызовами | высокий по объёму, средний по качеству |

Важно: **S4 не требует новых алгоритмов, только переноса уже написанной
хост-математики в DSP-команды.** C-стенд уже доказал, что граф из ~85 команд
даёт побитово тот же результат, что 85 отдельных `exec`, и стоит 47.7 мс
(`exec_test`, «полный граф: 1 `exec` vs 85 `exec` — 0/2048»).

### 3.2 Бюджет команд для одного списка на токен

| блок | команд | расчёт |
|---|---|---|
| FFN | 24 | 1 на слой |
| conv | 39 | 3 × 13 |
| attention | 88–99 | 8–9 × 11: qkv(4) + `NORMQ`(1) + `ROPE`(1) + `KVSTORE`(1) + `ATTN`(1) + `ATTN_SCALE`(1) + o_proj(1) |
| norm/residual между блоками | 48–72 | 2–3 на слой |
| `lm_head` + argmax/top-k | 1–2 | `GEMV` (+ опционально `ARGMAX`) |
| **итого** | **200–236** | предел `LFM_CMD_MAX = 256`, `list_bytes ≤ 1 МиБ` |

Влезает, но без запаса. Разумно поднять `LFM_CMD_MAX` до 384–512
(`lfmgemv_impl.c:3249`): 512 команд — это 49 КБ списка, лимит 1 МиБ не
трогаем. Scratch: 24 слоя × (x, normed, merged, block) ≈ 240 КБ + conv-кольца
7 МиБ (сейчас `EXEC_SCRATCH_BYTES = 8 МиБ`, `dsp.rs:596`) + норма-веса 768 КБ
→ 16 МиБ с запасом (DSP-heap это выдержит: веса не в heap).

### 3.3 Про «батчинг daemon-команд»

Батчить больше нечего: в установившемся режиме все per-tensor вызовы — это
`exec`/`kv_write`. `alloc_buf`/`load_buf`/`set_scale` — только загрузка.
Поэтому единственный батчинг, который остался, — склейка самих `exec`
(§3.1), и он упирается не в транспорт, а в хост-математику между слоями.

## 4. Трафик и потолок

### 4.1 Честные байты на токен

Веса int4 = `N·K/2`, все размеры кратны `K_ALIGN = 256` / `N_ALIGN = 32`,
паддинга нет (кроме гейта: 16→32 строки, уже учтено) **[код]**:

| тензор | шт | байт на шт | байт всего |
|---|---|---|---|
| FFN gate+up+down (7680×2048, 2048×7680) | 24 | 23 592 960 | 566 231 040 |
| attention q/k/v/gate/o | 11 | 5 275 648 | 58 032 128 |
| conv in_proj + out_proj + blob | 13 | 8 527 872 | 110 862 336 |
| `lm_head` 128 000×2048 | 1 | 131 072 000 | 131 072 000 |
| **веса** | | | **866 197 504** |
| per-row масштабы (4 Б/строка) | | | 3 360 000 |
| активации host↔DSP (act+out) | | | ~0.35 МБ |
| **веса + масштабы + активации** | | | **≈869.6 МБ** |
| KV, ctx 2048 (6 full + 5 sliding) | | | 10.6 МБ |
| KV, ctx 256 | | | 2.2 МБ |
| **итого, ctx 2048** | | | **≈880 МБ** |

Доли: FFN **64.4 %**, `lm_head` **14.9 %**, conv **12.6 %**, attention **6.6 %**.
KV при 2K-контексте — 1.2 %, при 8K — ~4.5 %: на decode это не проблема
трафика, проблема — время `ATTN` (9.7 мс на 11 слоёв при 2K).

### 4.2 Roofline

| ограничение | цифра | время на токен | tok/s |
|---|---|---|---|
| память, 20.6 ГБ/с [замер, FFN-матрица, 2 ctx] | 880 МБ | 42.7 мс | **23.4** |
| память, 22.7 ГБ/с [замер, старый стенд] | 880 МБ | 38.8 мс | 25.8 |
| compute, 45.3 GMAC/s [замер] | 1.732 GMAC | 38.2 мс | 26.2 |
| compute, 41 GMAC/s [замер, FFN] | 1.732 GMAC | 42.2 мс | 23.7 |
| DDR-чтение, 38.7 ГБ/с [замер, 8 потоков] | 880 МБ | 22.7 мс | 44 |

MAC на токен = 2 × байт весов, потому что int4. Память и compute
**сбалансированы** (20.6 ГБ/с ↔ 41 GMAC/s) — это и есть потолок одного PD
с двумя HVX-контекстами.

### 4.3 Проверка утверждения «потолок 23 tok/s»

Утверждение верно и даже немного оптимистично:

* 880 МБ / 20.6 ГБ/с = 42.7 мс → **23.4 tok/s** — при 100 % попадании в пик
  полосы и нулевых накладных;
* пик 20.6 ГБ/с измерен на **одной** матрице 7.86 МБ; в реальном слое FFN
  идёт на 18.1 ГБ/с (`exec_test`: 1304 мкс × 24 = 31.3 мс на 566 МБ), conv —
  на 14.7 ГБ/с. По этим цифрам DSP-пол ≈ 54 мс → **18.5 tok/s**;
* добавить 1.7 мс SiLU (24 × 0.07), 1.3 мс conv-glue, ~2 мс ALU attention —
  и потолок падает до **~21 tok/s** даже при идеальном транспорте.

Для 25 tok/s (40 мс) нужно **22.0 ГБ/с и 43.3 GMAC/s одновременно**, т.е.
выше измеренного пика по обоим параметрам, с нулевым запасом на SiLU/conv/
attention. На одном PD это нереалистично.

### 4.4 Схемы, укладывающиеся в бюджет

| схема | трафик | полоса | время | потолок |
|---|---|---|---|---|
| как есть, 1 PD | 880 МБ | 20.6 | 42.7 мс | 23.4 |
| + shortlist `lm_head` (1024 центроида + 4×128 строк) | 751 МБ | 20.6 | 36.5 мс | **27.4** |
| + FFN 3 бита (вне рамок: качество) | 739 МБ | 20.6 | 35.9 мс | 27.9 |
| 2 unsigned PD, сплит строк | 880 МБ | 30–33 [оценка по 12.2/22.3/33.3] | 26.7–29.3 мс | **34–37** |
| 2 PD + shortlist | 751 МБ | 30–33 | 22.8–25.0 мс | 40–44 |

Замер «1/2/4 независимых PD: 12.2 / 22.3 / 33.3 ГБ/с» (`measurements.md:33`)
говорит, что упор не в DRAM (38.7 ГБ/с на 8 потоков), а в числе PD×контекстов.
Это единственный способ поднять полосу без потери качества.

Механика 2 PD уже поддержана примитивами: `alloc_view(ah, off, nbytes)`
даёт ручку на поддиапазон строк матрицы, `map_arena` — отдельную арену на PD,
`alloc_in` — тот же fd в оба PD (физические страницы общие). Нужны два
хост-потока с параллельными `exec` и разбиение N пополам.

### O1. Переиспользуемые буферы `exec` (S)

**Суть.** Один раз на handle выделить rpcmem-буферы максимального размера под
`act`, `rt`, `out`, `times` и переиспользовать их во всех вызовах; при
необходимости — `remote_register_buf(ptr, len, 0)` + `KEEP_MAP`
(`FASTRPC_ATTR_KEEP_MAP` уже в конфиге, `cdsprpc.rs:29`, но **не
используется**; `remote_register_buf` вообще не резолвится). Дополнительно:
не передавать `times` в горячем пути (это отдельная выходная
последовательность → отдельный pin), включать только под `MYELIN_TRACE`;
держать `act`/`out` в rpcmem, а не в `Vec`.

**Почему верим.** C-стенд с теми же размерами платит 0.335 мс/вызов, Rust —
0.82. `rpc_test`: 1 in/1 out (16 Б/4 КБ) — 150–166 мкс, 1 in/3 out (ffn) —
219–227 мкс. То есть в C «дорогая» форма стоит 0.22 мс, а не 0.8.
`rpc_test` также фиксирует: 256 КБ payload = 0.74–0.86 мс, т.е. цена растёт
с числом страниц → гипотеза pin-per-call состоятельна.

**Ожидание.** 82 × (0.71 − 0.35) ≈ 30 мс; консервативно 26–34 мс.
Wall 109 → 75–83 мс, **12.5–13.3 tok/s** (против 9.15).

**Риск.** Низкий: буферы живут столько же, сколько handle; содержимое
проверяется существующим `dsp-layer-check`/`dsp-generate` (RESET_CHECK,
побитовое сравнение).

**Проверка.** `MYELIN_TRACE`: `ms/call` должен упасть до ≤0.35; вывод
`dsp-generate` на 24 токенах — те же токены, что до правки.

### O2. Статичные списки и кэш арен (S)

**Суть.** Сейчас список `ATTN` содержит `tbl_len = pages`, а `pages` растёт
каждые 32 токена (`dsp.rs:1747`). Каждая новая страница порождает новый
байтовый список → новый `map_arena` (2.2 мс) и запись в кэш. При ctx 2048
это 11×64 = 704 варианта против `LIST_CACHE = 128`
(`executor.rs:130`) и `MAXARENA = 160` в скелете: кэш начинает вытеснять
**стабильные** списки FFN/conv, и дальше возможен ремап 10–20 списков на
каждый токен (оценка: +22–44 мс/токен) — скрытый обрыв на длинном контексте.

**Решение без правок DSP.** `attn_core` использует `tblLen` только в проверке
`(pos >> 5) >= tblLen` (`lfmgemv_impl.c:2153`), а длину окна считает из
`pos/seq/window`. Значит достаточно передавать `tbl_len = cache_pages` и
identity-таблицу `0..cache_pages` (её можно один раз положить в `act` рядом
с q; +до 256 Б на вызов). Список становится байт-в-байт стабильным.
Заодно: `LIST_CACHE = 160` (как `MAXARENA`), поиск по хэшу (сейчас линейное
сравнение всего списка по 71–160 записям на каждый вызов), и хранить
pre-encoded список, а не пере-кодировать `list.to_bytes()` каждый раз.

**Ожидание.** 1–2 мс сейчас (на коротком ctx) и снятие cliff'а 20+ мс/токен
на ctx ≥ 512.

### O3. Хост-микро (S)

* `Session::step_with` вызывает `std::env::var_os` **на каждый слой** (24) и
  `dump_vector` ×48 → ~72 блокирующих поиска в environ на токен; вынести в
  конфиг сессии.
* `RopeTable::new` строится заново на каждый attention-слой каждый токен
  (11 × 64 `powf`); кэшировать в `DspBackend` — таблица зависит только от
  spec.
* `RopeTable::apply` делает `sin_cos` на каждую пару каждого заголовка
  (≈1280 на слой, 14 тыс. на токен). Углы одинаковы для всех голов: считать
  64 пары sin/cos **один раз на позицию** и применять к 16+4 головам.
* `quantize`/`dequantize`/`rt_to_bytes` аллоцируют `Vec` на каждый вызов
  (≈200 аллокаций/токен) — писать в переиспользуемые буферы.
* `lm_head`: `argmax(code × out_scale) = argmax(code)` — можно не
  де-квантовать 128 тыс. значений в f32 (0.2 мс + 512 КБ аллокации).

Итого 0.7–1.2 мс — немного, но это 2–3 % бюджета 40 мс и почти бесплатно.

### O4. Attention: 33 → 11 вызовов (M)

**Суть.** Две новые команды:

* `KVSTORE` — K/kt/V уже лежат в scratch (их считает хост), DSP копирует их в
  резидентные образы по `head*slots+slot`; заменяет RPC `kv_write`;
* `ATTN_SCALE` — `q12 × v_scale[kh*128+dim] × gate[qh]` → int8. Таблица
  512 f32 — резидентная (кладётся при стейджинге слоя), гейт — 16 f32 в rt.
  Сейчас это хост-цикл `dsp.rs:1766-1786`.

Тогда qkv(4) + `KVSTORE` + `ATTN` + `ATTN_SCALE` + o_proj — один список на
слой. RPC 82 → 60.

**Ожидание.** 22 (exec) + 11 (kv_write) = 33 × цена вызова: 11 мс при 0.335,
до 27 мс при 0.82. После O1 — ~11 мс.

**Риск.** Средний: `ATTN_SCALE` — новая арифметика. Гейт: побитовое сравнение
`out` с текущим путём на реальном слое (`dsp-layer-check`, дампы
`MYELIN_DUMP_*`), затем cos ≥ 0.999 на 24 токенах.

### O5. Один `exec` на токен (L) — главный рычаг после O1

**Суть.** Перенести в DSP три оставшиеся хост-операции:

1. `NORMQ(src_f32, weights[], eps, scale) → int8` — RMSNorm + квант;
2. `NORMQ_ADD(src_f32, residual_f32, w_post[], w_ffn[], eps, scale) → int8`,
   заодно пишет `merged` f32 — это сразу два нормирования и residual из
   `session.rs:419-437`;
3. `ROPE` — поворот f32 (sin/cos на позицию приходят в `act`, 2 таблицы ×
   512 Б: full θ=1e6 и sliding θ=1e4).

Веса норм (24 слоя × 4 × 2048 f32 = 768 КБ) — в scratch при старте сессии.
Активации слоёв — фиксированные смещения в scratch. Список собирается один
раз, `rt` несёт позицию и счётчики conv по слоям.

**Ожидание.** 48 оставшихся вызовов × 0.335 = 16 мс; плюс исчезают паузы
DSP между матрицами (сейчас после каждой матрицы DSP ждёт хост) и появляется
возможность `l2fetch` через границу слоя. По C-стенду ориентир wall —
47.7 мс на 85 командах без `lm_head`, т.е. **~54 мс с головой → 18.5 tok/s**;
после O6 — 20–22.

**Риск.** Средний по качеству: RMSNorm на DSP считается в f32 (на V68 f64 —
soft-float), CPU-оракул суммирует в f64 → расхождение ~1e-7, не побитово.
Нужен гейт: cos по слоям ≥ 0.9999 и совпадение argmax на 24–64 токенах.
Объём: ~600–1000 строк C + переработка `DspBackend` (сейчас один вызов
`Backend::*` на слой; нужен `Backend::token` или fast-path в `DspBackend`,
который сам обходит 24 слоя).

### O6. Тюнинг ядер (M)

По `exec_test`: FFN 1304 мкс/слой = 18.1 ГБ/с (пик 20.6 → −3.8 мс),
conv-проекции 14.7 ГБ/с (−1 мс), `ATTN` 878 мкс против 660 мкс на «горячем»
KV (−2.4 мс). Суммарно 4.5–6 мс. Отдельно проверить `in_proj` (6144×2048):
в `conv_test` он мерился 827 мкс = 7.7 ГБ/с — если это не артефакт старого
стенда, там лежит ещё ~5 мс.

### O7. `lm_head` (M, гейт по качеству)

131 МБ = 15 % трафика. Два независимых улучшения:

* **дешёвое:** `argmax`/top-k на DSP (`ARGMAX` по int8), наружу — 64
  кандидата вместо 128 КБ: −0.3 мс хоста и −128 КБ marshalling;
* **трафик:** двухступенчатый shortlist — 1024 центроида (1 МиБ) → top-4
  кластера → 512 точных строк (0.5 МБ) вместо 125 МиБ: −129 МБ = −6.3 мс.
  Риск: перестаёт быть точным argmax; нужен замер на реальных логитах
  (сколько раз истинный argmax не попадает в shortlist).

### O8. Второй PD (L) — единственный способ пробить 23

Полоса на PD не масштабируется: 2 контекста — упор (`measurements.md:32`),
но 1/2/4 PD дают 12.2/22.3/33.3 ГБ/с. Сплит по строкам матрицы через
`alloc_view` + два параллельных `exec` из двух хост-потоков. Ожидание:
DSP 51 → 29–33 мс, потолок 30+. Риск: двойная арена/scratch на PD,
синхронизация на каждой матрице (2 RPC вместо 1, но параллельных),
проверка, что оба PD видят один и тот же fd.

### O9. Спекулятивный decode (L, вне рамок)

M=2–4 переиспользует прочитанные веса на 2–4 токена → эффективный ×1.5–1.8
при том же трафике. Требует draft-модель/head и приёмки по качеству.
Это единственный путь к 35+ без второго PD.

## 6. Вердикт по 25 tok/s

**На текущей архитектуре (один PD, два HVX-контекста, host glue между
слоями) 25 tok/s недостижимы.** Не потому, что «медленный транспорт», а
потому что после его устранения остаётся пол 42–47 мс:

* трафик 880 МБ при 20.6 ГБ/с = 42.7 мс (23.4 tok/s) — это **без** SiLU,
  conv-glue и ALU attention;
* compute 1.732 GMAC при 45.3 GMAC/s = 38.2 мс (26.2 tok/s) — пик старого
  стенда, в интегрированном графе 41 GMAC/s (23.7 tok/s);
* реальные ядра в графе дают 54 мс с `lm_head` → 18.5 tok/s.

**Обязательные условия для 25:**

1. накладные ≤ 2–3 мс/токен (один `exec` + зарегистрированные буферы);
2. DSP ≤ 37 мс;
3. для п.2 — либо эффективная полоса ≥ 22 ГБ/с в среднем по графу (а с
   учётом ~5 мс нематричной работы — ≈25 ГБ/с; сейчас 18.1 на FFN, 14.7 на
   conv), либо сокращение трафика на ≥ 8 % (shortlist `lm_head` даёт 15 %).

Пункт 3 на одном PD — это +10–20 % к пику без запаса. Практически: **25 tok/s
требуют второго PD** (или 3-битных FFN, что вне рамок) **и** одного `exec`
на токен. Тогда реалистично 28–35 tok/s.

**Следующий потолок** — не interconnect, а пара «DRAM × HVX»: 38.7 ГБ/с
чтения (8 потоков) и ~90 GMAC/s на 4 контекстах (2 PD) дают ~19–23 мс →
40–50 tok/s. Дальше упираемся в качество квантования (int4 уже на грани) и в
то, что decode с M=1 не переиспользует веса: спекулятивный decode —
следующий архитектурный шаг.

**Промежуточные цели, которые стоит зафиксировать как приёмку:**

| веха | tok/s | что доказывает |
|---|---|---|
| O1+O2+O3 | 12.5–13.5 | накладные перестали быть доминантой |
| O4 | 14–15.5 | 60 RPC, attention одним списком |
| O5 | 18.5–19 | один `exec` на токен (паритет с C-стендом) |
| O6 | 20–22 | ядра на пике полосы — практический потолок 1 PD |
| O8 | 28–35 | полоса масштабируется PD, 25 пройдены |

## 7. Риски

1. **Ложная атрибуция 58 мс.** Если E1 покажет 0.3 мс/вызов (процесс был
   заморожен), то O1 даст не 30, а 3–5 мс, и весь план смещается к O5.
   Поэтому E1 — до любых правок.
2. **Numerics при переносе norm/rope на DSP.** f32 вместо f64 в RMSNorm,
   int8-повторный квант q. Гейт: cos по слоям, argmax на 24–64 токенах,
   побитовое сравнение там, где возможно (KVSTORE, ATTN_SCALE).
3. **`ATTN` с `tbl_len = cache_pages`.** Проверка `(pos>>5) >= tblLen`
   пройдёт, но таблица должна содержать все `cache_pages` валидных id;
   ошибка даст тихий мусор в attention. Нужен тест на последней странице.
4. **Длинный контекст.** Кэш списков 128 против 71 + 11×(ctx/32) — обрыв,
   который легко не заметить на 24 токенах. Мерить на 128+ токенах, ctx 512+.
5. **DVFS.** `set_perf()` просит TURBO + `mips_bw` 34 ГБ/с; в REPORT20
   голосование за шину **сбрасывало** клок (1133 → 375 pcycles/µs). Стоит
   проверить, не вредит ли `mips_bw`-запрос в текущей прошивке; мерить только
   с включённым экраном (в фоне wall раздувается до 120–190 мс на вызов).
6. **Второй PD.** Тот же fd в двух PD, две арены, два scratch — неизвестно,
   сколько памяти даст DSP-heap под второй scratch (сейчас 8 МиБ). Проверить
   `reserve_scratch` на обоих до интеграции.
7. **`lm_head` shortlist** меняет распределение логитов → риск повторений/
   деградации. Гейт: сравнение argmax на 200+ токенах реального текста.

## 8. Эксперименты на устройстве (когда оно освободится)

Порядок — от дешёвых и решающих к дорогим.

1. **E1. Фон vs передний план.** `dsp-generate` 32 токена, ctx 256 и 1024,
   экран включён, процесс на переднем плане (`am start`/`input keyevent`),
   `MYELIN_TRACE=1`. Снять `calls`, `arena ms`, `invoke ms`, `ms/call`,
   `DECODE_STEPS`. Повторить в фоне. **Решение: 58 мс — это маршалинг или
   заморозка.**
2. **E2. Цена вызова vs payload.** Микробенч (можно на базе `npu-bench`):
   `exec` 1 команды, act 0/2К/8К, out 2К/8К/128К; (a) `Vec`, (b) rpcmem,
   (c) `remote_register_buf` + `KEEP_MAP`; 200 итераций, min/median.
   **Даст константу и подтвердит O1.**
3. **E3. Per-op DSP.** Прокинуть `times` из `lfm_run_cmd` в ядра (или
   отдельный probe) и снять разложение 51 мс: FFN / ATTN / CONV / GEMV /
   `lm_head`. **Проверит §2.1 и покажет, где O6.**
4. **E4. Host glue.** `exec_host_micros` + wall шага минус DSP минус invoke.
   **Проверит 1.5–2.5 мс.**
5. **E5. Дрейф списков.** 128 токенов, ctx 512 и 2048, счётчик `map_arena`
   и `unmap_arena`. **Проверит cliff из O2.**
6. **E6. Полоса conv.** Отдельно `in_proj` (6144×2048) в текущем срезе:
   827 мкс — это 7.7 ГБ/с или артефакт старого стенда.
7. **E7. Второй PD.** Один GEMV 7680×2048, сплит N пополам, два PD, два
   потока; замерить wall и агрегат ГБ/с. **Решает судьбу O8.**
8. **E8. `lm_head` shortlist.** На сохранённых логитах: доля токенов, где
   истинный argmax не попал в top-4 кластера. **Решает судьбу O7.**
9. **E9. DVFS.** Один и тот же токен-граф с `set_perf()` и без
   `mips_bw`/DCVS-запроса; `mx4_test clk` до/после.

## 9. Приложение: формулы

```
байт весов int4      = N_pad * K_pad / 2
MAC на токен         = 2 * байт весов            (int4)
время по памяти      = трафик / полоса
tok/s                = 1000 / мс_на_токен
накладные            = RPC * цена_вызова + host_glue + ремапы
```

Текущие значения для подстановки: трафик 880 МБ (ctx 2048), RPC 82,
цена вызова 0.82 мс (Rust) / 0.335 (C-стенд), DSP 51 мс, host glue ~2 мс.

Ориентиры для планирования (все [замер]): пустой RPC 0.117–0.164 мс;
FFN-матрица 7680×2048 int4 — 0.378 мс (20.6 ГБ/с); FFN-слой — 1.30–1.48 мс;
conv-слой — 0.74–1.19 мс; `ATTN` @2048 — 0.57–0.88 мс; `map_arena` — 2.2 мс;
1/2/4 PD — 12.2/22.3/33.3 ГБ/с; DDR 8 потоков — 38.7 ГБ/с.
