# Контракт ядер: эталон `backend-opencl` → HVX/HMX

Документ описывает **только то, что реально делает эталон** (`crates/backend-opencl`,
OpenCL-бэкенд lfm3). Код не менялся. Все формулы выведены из перечисленных
файлов/строк; где поведение неоднозначно — это вынесено в
[«Открытые вопросы»](#открытые-вопросы-к-оркестратору).

Обозначения: `H` — hidden, `F` — ffn, `V` — vocab, `d` — head_dim, `G = 32` —
группа квантования (`src/lib.rs:93`), `P = 32` —токенов в странице KV
(`src/lib.rs:95` = `src/radix.rs:3`).

## 1. Форматы весов

### 1.1 Q4_K (родной ggml), блок 144 B / 256 весов

Источник: `crates/infra-quant/src/lib.rs:40-65`, `src/prepack.rs:3-6,165-177`.

| Смещение | Размер | Содержимое |
|---|---|---|
| 0 | 2 | `d` — fp16 (little-endian), супер-масштаб |
| 2 | 2 | `dmin` — fp16, супер-минимум |
| 4 | 12 | `sc[0..8]` и `m[0..8]` по 6 бит: байты 0..4 — младшие 6 бит `sc[j]/m[j]` для `j<4`, байты 8..12 — старшие 2 бита для `j>=4` + их младшие нибблы |
| 16 | 128 | `qs[128]`: 4 «четверти» по 32 байта, в байте два 4-бит кода |

Распаковка 6-битных полей (`src/prepack.rs:165-177`, `infra-quant:30-38`):

```
jm = j & 3;  h = j >> 2
a = qs_scales[jm]; b = qs_scales[jm+4]; c = qs_scales[jm+8]
lo_d = a & 63;  lo_m = b & 63
hi_d = (c & 15) | ((a >> 6) << 4)
hi_m = (c >> 4) | ((b >> 6) << 4)
sc[j] = h ? hi_d : lo_d;   m[j] = h ? hi_m : lo_m
```

Деквант (точная формула эталона, `infra-quant:48-63`):

```
для jq = 0,1,2,3:                       # четверть, 64 веса
  (sc1,m1) = scale_min(2*jq);   (sc2,m2) = scale_min(2*jq+1)
  для l = 0..31:
    w[64*jq + l]      = d*sc1*((qs[32*jq + l]     ) & 0x0F) - dmin*m1
    w[64*jq + 32 + l] = d*sc2*((qs[32*jq + l] >> 4) & 0x0F) - dmin*m2
```

Следствия, обязательные для повтора:

* `q` — **беззнаковый** 0..15; знак даёт вычитание `dmin*m` (offset-форма, не two's complement).
* младший ниббл байта — **чётный** логический вес (`64*jq + l`), старший — `64*jq + 32 + l`.
* `sc`, `m` — целые 0..63, но домножаются на **fp16** `d`/`dmin`.
* Порядок строк матрицы: `row_stride = (cols/256) * 144`, строка идёт подряд.

### 1.2 Q4_K → «препак» 148 B (то, что читают ядра на GPU)

`prepack_q4_k`, `src/prepack.rs:101-122`. Блок **148 B**, а не 144:

| Смещение | Размер | Содержимое |
|---|---|---|
| 0 | 4 | копия `d`,`dmin` (байты 0..4 исходника) |
| 4 | 16 | 8 пар `(sc[j], m[j])` **по одному байту**, уже распакованные |
| 20 | 128 | копия `qs` исходника (16..144) |

Причина: ядру нужен доступ к масштабу без битовой распаковки на устройстве и
выровненное окно 4 байта на пару подгрупп (`src/prepack.rs:255-268`).

### 1.3 Q6_K (эмбеддинг, lm_head, часть матриц), блок 210 B / 256 весов

`crates/infra-quant/src/lib.rs:67-100`, декод в шейдере `kernels/decode.cl:6-30`.

| Смещение | Размер | Содержимое |
|---|---|---|
| 0 | 128 | `ql` — младшие 4 бита |
| 128 | 64 | `qh` — старшие 2 бита (по 4 группы на байт) |
| 192 | 16 | `sc[16]` — **int8** масштабы подблоков |
| 208 | 2 | `d` — fp16 |

```
для n = 0,1 (половины по 128):
  для l = 0..31:
    q1 = ((ql[64n+l]    & 15) | (((qh[32n+l]    ) & 3) << 4)) - 32
    q2 = ((ql[64n+l+32] & 15) | (((qh[32n+l] >>2) & 3) << 4)) - 32
    q3 = ((ql[64n+l]  >> 4)   | (((qh[32n+l] >>4) & 3) << 4)) - 32
    q4 = ((ql[64n+l+32]>>4)   | (((qh[32n+l] >>6) & 3) << 4)) - 32
    w[128n + l +  0] = d * sc[8n + l/16 + 0] * q1
    w[128n + l + 32] = d * sc[8n + l/16 + 2] * q2
    w[128n + l + 64] = d * sc[8n + l/16 + 4] * q3
    w[128n + l + 96] = d * sc[8n + l/16 + 6] * q4
```

Знак — **offset-32** (`-32`), масштаб `sc` — знаковый int8, `d` — fp16.

### 1.4 int8/32 — формат, которым реально считает эталон («int4/32» в задаче)

> **Факт:** в эталоне **нет** весового формата int4/32. Единственный
> переквантованный формат — **int8 с группой 32**; 4-битные веса в репозитории
> есть только в DSP-пути (`myelin/docs/dsp-kernels.md:21-33`, offset-8) и в
> HMX `weight.n` (`myelin/docs/hmx.md:258-290`, two's complement). Разрыв
> зафиксирован в [открытых вопросах](#открытые-вопросы-к-оркестратору), п. 1.

Продакшн-путь: `prepack_q4_i8_with_threads` / `prepack_q6_i8_with_threads`
(`src/prepack.rs:179-215`, `126-163`). Включается по умолчанию (`q4i8=true`,
`q6i8=true`, `src/options.rs:56-57`).

**Математика квантования** (`src/prepack.rs:48-76`, ветка Q4_K):

```
для каждой строки r и каждой группы g из 32 подряд идущих входных каналов:
  vals[i] = dequant_q4k(w[i])                      # f32, см. 1.1
  amax    = max_i |vals[i]|
  scale   = amax>0 ? amax/127 : 0                  # f32, хранится как есть
  q[i]    = clamp(round(vals[i] * 127/amax), -127, 127)   # round = half away from zero
```

* Диапазон `q ∈ [-127, 127]` — **симметричный, zero-point нет**, `-128` не используется.
* `round` — Rust `f32::round()` = **half away from zero**. Это НЕ то же, что
  `convert_int_rte` в активациях (см. §2): на точных `0.5` результаты расходятся на 1 LSB.
* Масштаб пишется в **f32**, не fp16 и не Q16. Ошибка реконструкции ≤ 0.5·scale
  (проверяется тестом `src/prepack.rs:399-427`).

**Раскладка памяти (критично для HVX/HMX)** — group-major, row-minor:

```
q_index(g, r, i)     = (g*rows + r)*32 + i          # i8
scale_index(g, r)    =  g*rows + r                  # f32
g = block_in_row*8 + sub_block (0..7)               # 8 групп на 256 каналов
```

То есть для `rows` строк тензора байты лежат **группами по всем строкам** —
`[g][row][32]`, а не `[row][cols]`. Собственной «строки» у тензора нет: строка
`r` размазана по `cols/32` блокам по 32 байта. Это удобно для GEMM по 64
строкам (`kernels/batch.cl:2273-2276` читает `wq8[((b*8+g)*rows + row)*32]`) и
это же надо воспроизвести в HVX/HMX-упаковщике, иначе ядро не совпадёт с
эталоном.

Ещё два следствия:

* int8-копия **сосуществует** с 148-байтным ниббловым препаком (память почти
  удваивается: 4.625 → 9.0 бит/вес = 8 бит данных + f32/32; цена в
  `benchmarks/machine.md:721-724`).
* `LFM_Q4I8_FFN_ONLY=1` оставляет int8 только у FFN (`src/options.rs:120-122`,
  `src/lib.rs:780-782`).

## 2. Форматы активаций

### 2.1 `quantize_q8` — per-group-32, симметричный, без клиппинга

`kernels/decode.cl:78-121`; батч-вариант `kernels/batch.cl:242-264`.
Формула (одна на все пути — `quantize`, `rms_quant`, `silu_quant`,
`norm_add_quant`, `quantize_b`):

```
для каждой группы g из 32 подряд идущих элементов строки:
  amax = max_i |x[32g+i]|                 # f32, порядок fmax не важен (точный max)
  sc   = amax > 0 ? amax/127 : 0          # f32 -> xs[g]
  inv  = amax > 0 ? 127/amax : 0
  q[i] = convert_int_rte(x[32g+i] * inv)  # round-to-nearest-even, int8
```

| Свойство | Значение | Ссылка |
|---|---|---|
| Гранулярность | **per group of 32** (`GROUP=32`) вдоль входных каналов | `src/lib.rs:93` |
| Per-row/per-tensor | per **(row, group)**: ноль на строку нет, ноль на тензор нет; `xs` = `f32[ntok * (n/32)]`, индекс `t*(n/32)+g` | `batch.cl:258`, `decode.cl:111` |
| Клиппинг | **отсутствует** (гарантирован тем, что `|x| ≤ amax`, переполнение невозможно; `-128` не появляется) | `decode.cl:113-117` |
| Округление | `convert_int_rte` = ties-to-even | `decode.cl:115` |
| Нулевая группа | `amax=0 → sc=0, inv=0 → все q=0` | `decode.cl:107-108` |
| Хранение scale | **f32** | — |

Замечание: `sc*inv = 1` не обязательно; деквант активации делает **ядро GEMV**
умножением на `xs`-группу, отдельной материализации f32-вектора нет.

### 2.2 Слитые с нормировкой/активацией квантователи

Все они дают **тот же** int8/32, но считают вход «на лету»:

| Ядро | Формула до квантования | Ссылка |
|---|---|---|
| `rms_norm` / `rms_quant` | `y = x * rsqrt(mean(x²)+1e-5) * w` | `decode.cl:32-53,378-410` |
| `rms_norm_add` / `norm_add_quant` | `y = op*s1*w_post + res` (residual), затем `z = y*rsqrt(mean(y²)+1e-5)*next_w` → квант | `decode.cl:439-527` |
| `silu_mul` / `silu_quant` | `y = (g/(1+exp(-g))) * u`, `g = ug[i]`, `u = ug[up_off+i]` | `decode.cl:345-353,412-437` |

`eps = 1e-5` **захардкожен** в шейдерах, `cfg.norm_eps` в ядро не передаётся
(`decode.cl:49,72,393,467,492`). Для LFM3 metadata даёт ровно `1e-5`
(`domain/src/config.rs:436-437`) — совпадает, но это неявная зависимость.

`norm_add_quant` считает **два разных RMS**: по `op` (выход подслоя) и по
`op*s1*w+res` (после residual). Порядок: RMS(op) → `v = op*s1*p + r` →
RMS(v) → `w = v*s2*next_w` → квант по 32. Это ровно residual + post-norm.

## 3. GEMV / GEMM

### 3.1 Контракт входа-выхода (все ядра)

```
int8/32:  y[t][row] = Σ_g  xs[t][g] · ( Σ_{i∈g} qw[row][g][i] · xq[t][g][i] ) · s_w[row][g]
Q4_K:     y[t][row] = Σ_g  xs[t][g] · ( d·sc_g·dot_g − dmin·m_g·sum_g )
```

где `dot_g` — int32-сумма произведений по группе, `sum_g = Σ_i xq[t][g][i]`
(int32, общая для всех строк). Выход — **f32**, без дополнительной нормировки.

Раскладка выхода разная:

| Путь | Форма `y` | Индекс |
|---|---|---|
| decode (`ntok=1`) | `[rows]` | `y[row0+r]` |
| batch/prefill | `[ntok][rows]` (token-major!) | `y[t*rows + row]` |

### 3.2 Decode GEMV (по ниббловому Q4_K, 144 B)

`gemv_q4_k_i8`, `kernels/decode.cl:137-203`. Запуск: `gemv_auto`,
`src/lib.rs:1336-1361`, `1372-1388`.

| Параметр | Значение (по умолчанию) |
|---|---|
| workgroup | `wg = 256` (`LFM_WG`, кратно 64); для 148-B препака `local = wg_b = 64` |
| строк на подгруппу | `RGEMV = 4` (`-DRGEMV=4`) |
| строк на workgroup | `nsg * RGEMV`: 8·4 = **32** при local=256, 2·4 = **8** при local=64 |
| grid | `ceil(rows/32) * wg` (всегда от `wg`, `src/lib.rs:1372-1373`); при local=64 это 4 WG на 32 строки |
| lane → каналы | `u = lane & 7`: окно 16 B (`wbase = (u>>1)*64 + (u&1)*16`), группы `sb_lo = (u>>1)*2` и `sb_lo+1` |
| блоков в полёте | `bpi = subgroup/8` (при subgroup=32 → 4 блока = 1024 канала за итерацию) |

Внутри одной 32-группы:

```
dl   = Σ_{i<32} q_low[i]  * xq[i]        # int32, точный (sdot4 на AMD)
dh   = Σ_{i<32} q_high[i] * xq[i]        # int32
sum  = Σ_{i<32} xq[i]                    # int32, считается один раз на группу
acc += xs * ( float(dl) * (d*sc) - float(sum) * (dmin*m) )
```

Порядок критичен: **сначала точный int32 dot внутри группы, потом приведение к
f32 и умножение на масштабы**, а не наоборот. `sum` не зависит от строки и
переиспользуется для всех `RGEMV` строк.

Накопление — `float acc[4]` на lane, затем `sub_group_reduce_add(acc[r])`
(`decode.cl:198`). Финальная «нормализация» отсутствует — просто запись
`y[row0+r] = total` при `lane==0`.

Тот же контракт у вариантов: `gemv_q4_k_i8_pk` (препак 148 B, `decode.cl:206-270`),
`gemv_q6_k_i8` (int8-препак Q6, `decode.cl:272-343`, `acc += xs*s_w*dl` — без
члена `sum`), `gemv_q4_k_i8_4p_b` (сразу 4 выхода: `rows = r1+r2+r3+r4`,
`kernels/batch.cl:1121`).

### 3.3 Батч 2..8 токенов: ниббловый GEMM 64×8

`gemm_q4_k_i8_b8p` (`kernels/batch.cl:1903-2030`), запуск `src/lib.rs:1473-1503`,
`1559-1587`.

| Параметр | Значение |
|---|---|
| workgroup | 64 (1 строка на поток), grid = `ceil(rows/64)*64` |
| токенов за запуск | 8, чанки по 8 с `tok0` (`launch_b8p_chunks`, `src/lib.rs:1394-1448`) |
| LDS | `xt[2*8*256]` double-buffer + `xsum[2*8*8]` + веса текущего блока `ws[2*64*16]`, `wh[2*64*4]` |
| вес на итерацию | один 148-B блок: 4×`q`, в каждом 32+16 B → 64 веса (2 группы) |
| формула | `acc[t] += xs[t][g]*(dl*(d*sc) - sum_l*(dmin*m))`, `dl` — 8 `dot4` |

### 3.4 Prefill: int8/32 GEMM

Основной путь `gemm_i8_pf` (`kernels/batch.cl:2207-2316`), при `ntok≤16` —
`gemm_i8_pf16` (256 потоков, `batch.cl:2318-2428`), fallback `gemm_i8_gz`
(`batch.cl:2102-2204`), Q6 — `gemm_q6_i8_pp` (`batch.cl:1358-1452`).
Выбор: `src/lib.rs:1588-1619`.

| Параметр `gemm_i8_pf` | Значение |
|---|---|
| workgroup | **512** потоков, 16 варпов |
| тайл | 64 выходных строк × **32 токена** |
| разбиение варпов | `whalf = warp>>3` → 2 половины по 32 строки; `rloc = whalf*32 + lane` |
| токены варпа | `tok_base = (warp&7)*4` → 4 токена на варп, `acc[4]` |
| grid | `ceil(rows/64) * ceil(ntok/32) * 512` |
| LDS | `xt[2*32*256]` (double-buffer активаций), `xsl[2*32*8]` |
| вес | 32 int8 на строку на группу, читается `uint4 ×2` = 8×`dot4` |
| формула | `acc[j] += float(dl) * wsc[row][g] * xs[t][g]` |

Активации в LDS стейджатся **в исходном виде** (не перепакованные): 256 B на
токен = 8 групп по 32. Веса читаются из group-major раскладки §1.4 напрямую.

## 4. FFN

Порядок задаётся `forward_step` (`src/lib.rs:2607-2648`).

| # | Шаг | Вход → выход | Ядро |
|---|---|---|---|
| 1 | residual + post-attn-norm + ffn-norm + квант | `tmp` + `post_attention_norm` + `x` → `x` (residual), `xq/hs` (int8/32 по `H`) | `norm_add_quant` |
| 2 | gate+up одной матрицей | `xq/hs` → `ug` = `f32[2F]` | GEMV/GEMM, `rows=2F, cols=H` |
| 3 | SiLU(gate)·up + квант | `ug` → `actq/acts` (int8/32 по `F`) | `silu_quant`, `n=F`, `up_off=F` |
| 4 | down | `actq/acts` → `tmp` = `f32[H]` | GEMV/GEMM, `rows=H, cols=F` |
| 5 | residual + post-ffn-norm + next-norm + квант | `tmp` + `post_ffw_norm` + `x` → `x`, `xq/hs` под `attn_norm` **следующего** слоя (или `output_norm`) | `norm_add_quant` |

Детали:

* Матрица `ffn_ug` — **конкатенация по строкам**: сначала все `F` строк `ffn_gate`,
  потом все `F` строк `ffn_up` (`src/lib.rs:856-899`: `fused = gate ++ up`).
  Значит `gate = ug[0..F]`, `up = ug[F..2F]`, `up_off = F`.
* Активация ровно `SiLU(g) * u` (`g/(1+exp(-g))*u`), без clamp, затем per-32 квант.
* «Intermediate-точка в int8» — **только** выход `silu_quant` (`act`). Между
  gate/up и SiLU всё в f32; между down и residual — f32.
* `next_w` для шага 5: `blk.{L+1}.attn_norm.weight`, а на последнем слое —
  `output_norm.weight` (`src/lib.rs:2640-2647`).

## 5. Attention

### 5.1 Индексация KV: paged, varlen, block table

Paged всегда, страница = 32 токена. Таблица на последовательность:
`tbl[page]`, `slot = (tbl[page] << 5) | (pos & 31)` (`decode.cl:609-616`,
`batch.cl:828-839,866`). Батч использует срезы `tbl_off[t]` (в элементах `u32`) и
`pos_b[t]` — то есть **varlen**: у каждой строки батча свой `pos`, своя длина
`len = pos_b[t]+1` и свой срез таблицы. Страницы аллоцируются
`ceil(ctx/32)*kv_pool`, KV держат только attention-слои (`src/lib.rs:1085-1086`).

Адрес K/V одного токена: `slot * kv_heads * head_dim + kvh * head_dim`
(токен-major, внутри — голова, внутри — канал).

### 5.2 Форматы K/V

| `LFM_KV` | K | V | Точность vs f16 | Ссылка |
|---|---|---|---|---|
| `f16` (default) | fp16 | fp16 | эталон | `common.cl:61-73` |
| `q4` | TQ: fp16-норма + 4-битный кодбук (16 уровней), после Hadamard+знакового вращения | 4-бит offset-7 + `max_abs/7` fp16 на токен | ~0.998 | `kvq4.cl:3-122` |
| `kvarn` (k4v2/k4v4) | 4-бит код + масштабы на канал/токен (f16) | 2/4-бит + bias/scale f16, вращение | k4v2 ~0.985–0.994, k4v4 строже | `kvarn.cl`, `myelin/docs/paged-kv.md` |

На устройстве без fp16 (`LFM_F32_KV`) KV хранится во float, заголовки читаются
вручную (`common.cl:26-60`).

### 5.3 QK^T, softmax, PV

Decode, `attention_h` (`decode.cl:630-722`):

* голова = workgroup (`grid = heads*64`, `local = 64`), `kvh = head / (heads/kv_heads)`;
* `lane` обрабатывает пару каналов `(2*lane, 2*lane+1)`, т.е. 64 lane = `head_dim=128`;
* `scale = 1/sqrt(head_dim)` применяется **после** редукции скалярного произведения;
* online softmax (flash-decoding), по 2 позиции за итерацию:
  `m_new = max(m, s0, s1); corr = exp(m-m_new); w = exp(s-m_new); l = l*corr + w0 + w1; acc = acc*corr + w0*v0 + w1*v1`;
* **окно**: `start = (pos+1 > window) ? pos+1-window : 0`, `window=0` → полное
  (хост считает `start` из `cfg.sliding_window` и передаёт его, `src/lib.rs:2398-2402`;
  в батче — параметр `window`, `batch.cl:855`);
* выход головы умножается на гейт: `out = (acc/l) * sigmoid(gate[head])`
  (`decode.cl:719`, гейт считается отдельным GEMV `attn_gate`, `rows=heads`,
  `src/lib.rs:2210-2217`).

Разбиение по длине: `attention_splits(span) = clamp(span/512, 1, 16)`
(`src/lib.rs:47-49`). Сплиты пишут `pacc[head][split][head_dim]` и `pml[..] = (m, l)`,
затем `attention_combine` перенормирует
(`decode.cl:583-607`, batch `batch.cl:797-826`):

```
M = max_s m_s;  l = Σ_s l_s·exp(m_s-M);  a = Σ_s acc_s·exp(m_s-M)
out = (a/l) * sigmoid(gate)
```

Батч-варианты: `attention_b_h` (4 головы/workgroup × 64 lane, `batch.cl:841-893`),
`attention_b_fa` (8 каналов/lane + shuffle-xor reduce, `batch.cl:895-937`),
`attention_b_h2`, сплит-версии `attention_split_b_*`, `_fa2`, `_h4_p4`.

### 5.4 RoPE и qk-norm

`rms_rope_qk` (`decode.cl:529-581`), батч `rms_rope_heads_b` (`batch.cl:747-795`):

1. RMS-норм по `head_dim` с собственным `w` (`attn_q_norm` / `attn_k_norm`), `eps=1e-5`;
2. **split-half** rope: пары `(i, i+head_dim/2)`, `i < head_dim/2`,
   `angle = pos * inv_freq[i]`, `a' = a·cos − b·sin`, `b' = b·cos + a·sin`;
3. `inv_freq[i] == 0` → пара **не вращается** (частичное rope: full-слои
   `rotated_dim=64` → активны `i<32`; sliding-слои 128 → все 64 пары).

Та же формула в CPU-эталоне (`crates/infra-cpu/src/lib.rs:102-115`).

## 6. LM head / vocab projection

* Tied embeddings: отдельного `output.weight` нет, логиты = GEMV по
  `token_embd.weight` (`src/lib.rs:2655-2664`), `rows=V=128000`, `cols=H`.
  Untied head явно не поддержан (`src/lib.rs:976`).
* Формат эмбеддинга — **Q6_K**; декод строки токена `embed_q6k`
  (`decode.cl:6-30`) даёт f32-вектор `H` (embed-путь, `src/lib.rs:2097-2114`).
* Для LM head на prefill используется тот же GEMM, что для матриц (`rows=128000`),
  выход `f32[V]`; выбор строк — `logits_rows`/`logits_map` (`src/lib.rs:637-670`,
  `3293-3368`).
* **Shortlist отсутствует**: считается полный словарь. Идея двухступенчатого
  shortlist (1024 центроида → top-4×128 строк) есть только в плане myelin
  (`myelin/docs/decode-plan.md:249,411-414`), в эталоне её нет.
* Argmax для батча — `logits_argmax_b` (`batch.cl:2640-2682`), f32-сравнение
  строго `>` (первый максимум побеждает).

## 7. Что даёт качество «Paris, and the capital of …»

Эталонный чек: `gpu-gen --tokens 8` → `Paris, and the capital of Japan is`
(`benchmarks/machine.md:839`, `tools/bench_check.sh:96-103` — проверка подстроки
`*Paris*` для `f16` и `kvarn`). Probe для A/B форматов весов —
`examples/quality_probe.rs:1-9`: те же 5 токенов `597 5205 302 3980 355`
(«Paris, and the capital of»), greedy-продолжение печатается как `FIRST`/`TOKENS`
(ожидаемое продолжение — `Japan …`); запуск с `LFM_PREPACK=0` даёт нативный Q4_K,
с `=1` — int8/32.

Числа, которые определяют «качество»:

| Конфигурация | cos к эталону | Источник |
|---|---|---|
| int8/32 prefill vs ниббловый Q4_K (`len 601, batch 64`) | **0.999861** vs 0.999906 | `machine.md:725` |
| int8/32 + новый GEMM | 0.999890 vs 0.999886 | `machine.md:184` |
| Q6 через int8-ядро | 0.999879 | `machine.md:198` |
| full GPU (f16 KV) vs CPU f32 | 0.998 (0.998427…0.998114) | `machine.md:505,839` |
| `kv` = kvarn vs f16 | 0.998543 vs 0.998427 | `machine.md:505` |

Отсюда — что реально влияет:

1. **`GROUP=32` и per-group absmax** — основная причина, почему int8/32
   практически не теряет относительно Q4_K: группа 32 совпадает с внутренней
   суб-группой Q4_K, и переквант идёт **по уже деквантованным** значениям.
   Увеличение группы (64/128) ухудшит cos сильнее, чем что-либо ещё.
2. **Симметричный диапазон ±127 без zero-point** — двойное округление Q4_K→int8
   остаётся в пределах 0.5 LSB int8; любая асимметрия (zero-point, `-128`)
   сдвигает результат на 1 LSB и ломает сверку top-k.
3. **Масштабы в f32, а не fp16** — fp16-масштаб на 128000-строчном head и на
   глубоких слоях даёт заметный дрейф; в эталоне масштабы активаций и весов
   всегда f32.
4. **Отсутствие клиппинга в активациях** — клип (например, ±6σ) изменил бы
   хвосты SiLU-выхода; в эталоне клипа нет вообще, только естественная граница
   `|q| ≤ 127`.
5. **KV = f16 по умолчанию.** Генерация «Paris…» воспроизводится и на `kvarn`
   (0.9949–0.9979 cos), но именно f16-путь даёт эталонный текст на AMD, а на
   Intel (UHD 630, режим без fp16 → KV во float) генерация совпадает с AMD
   (`machine.md:511-513`).
6. **`eps=1e-5` и SiLU в f32** до квантования — на «Paris» влияет слабо, но
   участвует в общей cos-сверке.

Практический вывод для приёмки HVX/HMX: сверять не текст, а (а) cos логитов
≥ 0.9998 против OpenCL-эталона на сохранённых логитах, (б) top-5 совпадение,
(в) текст «Paris, and the capital of Japan is» как smoke-тест.

## 8. Инварианты для HVX/HMX (обязательные)

**Веса**

1. `GROUP = 32` вдоль входных каналов; масштаб — **один на (row, group)**, `f32`.
2. Симметричный диапазон `q ∈ [-127, 127]`, zero-point отсутствует, `-128` не
   используется.
3. `scale = amax/127`, где `amax = max|w_dequant|` по группе; при `amax=0` —
   `scale=0` и `q=0`.
4. Округление весов — **half away from zero** (Rust `round`), не ties-to-even.
5. Порядок байтов: `q[(g*rows + r)*32 + i]`, `scale[g*rows + r]` — group-major,
   строка внутри группы. Менять на row-major нельзя без правки ядра-потребителя.
6. Внутри группы `i` идёт по возрастанию входного канала; младший ниббл/байт —
   меньший `i`.
7. Для нибблового Q4_K: `q` беззнаковый 0..15, деквант
   `d*sc*q − dmin*m`, `sc/m` — 6-битные, распаковка по §1.1; младший ниббл —
   вес `64jq+l`, старший — `64jq+32+l`.
8. Q6_K: `q = (nib | (qh_bits<<4)) − 32`, `sc` — **int8**, `d` — fp16.

**Активации**

9. Per-group-32 absmax, `sc = amax/127` (f32), `q = rte(x*127/amax)`, без клиппа.
10. Нулевая группа → `sc=0`, `q=0` (не NaN, не деление на ноль).
11. `xs` — `f32[ntok * (n/32)]`, индекс `token*(n/32) + g` (token-major).
12. Все fused-нормировки используют `eps = 1e-5` и считают RMS **до** умножения
    на `w`, ровно как `decode.cl:378-410`.

**GEMV/GEMM**

13. Внутри группы — **точный int32** dot (32 произведения); приведение к f32 и
    умножение на `scale_w * scale_x` — **после** группы.
14. Для Q4_K обязателен член `− sum(x) * (dmin*m)`, где `sum(x)` — int32-сумма
    активаций группы, общая для всех строк.
15. Выход — f32; для батча раскладка `y[token*rows + row]` (token-major).
16. Никакой финальной нормировки/деления на 127 в GEMV нет.
17. `SiLU(g)*u` в f32, затем per-32 квант; `g = ug[0..F]`, `u = ug[F..2F]`.

**Attention**

18. `slot = (tbl[pos>>5] << 5) | (pos & 31)`, страница 32 токена, `tbl_off` — в
    элементах `u32`.
19. `kvh = head / (n_heads/kv_heads)`; адрес `slot*(kv_heads*d) + kvh*d`.
20. `scale = 1/sqrt(d)` **после** dot, online-softmax с `corr=exp(m−m_new)`.
21. Окно: `start = max(0, len − window)`, `window=0` → полное.
22. Гейт головы: `out *= sigmoid(gate[head])` после деления на `l`.
23. Сплиты: `clamp(span/512, 1, 16)`, комбинация через `max(m_s)`.
24. RoPE: split-half пары `(i, i+d/2)`, `angle = pos*inv_freq[i]`,
    `inv_freq==0` → без вращения; rope применяется **после** qk-RMS-нормы.

**Прочее**

25. `H % 256 == 0`, `F % 256 == 0`, `d == 128`, `cols % 256 == 0`.
26. LM head — полный словарь по `token_embd.weight` (tied), без shortlist;
    сравнение логитов строго `>` при равных.

**О бит-в-бит**

Целочисленная часть воспроизводима **точно**: int32-dot по 32 элементам,
int32-суммы активаций, int8-квантователи. Дальше начинается f32:

* порядок операций в эталоне: `xs * (float(dl)*(d*sc) − float(sum)*(dmin*m))`
  и `acc += ...` по группам подряд, затем `sub_group_reduce_add` (дерево
  редукции зависит от размера подгруппы и вендора);
* для int8/32: `((float)dl * wsc) * xs`, накопление по группам подряд.

Требовать побитового равенства f32-аккумулятора между разными ISA нельзя.
Практический критерий приёмки: **целочисленные стадии — бит-в-бит на фикстурах
(одна группа, один блок, одна строка); f32-стадии — |Δ| ≤ 1e-5·max|y| или
cos ≥ 0.9998 на логитах одного шага.**

## Открытые вопросы к Оркестратору

1. **int4/32 vs int8/32.** В эталоне нет весового int4/32: есть нативный Q4_K
   и переквант **int8/32**. Формулировка задачи («int4/32, GROUP=32»)
   расходится с эталоном. Варианты:
   (а) HVX/HMX читают **нативный Q4_K** (148-B препак) — бит-совместимо с
   эталоном, но на 1 операцию распаковки нибблов больше;
   (б) HVX/HMX читают **int8/32** (как prefill-путь эталона) — 2× трафик, зато
   проще и уже проверено (cos 0.99986);
   (в) собственный int4/32 (offset-8 или two's complement) — тогда нужен
   отдельный критерий эквивалентности к эталону, потому что 4-битный переквант
   Q4_K→int4 добавит второй шум поверх уже существующего. **Нужно решение до
   начала реализации упаковщика.**

2. **Округление весов.** Эталон: `round` = half away from zero (хост).
   Если HVX/HMX будут квантовать веса на устройстве/в своём упаковщике с
   `rte`, часть значений разойдётся на 1 LSB. Подтвердить: упаковка весов —
   **только на хосте, тем же кодом `prepack`**, устройство ничего не
   переквантовывает?

3. **Критерий «бит-в-бит».** Принять ли формулировку из §8 (целочисленные
   стадии бит-в-бит, f32 — cos ≥ 0.9998 / |Δ| ≤ 1e-5·max|y|)? Иначе задача
   невыполнима из-за порядка f32-редукции.

4. **Эталонная фикстура.** Нужны сохранённые эталоном данные для сверки:
   (а) `packed` + `int8/32` для 1–2 тензоров, (б) `xq/xs` после `rms_quant`
   на конкретном скрытом состоянии, (в) `ug`, `actq/acts`, (г) логиты для
   промпта `597 5205 302 3980 355`, (д) `pacc/pml` одного сплита. Кто их
   снимет и куда положит (`myelin/.../fixtures/`)?

5. **KV-формат для HVX/HMX.** Обязателен ли f16-KV для первой версии или сразу
   нужен kvarn/TQ? От этого зависит контракт attention (сейчас в §5.3 описан
   f16-путь как эталонный, остальные — как опции).

6. **`eps` и конфиг.** Ядра эталона игнорируют `cfg.norm_eps` и жёстко берут
   `1e-5`. Наследуем это (и фиксируем как константу контракта) или читаем из
   metadata? Для LFM3 значения совпадают, но при другой модели разойдётся.

7. **LM head.** Shortlist нет в эталоне; нужен ли он в первой версии HVX/HMX
   (трафик 128000×2048 int8 ≈ 262 МБ на токен) или начинаем с полного словаря
   ради сверки с эталоном, а shortlist добавляем позже с отдельным допуском?

8. **Допустимые отличия по слоям.** `shortconv` (13 из 24 слоёв) в эталоне —
   отдельные ядра `conv_step` + GEMV `in_proj/out_proj`; входят ли они в объём
   контракта HVX/HMX или первый этап только attention+FFN?
