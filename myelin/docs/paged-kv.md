# Paged KV и kvarn

Семантика повторяет OpenCL-бэкенд lfm3 (`crates/backend-opencl`: `radix.rs`,
`kernels/kvarn.cl`, `kv_blocks`), контракты зафиксированы в
`crates/lfm-npu-ref` (`abi.rs`, `layout.rs`, `kvarn.rs`). DSP-порт обязан
повторять те же правила; ниже — раскладка, инварианты и краевые случаи.

## 1. Страницы и таблица

* Страница = **32 токена** (`PAGE_TOKENS = KV_PAGE = 32`).
* `max_pages = ceil(ctx / 32) · kv_pool`.
* Каждая последовательность имеет свою таблицу: срез `tbl_all[seq·pt_stride ..
  (seq+1)·pt_stride]`, `pt_stride = max_pages`; в ABI это `Row::tbl_off`
  (в записях `u32`, не в байтах).
* Запись таблицы — физический номер страницы. Логический адрес токена:

```
page = pos >> 5
slot = (tbl[page] << 5) | (pos & 31)
```

* KV-арена: `kv_layers · max_pages · page_bytes(format)`. KV держат только
  attention-слои: у LFM3 24 слоя, из них 11 (`kv_layers = 11`).
* Таблица страниц: `max_seqs · pt_stride · 4` байт.

`Row` (ABI, 24 байта) несёт `token`, `seq`, `pos`, `ntok`, `kv_off`
(`seq·kv_stage`, в токенах KV), `tbl_off` (`seq·pt_stride`).
`StepDesc` (24 байта) — `n_rows`, `ntok`, `window`, `flags`
(`FLAG_PREFILL = 1`), `max_rows`, `reserved`.

## 2. Размеры страницы

### f16

`32 токена · kv_heads · head_dim · 2 байта · 2 (K и V)`.

При `kv_heads = 4`, `head_dim = 128` — **65 536 Б** на страницу.

### kvarn

На одну голову:

| поле | смысл | k4v2, Б | k4v4, Б |
|---|---|---|---|
| `kcode` | K 4 бита, 2 канала на байт (32·128/2) | 2048 | 2048 |
| `ka` | масштаб K на канал, f16 (128) | 256 | 256 |
| `kc` | масштаб K на токен, f16 (32) | 64 | 64 |
| `vcode` | V `v_bits` бит на канал (32·128·v/8) | 1024 | 2048 |
| `vb` | шаг V на токен, f16 (32) | 64 | 64 |
| `vbz` | нулевая точка V на токен, f16 (32) | 64 | 64 |
| `vc` | масштаб V на канал, f16 (128) | 256 | 256 |
| **итого на голову** | | **3 776** | **4 800** |

Страница целиком:

| формат | 4 головы | формула |
|---|---|---|
| f16 | 65 536 | `32·4·128·2·2` |
| kvarn k4v2 | **15 104** | `3776 · 4` |
| kvarn k4v4 | **19 200** | `4800 · 4` |

Проверка в `lfm-npu-ref`: `11 слоёв · 256 страниц · 15 104 = 42 532 864` Б на
ctx 8192, пул ×1 (≈40.6 МиБ кодов).

### Байтовые смещения внутри головы

Порядок полей — как в формуле `page_bytes` (вычислено из неё, не измерено):

| поле | k4v2 | k4v4 |
|---|---|---|
| `kcode` | 0…2047 | 0…2047 |
| `ka` | 2048…2303 | 2048…2303 |
| `kc` | 2304…2367 | 2304…2367 |
| `vcode` | 2368…3391 | 2368…4415 |
| `vb` | 3392…3455 | 4416…4479 |
| `vbz` | 3456…3519 | 4480…4543 |
| `vc` | 3520…3775 | 4544…4799 |

**Важно:** `page_bytes` задаёт только суммарный размер, а не межголовую
раскладку. В OpenCL-ядре коды лежат токен-мажорно с головой внутри токена:

```
kcode[((phys·32 + tok)·kv_heads + h)·64 + lane]
vcode[((phys·32 + tok)·kv_heads + h)·(64|32) + ...]
```

а скейлы — страница-мажорно: `ka[(phys·kv_heads + h)·128 + c]` и т.д.
В DSP-ядре attention (`/tmp/opencode/gemv`) принята **head-major** раскладка:
K-страница головы — непрерывные 2048 Б (32 токена × 64 Б), V после де-кванта —
4096 Б int8 на голову. При интеграции нужно выбрать одну раскладку и зафиксировать
её в ABI; сейчас это расхождение, а не баг.

## 3. Staging-кольцо

KV пишется не сразу в страницу, а в staging, откуда `kvarn_commit` кодирует
готовую страницу.

* `kv_stage = max(64, next_pow2(prefill_ntok))` (токенов на последовательность).
* staging-арена (host-эталон): `kv_layers · max_seqs · kv_stage · kv_dim · 4`
  байт (f32-зеркало; на DSP K и V выделяются отдельно).
* `max_rows <= kv_stage − 32`: тайл не должен затирать начало страницы, которое
  пришло из прошлого чанка. Для `kv_stage = 64` максимум 32 строки.
* Кольцо на последовательность; база — `Row::kv_off = seq · kv_stage`.
* Из staging читается только хвост `pos >= full_end`; закоммиченные страницы —
  из кодов.

Пример (ctx 4096, пул 1, 11 слоёв, 16 seq, 128 токенов): staging =
`11·16·128·512·4 = 46 137 344` Б.

## 4. Radix-кэш префиксов (хост)

Реализация — `crates/backend-opencl/src/radix.rs`; на DSP ничего не меняется.

* Хэш-цепочка по 32 токена: `block_hash(parent, tokens)` (FNV-подобное
  перемешивание + поворот родителя), результат `| 1`, чтобы 0 был маркером
  «не закэширован».
* Блок валиден только как префикс: одинаковые токены в середине дают другой хэш.
* Страницы общие, с refcount:
  * `take(hash)` — поднять страницу, `refs += 1`;
  * `publish(hash)` — повесить хэш после досчёта;
  * `release(page)` — `refs -= 1`, при 0 страница уходит в free-список, но
    остаётся в индексе (префикс доступен, пока не вытеснен);
  * `alloc()` — свободная страница с наименьшим `used` (LRU), старый хэш снимается.
* Последняя страница промпта **всегда пересчитывается** (минимум один токен):
  так получаются логиты и не нужен copy-on-write для общей последней страницы.
* Conv-состояние в KV не лежит: на каждую страницу и каждый conv-слой хранится
  снапшот `(conv_cache−1)·hidden` f32 = **49 КБ** (6·2048·4) при ctx 8192 —
  ≈12.6 МБ на слой. `snap_slots <= max_pages`.
* Вытеснение — LRU; отдельного бюджета нет, пул страниц — весь `max_ctx`
  (при `kv_pool = 1`).

Замер (OpenCL-референс, AMD): холодный prefill 512 токенов — 2773 мс,
повтор — 193 мс (2649 tok/s, 480/512 из кэша, ×14 по TTFT), cos логитов
1.00000000, top-5 совпал. После 12 чужих промптов кэш вытесняется, пересчёт
тоже совпадает бит-в-бит.

## 5. Инварианты (проверяет `arena_layout`)

| инвариант | значение |
|---|---|
| `ctx > 0`, `kv_layers > 0`, `kv_heads > 0`, `hidden > 0` | обязательно |
| `kv_pool` | `1..=16` |
| `kv_stage` | степень двойки, `>= 64` |
| `max_rows` | `<= kv_stage − 32` |
| `kvarn` | `head_dim == 128` (f16 — любой) |
| `snap_slots` | `<= max_pages` |
| `conv_cache` | `>= 2` |
| арены | начало выровнено на 256 Б, `total` = конец последней |
| OOM | `Oom { what: Arena / Kv / Staging / PageTable / Conv / Snap / Total, need, have }` |

Нарушение — `NpuError::Invalid`/`HeadDim`/`Oom`, а не тихая порча памяти.
`MAX_PREFILL_NTOK = 1 << 24` защищает `next_pow2` от переполнения.

## 6. Краевые случаи

1. **Граница страницы на стыке чанков.** Страница может начинаться до первой
   строки текущего тайла. `kvarn_commit` читает её из кольца, поэтому тайл
   ограничен `kv_stage − 32`; иначе более поздний токен затрёт начало страницы.
2. **`tbl_off`.** Смещение таблицы в записях `u32`, не в байтах. Ошибка на
   `seq` умножает не тот срез: физический номер чужой последовательности.
   В ядре `tbl_off` передаётся отдельным аргументом (`lfm_kvarn_k(..., tbl,
   tbl_off, page, ...)`).
3. **Sliding window.** `tok0 = max(0, pos+1−window)`; страницы левее `tok0`
   не читаются, но остаются в таблице. Окно не меняет `kv_stage` и размер
   страницы.
4. **Последняя страница промпта.** Всегда пересчитывается; её нельзя отдавать
   из radix-кэша как общую, иначе не будет логитов и потребуется CoW.
5. **`kv_pool`.** В `myelin` принято `kv_pool = max_seqs` — каждой
   последовательности весь `ctx`, `max_pages = ceil(ctx/32)·max_seqs`
   (ограничение `<= 16` в эталоне). Меньший пул экономит память, но при
   исчерпании запрос получает KV-ошибку (на OpenCL: пул ×1 при ctx 2048
   обслужил 7 из 16 запросов, ×4 — все 16).
6. **`pos` за пределами `ctx`.** В эталоне не описан; на DSP нужен явный
   `Ctl::Invalid`, иначе `pos>>5` выйдет за таблицу. **Нет данных** о текущем
   поведении порта — зафиксировать при интеграции.
7. **Пустая последовательность / `ntok = 0`.** `Row::ntok >= 1` по контракту;
   нулевые строки отсекает хост.
8. **`kvarn` и `head_dim != 128`.** Кодек отвергает; f16 — можно.

## 7. Что не проверено

* Совпадение DSP-раскладки страницы с `lfm-npu-ref` побайтово (эталон есть,
  сверки на устройстве нет).
* Поведение `pos >= ctx`, `snap_slots = 0` и `kv_pool > 1` на DSP-порте.
* Стоимость `kvarn_commit` на устройстве (в host-эталоне это CPU-код).
