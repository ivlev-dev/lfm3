Документ для разработчика, который продолжает работу. Он отвечает на три
вопроса: **что уже работает**, **что решено и почему**, **что делать первым**.

Установка окружения — в `SETUP.md`. Индекс всей документации — `README.md`.

## 1. Что это за проект

Два независимых пути инференса LFM3-1.7B:

| путь | где | статус |
|---|---|---|
| **OpenCL-эталон** (`crates/`, `apps/lfm`) | ПК, GPU | работает, даёт эталонный текст, служит оракулом |
| **Myelin** (`myelin/`) | Android, Hexagon CDSP v68 (SD888) | ядра и транспорт работают, продуктовый формат выбран, идёт интеграция |

Цель Myelin: свой рантайм на Hexagon без QNN и без GPU. Ядра HVX/HMX
собственные, KV paged, планируется continuous batching и мульти-PD.

## 2. Главное решение: формат весов — **штатный Q4_K**

Решение принято 2026-11-23 после серии экспериментов.

**Почему Q4_K, а не собственный int4:**

| формат | бит/вес | cos(W) | текст |
|---|---|---|---|
| **Q4_K нативный** | **4.75** | **1.0000 (== f32)** | ` Paris, and the capital of Japan is Tokyo…` |
| int4 + per-row масштаб | 4.0 | 0.9834 | цикл `the country… the country…` |
| int4 + блок 256 | 4.13 | 0.9905 | связный, но слабее Q4_K |
| int4 + блок 128 | 4.25 | 0.9921 | связный |

Q4_K хранится в GGUF как есть, **не требует переквантования**, и при 4.75
битах даёт текст, идентичный 9-битному int8. Порт 1:1 из OpenCL-эталона
сделан и проверен: `cos 0.9999902` против f32, де-квант бит-в-бит с
`infra-quant` (см. `myelin/dsp/hvx/Q4K.md`).

**Что это значит для нового кода:** продуктовый путь читает Q4_K из GGUF и
считает `y = Σ_b Σ_g xs·(d·sc·dot32_g − dmin·m·sum32_g)`, int32-накопление,
f32 только на комбинации. Собственный int4 остаётся исследовательской веткой
(`myelin/dsp/hmx`, `dsp/quant`, `research/trellis`) — не продуктовой.

## 4. Цифры, на которые можно опираться

### 4.1 Prefill (int4-HMX, реальные веса, M=128)

| | значение |
|---|---|
| матрица 7680×2048: compute | **386.7 мкс** (5.21 TMAC/s) |
| копия DDR→VTCM | **1.97–2.18 мс** (3.8–4.5 ГБ/с) |
| итого с двойной буферизацией | **2.37 мс** (у QNN 2.44 мс) |
| слой FFN (gate+up+down) | 6.95 мс |
| 24 слоя FFN на 128 токенов | 167 мс ≈ **765 tok/s** |

Вывод: prefill упирается в доставку весов, не в вычисления; int4 дал паритет
с QNN.

### 4.2 Decode (HVX, один PD)

| | значение |
|---|---|
| полоса на реальном GEMV (reps=1000) | **24.35 ГБ/с** |
| трафик на токен (int4) | ≈880 МБ |
| потолок по полосе | **27.7 tok/s** |
| текущий разрыв | 112.67 мс/токен (8.9 tok/s) |
| DSP-время | ~51 мс |
| вызовов на токен | **82** (24 FFN + 13 conv + 33 attention + lm_head + 11 kv_write) |

Разложение: `51 мс DSP + 82 × 0.7 мс ≈ 57 мс` накладных. Изолированный
Rust-`exec` стоит 150–190 мкс — значит накладные не в маршалинге, а в числе
вызовов.

### 4.3 Мульти-PD

| конфигурация | полоса |
|---|---|
| 1 процесс, длинная серия | 24.35 ГБ/с |
| 4 процесса, длинная серия | ~40 ГБ/с (тест с общими данными; нужен тест с разными срезами) |
| 4 процесса, короткие серии | 18.8 ГБ/с — **хуже одного** |

Несколько `remote_handle_open` в одном процессе — **одна PD**. Мульти-PD =
несколько процессов. Вывод: мульти-PD имеет смысл только с длинными сериями.

## 5. Что известно про качество (и где ещё дыры)

| дефект | статус | отчёт |
|---|---|---|
| текст вырождался в цикл | **закрыт**: причина — per-row масштаб int4, продуктовый формат Q4_K | `docs/quality-int4-cpu.md` |
| KV писался в слот `position % 32` | **закрыт**: глобальный слот по таблице страниц | `docs/kv-batch-contract.md` §9 |
| `reset_state` не чистил KV-образы | **закрыт**: `LFM_CMD_KVZERO` | `docs/kv-batch-contract.md` §10 |
| shortconv: cos 0.95 на 13 из 24 слоёв | **открыт**, `CONV16` написан но выключен (в паре с per-row ломает текст) | `dsp/conv/README.md` |
| ~3 % расхождения в слое attention | **открыт**, нужен постадийный дамп | `myelin/docs/measurements.md` |
| V-кэш в int4 ломает текст | **известно**: V держать ≥ int8; `k4v2` (V 2 бита) в текущем виде опасен | `dsp/hvx/Q4K.md` §5.4 |

Важное методическое правило: **cos(W) — плохой критерий**. Блок 128+H32 имеет
cos 0.9932 и зацикливается, а per-row+H32 с cos 0.9882 даёт связный текст.
Приёмка — `relRMSE ≤ 0.14` **и** eval на ≥20 промптах (`myelin/eval/`).

## 6. Что делать первым (порядок)

1. **Интегрировать Q4_K в продуктовый путь.** Ядро есть (`q4k_impl.c`), но
   полный пайплайн на нём не собран: сейчас работает замена только матвеков,
   attention/conv/rope — f32. Задача: `dsp.rs` + `myelin-npu` читают Q4_K из
   пака и зовут `q4k`-метод; V-кэш остаётся int8.
2. **Свести вызовы (O4/O5).** Внимание 3 RPC → 1 (хост-часть готова,
   DSP-команды 20/21 — контракт в `docs/attn-fused-contract.md`), затем один
   `exec` на слой. Это единственный путь к 25 tok/s: 36 мс трафика + ≤4 мс
   накладных.
3. **Довести короткую свёртку** (shortconv) — самый крупный измеренный дефект
   качества после формата.
4. **Мульти-PD** — только если нужна батчевая пропускная способность; для
   одного запроса хватает одного PD.
5. **FFI/сервер/TUI/APK** — довести до состояния «ставится и работает».

## 9. Открытые вопросы

1. **25 tok/s**: на одном PD потолок 27.7, реально после O4/O5 ожидается 18–22.
   Нужен ли мульти-PD ради 25 — зависит от того, подтвердится ли 40 ГБ/с на
   разных срезах.
2. **shortconv**: как включить 16-битный путь, не ломая текст (сейчас
   `CONV16` поднимает cos и зацикливает).
3. **3 % в attention**: нужен постадийный дамп (q8 → score → softmax →
   attended → o_proj) на реальной фикстуре.
4. **Hadamard H32**: даёт связный текст бесплатно, но хрупок; нужен eval.
5. **Continuous batching**: контракт (`docs/kv-batch-contract.md`) есть,
   реализации нет.
6. **8 PD**: не проверялись; 4 — только по полосе.

## 10. Как не сломать проект

- Не менять формат весов без eval-набора: один жадный промпт ничего не доказывает.
- Не включать `KEEP_MAP` (портит данные на этой `libcdsprpc.so`).
- Не полагаться на `cos(W)` как на приёмку.
- Не путать `hexagon-sim` (HMX работает) и QEMU (HMX нет).
- Общие файлы (`dsp/hvx/lfmgemv_impl.c`, `dsp.rs`, `method.rs`) — менять по
  одному владельцу за раз: именно параллельные правки уже дважды создавали
  конфликты протокола.
