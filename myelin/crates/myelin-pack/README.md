# myelin-pack — GGUF → int8 HMX crownstone

Утилита и библиотека: берёт один тензор из GGUF (`dims = [K, N]`, `N` —
выходные каналы), квантует его в симметричный int8 с **построчными** (по
выходному каналу) масштабами, укладывает в кроустоны HMX `weight.b` (1 КиБ
на тайл 32×32) и собирает 256-байтовые bias/scale-блоки, без которых
int8-store на устройстве пишет нули.

Главное — встроенная проверка качества: blob распаковывается обратно, и
считаются `cos` по каждому каналу и по тензору, `max |Δ|` в единицах
масштаба канала и доля насыщенных значений.

Раскладка взята из эмпирики на устройстве:
`myelin/dsp/hmx/research/REPORT18.md` (§3, int8) и
`myelin/dsp/qnn-reverse/REPORT.md` (§2.5, bias/scale). Загрузчик GGUF не
дублируется: используется `lfm-gguf`, де-квантование — `lfm-quant`.

## Сборка и запуск

```sh
cd myelin
cargo build --release -p myelin-pack

# список тензоров
./target/release/myelin-pack list \
  --model ../models/LFM3-1.7B-Q4_K_M.gguf --filter attn_k

# упаковать тензор, положить blob и manifest, посчитать качество
./target/release/myelin-pack pack \
  --model ../models/LFM3-1.7B-Q4_K_M.gguf \
  --tensor blk.2.attn_k.weight \
  --out /tmp/attn_k.mpk --manifest /tmp/attn_k.json \
  --quality-json /tmp/attn_k.quality.json

# независимая проверка: blob + manifest + исходный GGUF
./target/release/myelin-pack verify \
  --blob /tmp/attn_k.mpk --manifest /tmp/attn_k.json \
  --model ../models/LFM3-1.7B-Q4_K_M.gguf
```

`pack` по умолчанию требует `cos_total >= 0.999` (порог меняется
`--min-cos`). Порог по худшему каналу включается отдельно
`--min-channel-cos`: у отдельных каналов с тяжёлым хвостом `cos` может быть
ниже среднего (см. «Качество»), это не дефект упаковки.

`--rows N` читает только первые `N` выходных каналов — удобно для быстрых
проверок больших матриц; качество считается по срезу.

В библиотеке: `myelin_pack::pack_gguf(path, tensor, max_rows, options)`.

## Формат blob (версия 1)

Все целые — little endian. `K`/`N` — исходные размеры тензора,
`K_padded = ceil(K/32)*32`, `N_padded = ceil(N/32)*32`.

### Заголовок, 128 байт

| смещение | размер | поле |
|---:|---:|---|
| 0 | 4 | magic `MPK1` |
| 4 | 2 | версия формата = 1 |
| 6 | 1 | dtype: `0` = int8 |
| 7 | 1 | flags: bit0 — K дополнен, bit1 — N дополнен |
| 8 | 4 | K (исходный) |
| 12 | 4 | N (исходный) |
| 16 | 4 | K_padded |
| 20 | 4 | N_padded |
| 24 | 4 | число K-тайлов (`K_padded/32`) |
| 28 | 4 | число N-тайлов (`N_padded/32`) |
| 32 | 4 | header_bytes = 128 |
| 36 | 4 | weight_base = 128 |
| 40 | 8 | weight_bytes |
| 48 | 8 | bias_base |
| 56 | 8 | bias_bytes |
| 64 | 64 | резерв (нули) |

`weight_base = 128` не случаен: HMX требует выравнивания веса на 128 Б.

### Веса

Тайл — 32 (K) × 32 (N), 1 КиБ, signed int8:

```text
addr(k, n) = (k >> 2) * 128 + 4 * n + (k & 3)      k, n — локальные 0..31
```

Порядок тайлов в blob — **сначала K-тайл, внутри него все N-тайлы**
(`tile_order = "k_tile_major"`, шаг N-тайла 1024 Б, шаг K-тайла
`n_tiles * 1024`). Именно такую раскладку проверяет стенд:
`i8_pack_wgt(..., wl = 4)` даёт
`off = 2048*(k>>5) + 1024*(n>>5) + tile_addr`, т.е. оба N-тайла одного
K-чанка лежат в одном 2-КиБ диапазоне `weight.b:deep`
(REPORT18: «N=64, weight.b:deep (2 КБ): + 1024*(n>>5)»). Поэтому диапазон
веса на один K-чанк — `n_tiles * 1024` байт (`wgt_rt = n_tiles * 1024 - 1`).
В manifest для каждого тайла есть явные `weight_offset` и `bias_offset`.

Недостающие K и N дополняются нулями; `K`/`N` и padded-значения хранятся в
заголовке и manifest.

### Bias/scale-блок

Один блок — 256 Б на 32 выходных канала: сначала 32 младших слова (u32,
128 Б), затем 32 старших (u32, 128 Б). Битовые поля 64-битного регистра
канала (PRM §2.3.1):

```text
[15:0]  scale        fp16, [35:32] — 4 доп. бита мантиссы
[31:16] output bias  fp16, [39:36] — 4 доп. бита мантиссы
[42:40] shape
[63:43] input bias
```

Пакер пишет только `scale` в младшем слове; `out_bias`, `in_bias`, `shape`
и дополнительные биты мантиссы — нули. Это то состояние, которое проверено
на устройстве (REPORT18: `word0 = 0x6000`, `word1 = 0`).

Неявный множитель int8-конверта — **1/512** (`scale = 0x6000` → 1.0),
поэтому в блок пишется `fp16(512 * s_w[n])`, и эффективный множитель равен
`s_w[n]`. `s_w[n] = max_k |w[k][n]| / 127`, zero point = 0. Квантование
считается по уже округлённому fp16 масштабу, чтобы целые коды и масштаб на
устройстве были согласованы. Масштаб дополненных N-каналов — 0.

### Manifest (JSON)

`format`, `format_version`, `dtype`, `tensor`, `source` (файл и ggml-тип),
`k`, `n`, `k_padded`, `n_padded`, `k_tiles`, `n_tiles`, параметры тайла,
`weight_base`/`weight_bytes`, `bias_base`/`bias_bytes`, размер блока
масштабов, `blob_bytes`, `blob_fnv1a64`, таблица масштабов
(`scale_f32`, `scale_f16_bits`, `max_abs` на канал) и `tiles`:
`[k_tile, n_tile, weight_offset, bias_offset]`.

`myelin-pack verify` сверяет manifest с blob (форма, размеры, контрольная
сумма, таблица масштабов) и пересчитывает качество по исходному GGUF.

### Как этим пользоваться в HMX-ядре

* вес для K-чанка `kt` и N-тайла `nt`:
  `blob[weight_base + kt * n_tiles * 1024 + nt * 1024 ..][0..1024]`;
* диапазон для `weight.b` (один K-чанк, все N-тайлы):
  `wgt_rt = n_tiles * 1024 - 1` (1023 при N_padded=32, 2047 при 64);
* bias/scale перед store для N-тайла `nt`: `blob[bias_base + nt * 256]`,
  256 Б, ровно как `mxmem2` у int8-конверта;
* накопление по K чанками: `dC = число_чанков - 1` (int8;
  не путать с fp16, где `dC` равен числу чанков);
* активация — unsigned uint8, вес — signed int8; store
  `:after:sat.ub` пишет 2 КБ на 64 spatial, поэтому буфер выхода должен
  быть выровнен на 2 КБ (ограничение адресации store, не формата blob).

## Качество

Метрики на канал: `cos`, `max |Δ|`, `max |Δ| / s_w`, доля кодов `±127`,
`rms` и `peak/rms` (для диагностики тяжёлых хвостов). Порог приёмки —
`cos_total >= 0.999`.

Полные тензоры LFM3 (`models/LFM3-1.7B-Q4_K_M.gguf`), релизная сборка:

| тензор | источник | K × N | cos (весь) | cos канала min / mean | max\|Δ\|/s | насыщение |
|---|---|---|---:|---:|---:|---:|
| `blk.2.attn_k.weight` | Q4_K | 2048 × 512 | 0.999948 | 0.999764 / 0.999951 | 0.5000 | 0.051 % |
| `blk.2.attn_q.weight` | Q4_K | 2048 × 2048 | 0.999955 | 0.999458 / 0.999954 | 0.5000 | 0.051 % |
| `blk.0.ffn_gate.weight` | Q4_K | 2048 × 7680 | 0.999960 | 0.997056 / 0.999961 | 0.5000 | 0.051 % |
| `blk.0.ffn_up.weight` | Q4_K | 2048 × 7680 | 0.999962 | 0.999048 / 0.999962 | 0.5000 | 0.051 % |
| `blk.0.ffn_down.weight` | Q6_K | 7680 × 2048 | 0.999947 | 0.996686 / 0.999945 | 0.5000 | 0.014 % |

`max |Δ|` ровно в половину шага масштаба — это предел округления int8,
дополнительной ошибки раскладка не вносит. Насыщение — в основном ровно
один элемент на канал (глобальный максимум); доля ниже 1/K.

Почему у 4 из 2048 каналов `ffn_down` `cos < 0.999` (минимум 0.9967):
это каналы с тяжёлым хвостом — `peak/rms` 23–36 при медиане 4.1. Один
выброс задаёт масштаб, мелкие веса квантуются грубо. Это ограничение
одного масштаба на канал, а не ошибка упаковки; общий `cos` тензора и
`max |Δ|/s` в норме. Если такие каналы станут проблемой, нужен второй
уровень масштабов по K (сейчас формат и ядро его не используют).

## int4 (`weight.n`) — не реализовано

Осознанно. Из `qnn-reverse/REPORT.md` известно: 4-битный тайл = 512 Б,
`Rt = 0x1FF`, инструкция `weight.n`, но **раскладка на устройстве не
проверена**. При этом обобщённая формула из PRM §1.4 для 4-бит
(`addr = (k>>3)*128 + 4*n + (k&7)`) не даёт инъективного отображения в
512-байтовый тайл (максимум 515 > 511), то есть требует уточнения.
Сделать «на глаз» означало бы молча получить неверный вес, поэтому int4
не включён ни в CLI, ни в библиотеку. Когда раскладка будет подтверждена
стендом, сюда добавляется `DType::I4` с отдельным типом тайла.

## Ограничения

* Пакер не знает масштаб активации: на устройстве эффективный множитель
  `s_w[n]` умножается на масштаб uint8-активации, рантайм должен учесть его
  сам (у fp16-пути так же).
* `out_bias`/`in_bias`/`shape` всегда нули; асимметричный zero point не
  поддерживается (симметричный int8, как в проверенном рецепте).
* Дополнительные 4 бита мантиссы масштаба не используются — пишется
  обычный fp16.
* Раскладка весов и bias-блока подтверждена для int8 на HMX v68;
  fp16-путь и int4 этим крейтом не покрываются.

## Тесты

```sh
cd myelin
cargo fmt -p myelin-pack -- --check
cargo clippy -p myelin-pack --all-targets
cargo test -p myelin-pack
```

* `tests/synthetic.rs` — случайная матрица, нули, единицы, `±max`, одиночный
  выброс, `K`/`N` не кратны 32 (дополнение и его нули), детерминизм,
  контрольные суммы, битые blob’ы и manifest, отказ на NaN и пустых строках.
* `tests/real_model.rs` — Q4_K (`blk.2.attn_k.weight`, N=45 → N_padded=64) и
  Q6_K (`blk.0.ffn_down.weight`, K=7680), порог `cos >= 0.999`, нулевые
  padding-каналы, JSON-раундтрип manifest. Без файла модели тесты
  пропускаются с сообщением.
