# Оценочный стенд квантования (`myelin/eval`)

Стенд отвечает на вопрос «формат int4 годится для прод-пути или нет» **на
наборе промптов и teacher-forced perplexity**, а не на одном жадном
продолжении. Причина: в `myelin/docs/quality-int4-cpu.md` §8 зафиксировано,
что greedy-траектории скачут от возмущения в один LSB (пример `CONV16`), а
`cos(W)` не коррелирует с текстом. Один промпт — не измерение.

Всё считается на CPU-пути (`CpuBackend`), без телефона и без правок в
`backend/cpu.rs`: формат выбирается существующими переменными `MYELIN_CPU_*`.

## 1. Файлы

| Файл | Назначение |
|---|---|
| `prompts.jsonl` | 26 промптов: факты, перечисления, диалог, код, перевод, инструкции (en + 2 ru) |
| `corpus.jsonl` | 6 текстов для perplexity (проза, диалог, инструкция, код, русский) |
| `run_eval.py` | A/B-драйвер: запускает воркер по одному процессу на формат, печатает таблицы и пишет артефакты |
| `results/` | `summary.md`, `results.json`, `metrics.csv`, `generations.md`, логи воркеров |
| `../crates/myelin-core/examples/quality_eval.rs` | воркер: greedy-прогон + метрики + perplexity, JSONL на выходе |

Воркер и драйвер разделены намеренно: флаги `MYELIN_CPU_*` читаются
backend'ом **один раз при загрузке чекпойнта** (через `OnceLock`), поэтому
один процесс = один формат. Драйвер запускает N процессов параллельно.

## 2. Быстрый старт

```bash
cd myelin

# 1. Собрать воркер
cargo build --release -p myelin-core --features hf-tokenizer --example quality_eval

# 2. Полный A/B: 6 форматов, 40 токенов на промпт, 3 процесса параллельно
python3 eval/run_eval.py --max-tokens 40 --jobs 3

# 3. Только два формата и без perplexity (быстрая проверка траекторий)
python3 eval/run_eval.py --formats ref,perrow --no-ppl --max-tokens 24 --jobs 2

# 4. Один формат вручную (для отладки), JSONL в stdout
MYELIN_CPU_INT4=1 MYELIN_CPU_WSTATS=1 \
  ./target/release/examples/quality_eval --format perrow --max-tokens 40
```

`run_eval.py` сам собирает воркер, если бинаря нет или передан `--build`.
Полный прогон на 8 CPU-ядрах занимает ≈ 25–40 минут (≈ 13–15 минут на формат
в одном процессе: 1.7B, ~0.5–0.7 с на токен).

Полезные ключи драйвера: `--formats a,b`, `--reference ref`, `--jobs N`,
`--out-dir DIR`, `--strict` (ненулевой код возврата, если формат не прошёл
пороги), `--no-ppl`.

## 3. Набор промптов

`prompts.jsonl`, по одному JSON-объекту на строку:

```json
{"id":"fact-capital-fr","type":"facts","lang":"en","prompt":"The capital of France is","expect":["Paris"]}
```

* `type` — `facts | list | dialogue | code | translate | instruction`;
* `expect` — необязательный список подстрок: попадание всех даёт `fact_hit`.
  Это **слабая** проверка факта, а не критерий приёмки (деградировавший текст
  тоже может упомянуть «Paris»);
* `id` уникален: по нему сопоставляются форматы в таблицах.

Покрытие: 26 промптов, из них 5 фактов, 4 перечисления, 4 диалога, 4 кода,
4 перевода, 3 инструкции, 2 русских. Промпты короткие (5–25 токенов), чтобы
prefill не доминировал по времени. Добавление промпта — одна строка; менять
код не нужно.

`corpus.jsonl` — фиксированные тексты для perplexity:

```json
{"id":"prose-france","lang":"en","text":"The capital of France is Paris, ..."}
```

Тексты не должны пересекаться с промптами: perplexity меряет **удержанный**
текст. Сейчас это ~220 токенов на 6 текстов; для более узкой доверительной
оценки стоит расширить до 500+ токенов (время растёт линейно).

## 4. Что меряется

### 4.1. Perplexity — главная метрика

Teacher forcing, без сэмплирования и без зависимости от жадной траектории: на
каждом шаге модель получает **истинный** предыдущий токен, а мы считаем
`−log p(target | prefix)`.

```
PPL = exp( (1/N) · Σ −log p(t_i | t_0..t_{i-1}) )
```

* `PPL` в сводке — по всем текстам корпуса, взвешенно по числу токенов;
* `ΔPPL vs ref` — относительный рост к формату `ref`;
* `Δ per text` — среднее по текстам относительное изменение; устойчивее
  агрегата, потому что не даёт одному «трудному» тексту перевесить остальные;
* `top1`/`top5` (next-token accuracy) — сколько раз истинный следующий токен
  попал в топ-1/топ-5. Полезно как «не сошла ли модель с распределения».

Perplexity не гарантирует читаемость, но она **не** зависит от того, куда
свернула greedy-траектория, поэтому именно она решает спор «per-row vs
блок 256».

### 4.2. Метрики greedy-прогона

Greedy, фиксированный seed (для greedy он не влияет, но пишется в meta),
40 токенов по умолчанию. На каждом шаге сохраняются top-1/top-2 логиты.

| Метрика | Определение | Зачем |
|---|---|---|
| `max_token_run` | длина самого длинного повтора одного и того же токена | «the the the» |
| `repeat2/3/4` | `1 − (уникальных n-грамм)/(всего n-грамм)` | доля повторов |
| `cycle_period`, `cycle_coverage` | самый длинный **точной периодический хвост**: период `p` и доля `reps·p/n` | жёсткий цикл «A B C A B C» |
| `novel_token_frac` | уникальные токены / всего | скудный словарь |
| `immediate_repeat_frac` | доля `t[i] == t[i−1]` | залипание на токене |
| `max_function_run` | самый длинный подряд идущий отрезок служебных слов/пунктуации (en+ru) | коллапс в «of the the the» |
| `function_frac` | доля служебных/пунктуационных токенов | — |
| `top1_seen_frac` | доля шагов, где top-1 уже встречался в сгенерированном тексте | «модель не вводит нового» |
| `mean_top1_prob` | средняя вероятность top-1 | падение уверенности |
| `mean_entropy` | средняя энтропия softmax, нат | размытие распределения |
| `mean_margin` | средний зазор top-1 − top-2, нат | — |
| `fact_hit` | все `expect`-подстроки найдены (где заданы) | слабая проверка факта |

`degenerate` — флаг на промпт, если выполнено **хотя бы одно**:

```
max_token_run >= 4
|| cycle_coverage >= 0.5
|| repeat4 >= 0.35
|| max_function_run >= 6
|| function_frac >= 0.65
```

Порог намеренно грубый: его задача — отделить «текст поехал» от нормальной
речи, а не оценить стиль. `degen%` в сводке — доля таких промптов.

### 4.3. Метрики весов (из `wstats`)

Воркер запускается с `MYELIN_CPU_WSTATS=1`, поэтому в лог попадает строка
`wstats: ... cos=... relrmse=... bytes/weight=...`. Драйвер вытаскивает
`relRMSE` и `bytes/weight` в сводку. Это **диагностика**, а не приёмка:
`cos(W)` уже показал себя плохим критерием (см. `quality-int4-cpu.md` §5).

## 5. Приёмка

Формат принимается, если выполнены **все** условия (константы в
`run_eval.py`, словарь `THRESHOLDS`):

| Условие | Порог | Комментарий |
|---|---|---|
| `PPL / PPL_ref` | ≤ 1.05 | главный гейт: ≤ 5 % роста PPL |
| `PPL / PPL_ref` на каждом тексте | ≤ 1.10 | ни один текст не должен развалиться |
| `degen_rate` | ≤ 0.15 | не больше 15 % промптов с флагом вырождения |
| `cycle_rate` | ≤ 0.10 | не больше 10 % жёстких циклов |
| `repeat4_mean` | ≤ 0.20 | средняя повторяемость 4-грамм |

Пороги откалиброваны по прогону из §7: у `ref` (Q4_K) `degen_rate` не нулевой
(модель сама иногда зацикливается на коде), поэтому гейт по деградации —
абсолютный и с запасом, а решение о формате принимает PPL и per-text Δ.

Если PPL в норме, а `degen_rate` высокий — это тревожный сигнал: смотреть
`generations.md`, какие промпты выпали, и повторить на большем наборе.
Если PPL вырос, а текст «нормальный» — верить PPL: greedy-текст обманчив.

## 6. Что стенд **не** ловит

* **Абсолютное качество относительно f32.** Источник уже Q4_K; все числа —
  относительно него. Сравнение форматов корректно, «сколько потеряли от
  настоящей f32» — нет.
* **Длинный контекст.** 40 токенов генерации, ~220 токенов perplexity. KV-кэш
  и скользящее окно на длинных последовательностях не проверяются.
* **Сэмплирование.** Только greedy: temperature/top-p траектории не меряются.
* **Устройство.** CPU-путь отличается от DSP округлением и порядком операций;
  формат, прошедший здесь, всё равно нужно прогнать на устройстве.
* **Смысл/факты.** `fact_hit` — грубая подстрока, BLEU/ROUGE не считаются:
  эталонных продолжений для открытых промптов нет, а BLEU на 40 токенах
  шумит сильнее, чем помогает.
* **Статистическая значимость.** 26 промптов и ~220 токенов PPL дают
  погрешность в единицы процентов; разница форматов в 1–2 % PPL — на границе
  шума. Для тонких решений расширять `corpus.jsonl`, а не число промптов.

## 7. Результаты

Сводная таблица последнего полного прогона лежит в
[`results/summary.md`](results/summary.md) (там же таблица
`промпт × формат` и acceptance). Сырые данные — `results/results.json`,
построчные метрики — `results/metrics.csv`, тексты — `results/generations.md`.

Конфигурации прогона (`run_eval.py`, список `FORMATS`):

| id | флаги | что это |
|---|---|---|
| `ref` | `MYELIN_CPU_Q4K=1` | значения из GGUF, без переквантования (эталон) |
| `perrow` | `MYELIN_CPU_INT4=1` | симметричный int4, один absmax на строку (текущий DSP) |
| `blk256` | `MYELIN_CPU_WBLOCK=256` | симметричный int4, масштаб на 256 входов |
| `blk128` | `MYELIN_CPU_WBLOCK=128` | то же, масштаб на 128 |
| `perrow-h32` | `MYELIN_CPU_INT4=1 MYELIN_CPU_WHAD=32` | per-row после блочного Адамара H32 |
| `blk256-h32-conv16` | `WBLOCK=256 WHAD=32 CONV16=1` | кандидат DSP-комбинации |

## 8. Воспроизводимость

* Один формат = один процесс: `OnceLock` в `WeightOpts` не переживает смену
  флагов внутри процесса.
* Greedy: `top1` считается тем же правилом, что `ops::argmax` (первый
  максимум при равенстве).
* Порядок промптов и текстов фиксирован файлами; `metrics.csv` содержит все
  сырые значения, сводка — только агрегаты.
* Логи каждого формата: `results/<id>.log` (prefill, скорость, `wstats`).
