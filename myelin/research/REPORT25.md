# REPORT25: zero-point для HMX (uint8-активации) и Hadamard-ротация int4/32

Дата: 2026-11-23. Стенды: `hexagon-sim` 21.0.04 (`-mv68 --mhmx 1`, VTCM
`0xd8400000`), QEMU `qemu-system-hexagon -M V68N_1024` (QuRT + HVX,
`dsp/sim`), телефон XQ-BC72 (SD888, Hexagon v68) — **был в сети в начале
сессии, к концу отвалился от adb**. Тулчейн: Hexagon SDK 6.7,
hexagon-clang 21.0.04.

> Канонический путь: `myelin/research/REPORT25.md`. Код и стенды — в
> `myelin/dsp/quant/`; `myelin/dsp/hmx/*` не тронут (там работает другой агент).

---

## 0. Итог

1. **Zero-point на HMX решён без стоимости.** Верхнее 32-битное слово
   bias-блока — это **знаковый int32 `input_bias`, который прибавляется к
   аккумулятору до умножения на scale**. Значит `-zp·Σw[n]` вносится прямо в
   `mxmem2`-слова: ни HVX-постобработки, ни хоста. Проверено на
   hexagon-sim (`probe_bias`).
2. **HVX zero-point не нужен.** `vrmpy` на HVX — это `Vub × Vb`: беззнаковый
   вес × **знаковый** активатор. Активации остаются int8, знак никуда не
   теряется; смещение уже сидит в весах (int4 offset-8) и компенсируется
   `-8·Σa` на строку. Зафиксировано по коду и подтверждено точным регрессом.
3. **Корректность на реальных весах:** uint8+zp путь на int4/32 совпал с
   signed-int8 CPU-эталоном **бит-в-бит по 8-битному выходу**:
   `maxerr=0` на 16 384 ячейках (срез) и на **3 932 160** ячейках
   (M=8 × N=7680 × K=2048, 125.8M MAC). Старый путь (int8-байты как u8, без
   zp) даёт cos **−0.025** к f32-истине — ровно тот класс ошибки, что поймали
   в REPORT23 (`cos=0.11`).
4. **На v68 16-битного выхода из HMX нет.** `sat.uh = acc:2x1` в hexagon-sim
   насыщается на 255 (значения >255 приходят как `0xFFFF`), а `cvt.uh = acc`
   — только `arch >= 73`. Поэтому per-group int32-точки читаются через u8 с
   per-(row,group) степенью двойки и смещением; это точное усечение.
5. **Hadamard-32 лучше Hadamard-128 для нашей сетки.** На реальном
   `blk.0.ffn_gate.weight` (K=2048, N=7680, M=16) cos int4/32:
   `0.99455 → 0.99533` (H32) → `0.99537` (H128); H32 при этом в 5 раз дешевле
   и **улучшает maxerr** (0.398 → 0.370), тогда как H128 его ухудшает
   (0.482). Рекомендация: **H32 на группу**.
6. **HMX с ротацией** тоже точен: `maxerr=0` на 16.8M MAC для H32 и H128,
   cos 0.99549 / 0.99539 (против 0.99452 без ротации).
7. Регрессы: QEMU `dsp/sim` — **PASS (0/5)**; HVX на телефоне — int4 M=1/2/4
   `max_abs_err=0`, int8-выход `0/256`; `attn_test` 64 токена cos 0.999909;
   `exec_test` PASS. Критическая правка KV-слота подтверждена A/B на телефоне.

## 1. Постановка и две ветки

Проблема из REPORT23 §7.3: `activation.ub = mxmem(...)` читает байты как
**беззнаковые 0..255**, а наши активации — int8 (`−128..127`). Отрицательный
код читается как 255.

Математика:

```
zp = 128,  u = q + zp,  q ∈ [-127,127]
dot(w, u) = dot(w, q) + zp·Σ_k w[n][k]
```

Компенсация нужна **на выходную строку** `n` (не на токен и не на K-блок,
если масштаб один на строку). Вопрос был только в том, куда её дешевле
внести.

**Ветка HVX.** `myelin/dsp/hvx/lfmgemv_impl.c`:

```c
Q6_Vw_vrmpyacc_VwVubVb(acc, weight_ub, act_b);   /* U×S -> int32 */
bias = (b->w8 ? -128 : -8) * sum_act_i8(act, K); /* одна константа на строку */
```

`Vub` — это **веса** (int4 в offset-8 / int8 в offset-128), `Vb` — активации.
Активации знаковые, zp не нужен; смещение весов уже скомпенсировано
`rowbias`. **Ничего менять не требуется** — это зафиксировано и покрыто
регрессом (см. §7).

**Ветка HMX.** `activation.ub` беззнаковая ⇒ нужен `zp=128` и компенсация.
Куда её класть — измерено в §2.

## 2. Что на самом деле делает bias-блок HMX (измерено)

PRM называет поле `input_bias` (PRM §2.3.1), но кодировку в SDK нет.
`probe_bias.c` (hexagon-sim) снимает семантику: активации/веса = 1, K=32
(acc=32), scale = `0x6000` (identity), верхнее слово варьируется.

```
VTCM base=0xd8400000
ub(hi=0)          = 32
  hi=+100                        -> ub=132      (+100, точно)
  hi=-100 (int32 twos complement)-> ub=0        (32-100 < 0, sat)
  hi=-1                          -> ub=31
  hi=100<<16                     -> ub=255      (не 16.16: было бы 132)
  hi=0x00008000 (32768)          -> ub=255      (не int16: было бы 0)
  hi=INT32_MAX / INT32_MIN       -> 255 / 0
scale=0x6000 (1.0)  -> 32
scale=0x6200 (1.5)  -> 48
scale=0x5800 (0.25) -> 8
```

Вывод: **верхнее слово = signed int32, прибавляется к acc; нижнее слово =
scale (fp16, реальный множитель = fp16/512)**. Переполнения int32 нет:
`|acc| ≤ K·127·8` и `|input_bias| = 128·|Σw| ≤ 128·K·8`, для K=2048 это
`< 2^21`.

Следствие: компенсация **бесплатная и точная**:

```c
/* 32 младших слова — scale, 32 старших — input bias (по каналу n) */
for (n = 0; n < 32; n++) {
    bl[n]      = 0x6000u;                       /* identity (0x4000 = 2^-8) */
    bl[32 + n] = (uint32_t)(-128 * rowsum_q4(tile, g, n));
}
```

(В стенде дополнительно прибавлен `+B` для u8-считывания, §3.)

## 3. Выход HMX на v68: только u8

REPORT23 писал, что «прод читает аккумулятор». Локально это проверить
нельзя: `probe_round`/`probe_bias` показывают, что

* `mxmem(...):after:sat.ub = acc` — точный u8 с насыщением 0..255;
* `mxmem(...):after:sat.uh = acc:2x1` в hexagon-sim **тоже 8-битный**:
  при `acc+bias` 0..255 отдаёт корректный BE-u16, а при >255 — `0xFFFF`
  (насыщение на 255, а не на 65535);
* `cvt.uh = acc(Rs):2x1` в заголовках помечен `__HMX_ARCH__ >= 73`.

Конверсия — **усечение** (`32·0.25`: 6→1, 7→1), не округление. Это важно:
эталон может воспроизвести её целочисленным сдвигом.

Поэтому per-group int32-точки в стенде читаются так:

```
out_u8 = (dot + tbias[n][g]) >> tshift[n][g]
```

где `tbias/tshift` — калибровка на (строку, группу), степень двойки
(scale-слово `fp16(512·2^-sh)`, точное), выбранная по наблюдаемому диапазону
M токенов. `in_bias = tbias − 128·Σw`. Никакого насыщения, усечение
совпадает с HMX.

**Риск для прода:** если на реальном v68 `sat.uh` всё-таки 16-битный (модель
hexagon-sim может быть неполной), 16-битный путь даст вдвое больше
разрешения на group-точку. Это надо снять на телефоне до того, как
проектировать per-group dequant под 16 бит. Сейчас контракт — u8.

## 4. Эталон и точное тождество

Активации — ровно как в OpenCL (`kernels/decode.cl:78-121`):

```
G=32; amax=max|x| по группе; scale=amax/127 (f32); inv=127/amax;
q=convert_int_rte(x*inv) ∈ [-127,127]; amax=0 -> sc=0,q=0
```

Веса — int4/32: `scale=amax/7` (f32), `q∈[-7,7]`, half-away-from-zero,
ниббл = `q & 0xF` (two's complement; для HVX — `q+8`).

Тождество, которое проверяет HMX:

```
dot_u8 = Σ_k (q_k+128)·w_k = Σ q_k w_k + 128·Σ w_k
dot_q  = dot_u8 − 128·Σ w_k                    (int32, точно)
```

Реализация в `quant.h`: `lfm_dot_u8_zp()`; на железе то же делает
`input_bias`.

Данные: `blk.0.ffn_gate.weight` из `models/LFM3-1.7B-Q4_K_M.gguf`
(Q4_K → f32 → int4/32, N=7680, K=2048), активации — SiLU(z), z~N(0,1)
(REPORT23-подобное распределение, но **знаковое**: 8 037 из 16 384
отрицательных), per-group-32 absmax/RNE.

Стенд: `host/mkcase gen` → `hmxsim/hmxtest` (hexagon-sim) →
`host/mkcase check`.

| прогон | ячеек | MAC | maxerr (u8) | cos(exact, truth) | cos(u8, truth) | raw int8-as-u8 |
|---|---|---|---|---|---|---|
| срез M=4, N=64 | 16 384 | 0.52M | **0** | 0.9944373 | 0.9940032 | 0.0742 |
| **big M=8, N=7680** | **3 932 160** | **125.8M** | **0** | **0.9945175** | 0.9944189 | **−0.0251** |

* `maxerr=0` — побайтовое совпадение u8-плоскости HMX с CPU-эталоном,

## 6. Hadamard-ротация (второе направление качества)

### 6.1. Конструкция

Как `crates/backend-opencl/kernels/kvq4.cl`:

```
R = (1/√d) · H_d · D,   D = diag(±1),  знаки — LFM_TQ_SIGN[4]
lfm_tq_rot_fwd(v) = (1/√d) H_d (D v)
```

`quant.h` повторяет это для `d=32` (первое слово `LFM_TQ_SIGN`,
`1/√32 = 0.1767766953`) и `d=128` (все 4 слова, `1/√128 = 0.0883883476`).
`R^T R = I`; проверено на QEMU: `<Rw,Rx>/<w,x> = 1 + 1.2e-7`.

Идея: `y = W x = (W R)(R^T x)` — веса хранятся повёрнутыми (офлайн), активации
поворачиваются на лету тем же `R` (ортогональность делает выбор `R`/`R^T`
несущественным, лишь бы одинаково с двух сторон). Per-32 квантование после
ротации видит гауссизированный блок.

### 6.2. Качество на реальном тензоре

`host/rotstudy` (Q4_K → f32 → [ротация] → int4/32; активации per-32 int8),
M=16, N=7680, K=2048. `cos(full)` — int4-веса + int8-активации к f32-истине.

| активации | rot | cos(w-only) | maxerr(w) | **cos(full)** | maxerr(full) | rel | amax/rms акт. |
|---|---|---|---|---|---|---|---|
| SiLU (знаковые) | 0 | 0.9945530 | 0.3981 | 0.9945273 | 0.3983 | 0.132 | 3.152 |
| | **32** | **0.9953264** | **0.3700** | **0.9953138** | **0.3769** | **0.125** | **2.271** |
| | 128 | 0.9953712 | 0.4816 | 0.9953586 | 0.4814 | 0.160 | 2.344 |
| SiLU+0.35 (REPORT23) | 0 | 0.9924707 | 0.6097 | 0.9924506 | 0.6225 | 0.142 | 2.819 |
| | **32** | **0.9951912** | **0.4111** | **0.9951801** | **0.4127** | **0.0943** | 2.377 |
| | 128 | 0.9954007 | 0.5040 | 0.9953871 | 0.5079 | 0.116 | 2.347 |
| uniform [-1,1] | 0 | 0.9952728 | 0.5238 | 0.9952653 | 0.5233 | 0.181 | 1.696 |
| | **32** | **0.9954052** | **0.3013** | **0.9953918** | **0.3005** | **0.104** | 2.407 |
| | 128 | 0.9953968 | 0.4061 | 0.9953812 | 0.3985 | 0.138 | 2.386 |

Наблюдения:

* **H32 и H128 дают одинаковый cos** (разница ≤0.0002), но H32 **заметно
  лучше по maxerr** (на 20–40 %) и в 5 раз дешевле. H128 смешивает 4
  квант-группы, а квантуем мы всё равно по 32 — это и портит хвост.
* `amax/rms` активаций падает 3.15 → 2.27 (H32): выбросы размазываются, что и
  объясняет выигрыш на REPORT23-распределении (+0.27 п.п. cos).
* Веса: H32 по построению не меняет `amax/rms` блока (ортогональное
  преобразование внутри той же 32-группы), выигрыш идёт от декорреляции ошибки
  квантования с активацией. Он скромный (+0.08 п.п.), но стабильный.

**Решение:** H32, блок = группа = 32. H128 не даёт качества выше, дороже и
хуже по maxerr. Метаданные пака: `rotation=32, group=32, sign0=0x9e3779b9,
scale=1/√32` (sidecar `<case>.bin.meta`).

### 6.3. Стоимость

Замер на QEMU (`dsp/sim`, probe 50/51, K=2048):

```
copy baseline (8 KB):                 21 823 pcycles/token
scalar H32 rotation:               1 075 768 pcycles/token   (+1.05M)
scalar H128 rotation:              1 326 463 pcycles/token   (+1.30M)
canonical quantiser only:          1 790 385 pcycles/token
```

QEMU **не является моделью тайминга** для f32: HVX-float там эмулируется
программно (softfloat), поэтому абсолютные числа не переносятся на CDSP.
Честная оценка для устройства: H32 — это `K/32 = 64` блока × 5 стадий ×
32 float-сложения ≈ 10K операций на токен; скалярно это ~10–15K циклов
(≈10 мкс при 1.13 ГГц), векторно (одна 128-байтная группа = 1 HVX-вектор,
5 стадий `vror/add/sub/select`) — ~2–3 мкс. Для decode (~10–20 мс/токен)
это <0.1 %, для prefill M=128 — один поворот на 128 токенов, т.е. ещё меньше.
**Тайминг на телефоне — отложен** (телефон ушёл из adb до прогона `rot`).

Реализация в проде: `lfm_rot_fwd_f32` (scalar, `quant.h`) + новая команда
exec `LFM_CMD_ROTQ` (`f32[K] → rotate → int8 q[K] + f32 scale[K/32]`).
Векторный прототип H32 на `vror`/масках был собран, но **не включён**:
`vadd.sf`/`vmpy.sf` на v68 не селектятся, а qf32-путь не удалось свести
lane-exact (см. §8). Это следующий шаг; контракт (вход f32, выход q+scale,
`rot ∈ {0,32,128}`) уже зафиксирован командой exec и тестом.

## 8. Ограничения и открытые вопросы

1. **u8-считывание HMX.** `sat.uh` на v68 в hexagon-sim — 8-битный. Если на
   телефоне он окажется 16-битным, per-group dequant можно упростить и
   повысить разрешение. До проверки контракт — u8 + степень двойки.
2. **Округление конверсии** — усечение. В проде это надо повторить (shift),
   иначе расхождение в 1 LSB на каждой group-точке.
3. **Hadamard-векторизация.** Скалярный H32 включён и точен; HVX-вариант
   требует либо `vadd.sf` (нет на v68), либо целочисленной формулировки
   (fixed-point H). Оценка выигрыша: ~10 мкс → ~2–3 мкс на токен.
4. **Тайминги на устройстве** для ротации не сняты (adb отвалился). QEMU-числа
   приведены только как относительные.
5. **Q4_K отменён**: все числа выше — int4/32 (symmetric), как в эталоне;
   нативный Q4_K (с `dmin·m`) в этом отчёте не используется.
6. **Стоимость per-group dequant** (64 группы × N строк) не входит в замер;
   это отдельный проход, как и в REPORT23 §8.1.
