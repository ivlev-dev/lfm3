# REPORT26 — TCQ (trellis-coded quantization) vs наш int4/32: офлайн rate-distortion на реальных весах

Дата: 2026-11-23. Каталог: `myelin/research/trellis/`.
Вопрос: стоит ли уходить с int4/32 на trellis-квантование (TCQ, в духе QTIP/EXL3) и тратить недели на HVX-декодер.
Ответ ниже — только измерения + арифметика стоимости, без рантайма и без устройства.

---

## 1. Вывод (TL;DR)

1. **Для 4-битного режима — не стоит.** TCQ при равном битрейте выигрывает у нашего int4/32
   `+0.45…+0.94 дБ` relMSE и `+0.00036…+0.00051` по cos(y). Это эквивалент **0.07–0.15 бита**.
   Чтобы обогнать наш формат по cos(y), TCQ нужен **≈4.1–4.2 бит/вес против наших 4.5** — экономия
   ~8 % байт весов, и она почти целиком объясняется не решёткой, а тем, что в этих конфигурациях
   масштаб лежит на 128 весов, а не на 32 (см. п. 4).
2. **Основной выигрыш TCQ растёт при снижении битрейта**: 2.5 бита → +2.7 дБ / +0.032 cos(y),
   3.5 бита → +1.5 дБ / +0.003 cos(y), 4.5 бита → +0.9 дБ / +0.0004 cos(y).
   Если роадмап идёт на 3 бита и ниже — TCQ осмыслен. Для 4 бит — нет.
3. **Размер решётки: N=64…256 достаточно.** N=16 → 256 даёт +0.0011 cos(y) (m=2), N=256 → 1024
   уже ничего не даёт (±0.0001, шум). LUT декодера: **512 Б (N=64, m=3) … 4 КБ (N=256, m=4)**,
   упаковка в нибблы делит на 2. Это не проблема.
4. **Дешёвая альтернатива, которую надо проверить раньше TCQ**: int4 с масштабом на 64/128 вместо 32
   (`4.25 / 4.12` бит/вес) даёт cos(y) `0.996927 / 0.996626` при наших `0.997458` (4.5 бита), т.е.
   **−0.0005…−0.0008 cos(y) за −0.25…−0.38 бита** и **без нового декодера** (декодер даже проще:
   меньше загрузок масштаба). TCQ поверх этого добавляет только `+0.0007` cos(y) (п. 4.4).
5. **Архитектурный блокер важнее цифр качества.** Наш быстрый путь — HMX `weight.n` (int4-dot в железе),
   и узкое место — доставка весов DDR→VTCM (`hmx/README.md:69`). Книга TCQ — `2^(m+1)` уровней, т.е.
   на выходе LUT получается значение с большим динамическим диапазоном, чем int4, и **это не
   int4-матрица**: скормить её HMX как есть нельзя. Либо материализация в int8 (2× трафик — экономия
   8 % съедается удвоением), либо новый datapath.
6. **Рекомендация**: HVX-декодер TCQ не делать. Сделать int4 с более крупным блоком масштаба
   (или 8-битным масштабом при g=32) — 1–2 дня, тот же класс выигрыша. Вернуться к TCQ, только если
   FFN пойдёт на ≤3 бита; тогда брать m=3, N=64…256.

### 2.3. Решётка TCQ (как реализовано)
Энкодер — точный Витерби вдоль K (2048 шагов на строку), декодер — конечный автомат + LUT.

* Кодовая книга: `Q = 2^(m+1)` уровней с шагом Δ, значения `(ℓ − (Q−1)/2)·Δ`, ℓ = 0…Q−1.
* Два косета: чётные/нечётные ℓ. Состояние `s` допускает **только один косет**: `p(s)`.
  Уровень для веса k: `ℓ = 2·sym + p(s)`, `sym` — m-битный символ (это и есть хранимый битстрим).
* Переход: `s' = ((s << 1) | (sym & 1)) & (N−1)` — сдвиговый регистр, `p(s) = parity(popcount(s))`.
  Так как `popcount(s<<1)=popcount(s)`, получается рекурсия косета
  `p(s') = p(s) XOR бит1(ℓ)`: косет следующего шага — интеграл выбранного бита (классическая TCQ-структура).
* Начальное состояние свободное (хранится L бит на строку — 0.005 бит/вес, учтено в бюджете).
* Шаг Δ: прокси по **одному косету** (уровни фиксированной чётности, шаг 2Δ) на блок, плюс один
  глобальный множитель, откалиброванный по реальной MSE Витерби на 4 строках (детерминированно).
  Прокси по полной перемежающейся решётке даёт Δ в ~2 раза меньше нужного — это была первая версия,
  она систематически недобирала 0.5–1 дБ; сравнение обеих версий доступно (`TQ_PROXY=1`).
* Декодер проверен против энкодера (LUT-путь, вывод `PASS` в логе): значения на выходе LUT побитово
  совпадают с путём Витерби, `sse(decoded) == cost(path)`.

Прочее: поворот `R = (1/√d)·H·D` — **тот же**, что в `myelin/dsp/quant/quant.h` / `crates/backend-opencl/kernels/kvq4.cl`
(та же таблица знаков `LFM_TQ_SIGN`, та же нормировка), d ∈ {32, 128}, блок-диагонально по K.
Поворачиваются и веса, и пробы x, поэтому `y = W·x` инвариантен и cos(y) считается честно.

### 2.4. Метрики
* `cos(W)` — косинус по всем 512×2048 весам; `relMSE` = 10·log10(Σe²/Σw²); `maxerr` — max|e|.
* `cos(y)`, `cos(y) min` — косинус выхода слоя `y = W·x` (512 выходов) по 4 реальным x (min — худший
  вектор), `cos(y) gauss` — по 2 гауссовым x. **Главная метрика — `cos(y)`.**
* Время энкодера — стенное, один поток, `cc -O2`, экстраполяция на полную матрицу 7680×2048.

## 4. Анализ

### 4.1. Выигрыш TCQ при равном битрейте (ΔrelMSE / Δcos(y), H32)

| биты | TCQ | скаляр | Δ дБ | Δcos(y) | Δcos(W) |
|---|---|---|---|---|---|
| 2.50 | TCQ m2 N256 | int2/32 | **+2.74** | **+0.03150** | +0.04512 |
| 3.12 | TCQ m3 g128 | int3/g128 | +1.69 | +0.00418 | +0.00739 |
| 3.50 | TCQ m3 N256 | int3/32 | **+1.51** | **+0.00281** | +0.00576 |
| 4.01 | TCQ m4 rowsc | int4/row | +1.27 | +0.00077 | +0.00165 |
| 4.12 | TCQ m4 g128 | int4/g128 | **+1.18** | **+0.00066** | +0.00139 |
| 4.50 | TCQ m4 N256 | int4/32 tuned | +0.93 | +0.00042 | +0.00086 |
| 4.50 | TCQ m4 N256 | int4/32 shipped | +1.18 | +0.00072 | +0.00107 |

Классический предел TCQ (~1.53 дБ при высокой скорости) реализуется при m=2…3; при m=4 остаётся
0.9–1.2 дБ, потому что скалярная граница там уже почти оптимальна по масштабу блока
(наш `int4/32 tuned` получает на блок MSE-оптимальный масштаб перебором, TCQ — прокси + один
глобальный множитель; эта асимметрия работает **против** TCQ, см. п. 8).

### 4.2. Эквивалентный битрейт
Наклон скалярной кривой между 3.5 и 4.5 битами: **6.4 дБ/бит**. Отсюда эквивалент:

| TCQ | биты | relMSE | эквивалент скаляра (g32) | экономия |
|---|---|---|---|---|
| m2 N256 (H32) | 2.50 | -10.21 | 2.89 бита | **0.39 бита** |
| m3 N256 (H32) | 3.50 | -15.64 | 3.74 бита | **0.24 бита** |
| m4 g128 (H32) | 4.12 | -20.53 | 4.50 бита | **0.38 бита** |
| m4 N256 (H32) | 4.50 | -21.46 | 4.65 бита | 0.15 бита |

Замечание: экономия у `m4 g128` (0.38) больше, чем у `m4 N256` (0.15) не из-за решётки, а из-за того,
что масштабы на 128 стоят 0.125 бита вместо 0.5. Из этих 0.38 бита решётке принадлежит ~0.18
(она же даёт +1.18 дБ против `int4/g128` при равных 4.12 битах), остальное — блок масштаба.

Т.е. при 4 битах решётка даёт ~0.15 бита, при 3 — 0.24, при 2 — 0.39.
Это согласуется с теорией: TCQ окупается тем сильнее, чем грубее скалярная сетка.

### 4.3. Где TCQ «не хуже нашего int4/32» по cos(y)
Наш `int4/32` (H32): **cos(y) = 0.997458** при 4.50 бит/вес.

| TCQ-конфигурация | биты | cos(y) | вывод |
|---|---|---|---|
| m4 N256 | 4.50 | 0.997878 | лучше на +0.00042 |
| m4 N256 g128 | 4.12 | 0.997285 | **−0.00017** (в пределах шума ±0.0004) |
| m4 N256 rowsc | 4.01 | 0.997079 | −0.00038 |
| m3/4 N256 rowsc | 3.51 | 0.991713 | −0.0057 |

**Пересечение ≈ 4.1–4.2 бита/вес.** Экономия против наших 4.5 — **0.3…0.4 бита ≈ 7–9 % байт весов**,
и это верхняя оценка (см. п. 4.4 и п. 6).

### 4.4. Сколько из этого даёт именно решётка, а сколько — блок масштаба
Ключевой контроль. При 4.12 битах:

| | cos(y) | relMSE |
|---|---|---|
| int4/g128 (скаляр, блок 128) | 0.996626 | -19.35 |
| TCQ m4 g128 | 0.997285 | -20.53 |
| int4/32 (наш, 4.5 бита) | 0.997458 | -20.53 |

Отсюда: **уход с блока 32 на блок 128 (0.38 бита) уже даёт cos(y) 0.996626** — отставание от нашего
4.5-битного формата всего 0.00083, и оно закрывается решёткой на 0.00066 (≈80 %) уже при 4.12 битах.
Практический вывод: **сначала надо забрать 0.38 бита блоком масштаба** (нулевая цена в декодере),
и только потом думать, стоит ли 0.0002 cos(y) недель HVX-работы.

### 4.5. Поворот: складывается ли с TCQ
* RMS-выигрыш от поворота мал и нестабилен: у `int4/32` cos(y) 0.997192 (none) → 0.997162 (H32) →
  0.997238 (H128); у `int4/32 tuned` 0.997337 → 0.997458 → 0.997213. Т.е. **±0.0003, в пределах шума**.
  Этот тензор (ffn_gate слоя 0) уже достаточно «гауссов» по блокам 32.
* Зато поворот **убирает хвост**: `maxerr` у `int4/32 tuned` 0.0715 (none) → 0.0192 (H32) → 0.0206 (H128):
  без поворота в группах есть выбросы, и MSE-оптимальный масштаб клиппит их (отсюда большой maxerr).
* С TCQ: выигрыш решётки при m=4 растёт 0.45 дБ (none) → 0.93/0.94 дБ (H32/H128), при m=3 —
  1.39 → 1.50/1.51 дБ. Т.е. **эффекты аддитивны в дБ, но оба малы**; «сложения в бит» нет.
* Вывод: поворот оставить как страховку по хвосту (и он бесплатен по ALU), но ожидать от него
  прибавки битрейта на этих весах не стоит.

### 4.6. Размер решётки (LUT vs качество)
Δcos(y) при переходе по N (H32, m=3): N=64 → 256: +0.00008; N=256 → 1024: +0.00015 (шум).
При m=2: N=16 → 256: +0.0011. **Насыщение на N≈64–256.** Дальше растут только LUT и время.

| N | LUT m=2 | m=3 | m=4 | энкодер (m=4, замер/оценка) |
|---|---|---|---|---|
| 16 | 64 Б | 128 Б | 256 Б | ~8 с (замер на m=2 N=16) |
| 64 | 256 Б | **512 Б** | 1 КБ | ~25 с (m=3 N=64) |
| 256 | 1 КБ | 2 КБ | **4 КБ** | ~110 с (замер) |
| 1024 | 4 КБ | 8 КБ | 16 КБ | ~270–300 с (m=3 N=1024) |

(в нибблах делится на 2; таблица переходов не нужна: `s' = ((s<<1)|(sym&1))&(N−1)`).

## 5. Стоимость

### 5.1. Энкодер (офлайн, один раз на модель)
Замерено на 512 строках, экстраполяция на матрицу 7680×2048 (15.7 M весов), один поток, `cc -O2`,
наивная реализация (без SIMD/прунинга):

| конфигурация | с / матрицу | на весь 1.7B (≈1.13 G FFN-весов, 72 матрицы) |
|---|---|---|
| TCQ m3 N64 | 21–25 | ~0.5 ч |
| TCQ m3 N256 | 67–83 | ~1.5 ч |
| TCQ m4 N256 | 105–116 | ~2.2 ч |
| TCQ m3 N1024 | 262–298 | ~5.5 ч |
| int4 (любой блок) | ~2 | минуты |

Это приемлемо как разовая операция (квантование модели), но ~7 мкс на вес — оптимизируемо в 5–20×
(предвычисления ошибок по уровням, прунинг по порогу, SIMD).

### 5.2. Декодер: LUT и ALU на вес
Модель: 32 веса, скалярная/векторная оценка, без учёта latency шины.

| | int4/32 (наш) | TCQ m=4, N=256 |
|---|---|---|
| байт на 32 веса (wire) | 16 | 16 |
| распаковка | 2 сдвиг/маска | 2 сдвиг/маска (битстрим) |
| индекс LUT | — | 2 (индекс = `(s<<4)|sym`) |
| чтение таблицы | — | 1 (байт, gather) |
| знак/смещение + конверсия | 2 | 2 |
| FMA × масштаб | 1 | 1 |
| обновление состояния | — | 3 (`s<<1`, `or`, `and`) |
| **итого оп/вес** | **≈5** | **≈9–11** |
| на 32 веса | ≈165 | ≈290–350 |
| доп. LUT | — | 4 КБ (2 КБ в нибблах) |

Плюс важное свойство: состояние — это последние L бит битстрима, поэтому индекс LUT для веса k
зависит только от локального окна 2–4 байт. Значит последовательная зависимость снимается
предвычислением окон (наивная реализация «s обновляется по одному весу» — не обязательна).
Это единственная хорошая новость для HVX-реализации; основная проблема — gather по таблице
4 КБ (на HVX дорого; альтернатива — разложение LUT в сумму по битам индекса, ~8–10 оп/вес).

### 5.3. Архитектурная нестыковка (главное)
Наш быстрый путь — HMX `weight.n`, int4-dot в железе (`hmx/README.md:54,82`), и по README узкое
место — **доставка весов DDR→VTCM** (`hmx/README.md:69`), а не ALU.

TCQ-код на выходе LUT даёт 5-битные уровни (для m=4) — это **не int4-матрица**, HMX её так не съест.
Варианты:
* материализовать в int8 → трафик весов ×2, экономия 8 % превращается в −100 %;
* материализовать в int4 (только m≤3, 16 уровней) → решётка теряет весь смысл (её ценность — уровней
  больше, чем 2^m);
* делать trellis-aware dot product — новый datapath, а не «декодер к существующему».

Отсюда: даже при выигрыше 0.15–0.25 бита переход требует **нового пути доставки/умножения**, а не
«ещё одного кернела». Это и есть те «недели», о которых вопрос — и они не окупаются измеренным Δ.

## 6. Итоговая рекомендация

1. **HVX-декодер TCQ не делать** (в 4-битном режиме). Ожидаемый выигрыш 0.15 бита / +0.0004 cos(y)
   при 4.5 битах не стоит ни нового datapath, ни регулярного усложнения энкодера.
2. **Сначала забрать дешёвое**: int4 с масштабом на 64 или 128 весов.
   * 4.25 бита (`g64`): cos(y) 0.996927 (−0.00053 к нашему), −5.6 % байт;
   * 4.12 бита (`g128`): cos(y) 0.996626 (−0.00083), −8.4 % байт;
   * декодер **проще** текущего (в 4 раза меньше загрузок/броадкастов масштаба), ALU не растёт.
   Плюс проверить 8-битный масштаб в духе OCP MX (e8m0, при необходимости с per-row
   поправкой) при g=32: 4.25 бита без смены блока и без потери точности масштаба.
3. **Поворот H32/H128 оставить** — не ради RMS, а ради хвоста (maxerr 0.072 → 0.019) и устойчивости
   к выбросам; на ALU он бесплатен.
4. **Пересмотреть TCQ, если FFN пойдёт на ≤3 бита.** Тогда: m=3, N=64…256 (LUT 512 Б–2 КБ,
   энкодер ~0.5–1.5 ч на модель), ожидаемо +0.24 бита / +0.003 cos(y) против скаляра того же битрейта.
   При 2.5 битах выигрыш уже 0.39 бита и +0.031 cos(y) — там TCQ действительно меняет картину.
5. Если всё-таки строить TCQ — только вместе с решением, как кормить HMX, и с прототипом
   «decode в 4-битный тайл прямо на этапе DDR→VTCM» (тогда wire 3 бита, тайл 4 бита, HMX не меняется).
   Это единственная архитектура, где TCQ может окупиться.

## 7. Что осталось непроверенным (честно)

* **Один тензор.** `blk.0.ffn_gate.weight` слоя 0. По опыту `ffn_real_study` слой 0 — не худший и не
  лучший; для слоёв 12/23 распределения могут отличаться (там больше выбросов). Проверять на 3 слоях.
* **Прокси шага решётки.** Per-group Δ выбирается скалярным прокси по одному косету + один глобальный
  множитель, тогда как int4 получает точный per-group перебор. Это работает **против** TCQ; резерв
  оцениваю в 0.2–0.3 дБ (≈0.05 бита). Даже с ним вывод не меняется (0.15 → 0.2 бита).
* **Структура решётки.** Реализован 2-косетный сдвиговый регистр с `p(s)=parity(popcount(s))`.
  Более экзотические trellis (QTIP-style случайный LUT, больше косетов) могут дать больше — но наш
  замер насыщается по N (64→1024 ничего не даёт), т.е. ограничение не в числе состояний.
* **Токены для активаций** — псевдослучайные id (токенизатора в окружении нет). RMS и распределение
  правдоподобны (0.212), но это не текст. cos(y) на гауссовых x отличается от реальных на ≤0.003,
  так что выводы устойчивы.
* **maxerr** у вариантов с per-row масштабом плохой (0.15–0.21): один выброс в строке портит всё.
  Поэтому per-row масштаб — не рекомендация, рекомендация — g64/g128.
* Метрики на весах и на выходе слоя; сквозного влияния на перплексию/качество генерации не измеряли
  (нет прогона модели с этими весами).

## 8. Воспроизводимость

```
cd myelin/research/trellis
cc -O2 -I ../../dsp/hvx -o dump_act dump_act.c -lm
./dump_act ../../../models/LFM3-1.7B-Q4_K_M.gguf act0.bin 0,1,2 4   # ~16 c
cc -O2 -I ../../dsp/hvx -o tcq tcq.c -lm
./tcq ../../../models/LFM3-1.7B-Q4_K_M.gguf 512 act0.bin > results_final.txt   # ~4 мин
TQ_ROW0=4096 ./tcq ../../../models/LFM3-1.7B-Q4_K_M.gguf 256 act0.bin          # контроль
```

Фиксированные seed: splitmix64 (гауссовы пробы — seed 12345), токены — LCG 20240517 (как в
`ffn_real_study.c`). Переменные для экспериментов: `TQ_DS` (доп. множитель шага сверх калибровки),
`TQ_PROXY=1` (прокси по полной решётке вместо одного косета), `TQ_PAR=1` (косет = младший бит
состояния — деградирует по N, оставлено как контроль), `TQ_ROW0` (смещение строк).
Самопроверка энкодера/декодера печатается в лог (`TCQ encoder/decoder check (LUT path): PASS`).

Файлы:
* `tcq.c` — энкодер/декодер/метрики (единственный бинарь, только stdlib);
* `dump_act.c` — снятие реальных активаций через `myelin/dsp/hvx/lfm3_fwd.h`;
* `act0.bin` — 4 реальных FFN-входа слоя 0 (4×2048 f32, заголовок 4×int32);
* `results_final.txt` — полный лог 512 строк × 3 поворота × 22 варианта;
* `results512.txt`, `results256.txt` — предыдущие прогоны (история калибровки прокси шага).
